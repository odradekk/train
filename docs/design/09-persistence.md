## 边界

本文定义存档保存什么、怎样写入和恢复、存档身份、自动存档、导入与导出、示例存档和兼容策略。存档中的内容来源规则见 [02](02-definitions-and-content.md)；命令、运行时 ID 以及录制与复现见 [04](04-deterministic-simulation.md)；世界生成的输入见 [05](05-world-graph-and-generation.md#复现输入与输出)；资源与生产系统各 Job 的语义见 [10](10-resources-and-extraction.md)、[13](13-production-runtime-and-facilities.md)、[14](14-construction-refit-and-deconstruction.md)。

模块责任由 [ADR-0016](../adr/0016-separate-module-contracts-and-limit-implementation-access-to-composition.md)确定，统一见[跨层工作的责任](../contracts/README.md#跨层工作的责任)。宿主通过核心与内容的公开契约组合存档和切换会话，不读取内部结构或重算设计属性；准备、提交与回滚的接口协议留给[存档、内容发布与会话切换的跨层事务](https://github.com/odradekk/train/issues/284)。本次只确定责任，代码尚未迁移。

## 不变量

- 存档完整保存全部核心状态，包括世界图本身。读档不运行生成器，生成器的更新不改变已有存档。
- 能从内容和核心状态推算出来的派生状态不保存，场景和界面状态也不保存。
- 所有主要格式都有 Version 字段。
- Next Transaction ID、Next Entity ID、模拟步、步内序号和下一个命令编号必须进入存档。目前只有无状态随机，没有需要保存的随机状态；以后加入有状态随机流时，其完整状态必须进入存档。
- 读档要么整体成功，要么保持当前世界不变；不删除也不偷偷修补数据。

## 规则

### 存档组成

```text
Save
├─ Header：SaveFormatVersion、显示名称、保存时的真实时间、游戏内时间与资金摘要、依赖的 Mod 列表
├─ World Source：生成器版本、完整生效生成配置、内容指纹
├─ Core State
│  ├─ WorldSeed
│  ├─ 模拟步、步内序号、Next Command ID、Next Transaction ID、Next Entity ID
│  ├─ 全局玩家资金、人口与市场规则引用
│  ├─ 世界图：节点（位置、地貌概况、占据者、资源）与线路（长度、地貌概况、铁轨上限、铁轨数、断点）
│  └─ 列车、聚居地、资源与生产、战斗与世界生物等状态，见下文各节
├─ Embedded Content：引用到的设计、本局蓝图库、改装草稿、已有聚居地使用的聚居地模板
└─ External Definition References：DefinitionId + 上次使用的 Revision
```

- 上图是逻辑组成，具体字段编码在代码重构时确定。
- 资金的唯一权威值在核心状态中，头部只供列表快速显示保存边界的摘要，不能作为第二份余额使用。
- WorldSeed 是核心状态，战斗、生物行动和场景生成的带键随机都使用它。
- 世界来源只用于诊断，以及“用同样设置再生成一个新世界”，读档时不使用。生成输入的内容见 [05](05-world-graph-and-generation.md#复现输入与输出)。
- 连续量以可无损往返的 JSON 数值保存，使用与文化无关的 round-trip 表示，恢复相同的 `double` 值；不截断小数位，不允许非有限值。在有效语义内容相同的前提下，验收须比较中途保存恢复与不中断运行的结果，见 [04](04-deterministic-simulation.md#确定性验收)。
- 录制与复现包的起点存档使用同一种格式，见 [04](04-deterministic-simulation.md#录制与复现)。

### 不保存的状态

- 设计属性、当前能力和运营状态、建筑数量、选路缓存和各种查询索引：读档时由内容和核心状态重新计算。
- 场景、通知、战报、面板布局等界面状态；核心经营统计及近期运行报告不是此处的 UI 历史，按下文保存。

### 存档中的内容

- 存档中引用到的设计全部内嵌，相同内容只存一份。宿主设计中被引用的功能复合体只存引用（蓝图标识），不内嵌它的内容。存档还为每个构成哈希记一份显示名称和说明，取自第一次引入它的设计，之后不变；库存和市场显示这份名称，装在宿主上的设备则用宿主设计自己的副本（[功能复合体的来源、缺失内容的状态、结构耐久下限与嵌套排序](https://github.com/odradekk/train/issues/269)）。引用方包括实例、进行中任务的目标设计、委托和改装草稿。内容包和用户内容库中的蓝图不嵌入，它们被修改或删除后存档照常读取（[实例与蓝图：实例保存自己的设计，模板的存放与改装目标](https://github.com/odradekk/train/issues/260)，ADR-0012）。
- 本局蓝图库和改装草稿内嵌保存。
- 已有聚居地使用的聚居地模板内嵌保存，建立聚居地时复制的场景模型设计也一起内嵌，相同内容只存一份。读档后不重新选择模板，也不按新发布的模板或蓝图调整地块和场景；节点场景使用这些副本（[聚居地模板：初始状态、格式说明、Schema 与样例](https://github.com/odradekk/train/issues/266)）。
- 其他内容，例如体素定义、生物的蓝图、生物聚落类型、聚居地类型、生产流程，只保存 DefinitionId 和上次使用的 Revision，后者用于识别变化。读档时按 ID 解析为当前安装的定义，不嵌入旧副本。生物个体只引用所属物种（生物蓝图），读档和热重载时使用当前定义，不复制设计；这是“每个复合体实例有自己的设计”（ADR-0012）的例外。严格复现使用复现包中的原内容，见 [04](04-deterministic-simulation.md#录制与复现)。
- 设计只固定形状和对体素定义的引用，体素定义仍解析为当前值，所以 Mod 的平衡更新对已有车辆生效。当前规格变化时保留状态绝对值：耐久上限升高不自动修复；上限降低时不改写存档里的值，计算时取存档值和当前上限中较小的一个；相关能力重新计算。具体规则见 [02](02-definitions-and-content.md) 和 ADR-0005。
- 缺失定义时，包括缺失 Mod 或必需资产导致内容包无法通过校验的情况，读档前列出缺失的包和定义，由玩家选择取消或继续；继续时用占位保留原来的标识，规则见 [02](02-definitions-and-content.md#候选内容与运行中引用校验)（[内容包与依赖：内容定义的文件组成、依赖声明、缺依赖处理与热插拔](https://github.com/odradekk/train/issues/262)）。无法解释保存的状态时，加载明确失败。不删除状态，也不回退到旧定义。
- 占位保留状态，不丢失任何记录：部件耐久记录按部件编号保存，定义缺失的部件的记录不删除、不改写，存档时原样写回。计算时，缺失的体素和功能复合体没有能力、质量和价值，不计入结构耐久上限，也不受伤害。占位的格不能改装或修理，整辆车或整座建筑可以拆解，占位的格什么也不返还；改装草稿和目标设计不能包含缺失的定义。重新安装 Mod 后按当前定义重算，部件编号对得上的记录原样恢复，见 [03](03-vehicles-buildings-and-designs.md#缺失的内容)（[功能复合体的来源、缺失内容的状态、结构耐久下限与嵌套排序](https://github.com/odradekk/train/issues/269)）。
- Mod 数值更新后模拟结果不同，是预期行为，不属于无损往返失败。

### 文件、身份与写入

- 存档位于 `user://saves/<存档 UUID>/save.json`，是单个 JSON 文件。开头的头部供存档列表读取，不必解析整个文件。
- 每局游戏在创建时就获得存档 UUID，对应一个存档文件，保存时覆盖它。显示名称可以修改，不改变身份。
- “另存为”建立新的 UUID，之后的保存写入新存档，原存档保留。另存为不重编世界内部实体和内嵌内容的身份。
- 有未保存的修改时，返回主菜单或退出前提示“保存／不保存／取消”。保存失败或取消时留在当前对局。
- 写入时先把完整内容写到临时文件并校验，再替换原文件。失败时上一份有效存档和当前存档身份都保持不变。
- 核心模拟层因内部故障冻结时，不允许普通保存，因为这份状态在下一步必然再次出现同样的故障。这时只能导出复现包，或读取更早的存档，包括自动存档。
- 用户内容库和草稿的位置见 [02](02-definitions-and-content.md#内容目录与格式)。

### 保存边界

- 只在完整模拟步结束后，或暂停时一条完整命令结束后捕获；损伤结算、身份与所属关系变更均已完成，不保存半个事务。
- 运行时的保存请求在当前步结束后的边界捕获，不为保存额外推进模拟；暂停时直接保存最近完整边界的状态。
- 存档中没有待执行命令，见 [04](04-deterministic-simulation.md#模拟位置与执行时机)。存档保存模拟步、步内序号和下一个命令编号，使读档后的命令继续保持全序。未提交的面板输入不属于核心状态。
- 局部场景打开、战斗进行时都可以保存。

### 自动存档

- 每隔一段真实时间自动保存一次，间隔在设置中调整，也可以关闭。
- 每局游戏保留最近 3 份自动存档，轮换覆盖，与手动存档分开。
- 自动存档同样只在完整边界捕获，写入规则与手动存档相同。

### 导入与导出

- **导入**：玩家选择一个本地存档文件，按下文恢复流程完整校验。通过后建立新的存档 UUID 并加入存档列表，保留世界内部实体 ID 和模拟位置；原文件不改动，不按原 UUID 或名称覆盖已有存档。失败时不留下存档条目。
- **导出**：在完整边界捕获当前状态，写到玩家选择的位置。导出不改变当前存档的身份，也不清除未保存标记。覆盖已有文件须明确确认。
- 存档不附带 Mod、游戏程序或表现资产。缺少依赖时报告缺了什么，不自动安装 Mod。
- 携带原始内容和命令记录的 ZIP 是[复现包](04-deterministic-simulation.md#录制与复现)，不是存档。Demo 不建设下载站、账号、云同步或分享服务。

### 恢复流程

读档在候选会话中依次完成，全部通过后才整体替换当前世界：

1. **检查版本**：读取头部，检查格式版本，不支持的版本直接拒绝。
2. **解析内容**：读取内嵌的设计、本局蓝图库和聚居地模板；外部 ID 解析为当前定义；有缺失时列出缺了哪些，玩家选择取消或以占位继续。
3. **读取并适配状态**：读取核心状态，按上文适配当前定义，重新计算派生状态，并记录发生了哪些变化。
4. **一致性检查**：
   - ID 唯一，各个计数器大于所有已用的 ID；
   - 所有引用都能找到对象，例如列车到车辆、实例到设计、建筑到地块、战斗到参战者、生物群到聚落、任务到目标；
   - 结构不变量成立，例如铁轨数不超过上限、方向锁与铁轨上的列车一致、同一地点最多一场战斗、每个节点最多一个占据者。

- 任何一步失败，当前世界保持不变，并报告失败的阶段、对象和关系。
- 断轨、被毁的部件、进行中的战斗、已投降的聚居地、暂时没有可达路径，都是合法的受损状态，不算坏档。
- 内容更新可能让某份内嵌的设计或本局蓝图库中的蓝图在新规则下不再合法。这时已有实例照常运行，只在建造和改装时重新校验。
- 占位的验收：带 Mod 的受损实例存档，移除 Mod，读档并以占位继续，不做任何操作再存档，重新安装 Mod，部件耐久和结构耐久与最初完全一致。
- 读档完成后，向玩家列出发生了适配的内容。游戏处于暂停状态，由玩家开始。
- 严格复现核对原输入和状态；普通读档发生合法的内容适配时只记录变化，不要求适配后的结果与旧状态完全相同。

### 列车状态恢复

> 决策出处：[列车在图上的运行与调度](https://github.com/odradekk/train/issues/203)，2026-10-05。

以下列车与线路状态是核心状态，随存档保存，读档后不重新推算：

- 每列车的成员与顺序、位置（节点，或线路、铁轨号、方向和距离）、速度、运行或停车状态；
- 运行计划及进度：当前目标、剩余停留时间、单次计划是否已走完；
- 每列车的交战规则；
- 各条铁轨的方向锁，以及节点处进入线路和等待站台的顺序；
- 线路上进行中的扩建与修复任务及其进度，以及自动修复设置；
- 停放在聚居地的车辆。

读档后按原状态继续，结果与不中断运行一致，见 [04](04-deterministic-simulation.md#确定性验收)。

### 聚居地与建筑状态恢复

> 决策出处：[聚居地的经营、建设与场景](https://github.com/odradekk/train/issues/206)，2026-10-05。

以下聚居地状态是核心状态，随存档保存：

- 每个聚居地的所有者与关系、类型、聚居地模板和常住人口；
- 本局人口规则引用，以及各聚居地的消费剩余量、消费与人口统计进度、累计应需与实际满足量、人口变化小数余量，规则见 [18](18-population-and-labor.md#创建征服与恢复)；
- 士气、是否已投降，以及聚居地的交战规则；
- 每个地块上的建筑实例（设计、部件耐久、结构耐久）或工地；
- 进行中的建造、改装、修理、拆解任务与委托队列；
- 玩家的租用库存、它的容量和到期时间，以及是否因宣战而冻结；
- 停放在聚居地的车辆。

可用劳动力由人口及当前有效规则派生，不另存一份权威值。人口规则作为外部定义解析，不内嵌旧参数兜底；读档缺失时的保留、暂停与恢复遵循 [18](18-population-and-labor.md#内容缺失与更新)。人口规则合法变更时的未完成统计期适配，由[跨层事务票](https://github.com/odradekk/train/issues/284)明确，不借读档重置统计和余量。

### 战斗与世界生物状态恢复

> 决策出处：[战斗、征服与世界生物在核心模拟层中的表示](https://github.com/odradekk/train/issues/208)，2026-10-05。规则见 [17](17-combat.md)。

以下状态是核心状态，随存档保存：

- 进行中的战斗：稳定 ID、地点、参战者、开始的步号，以及集中攻击的目标；
- 每个武器部件和每只生物距下次攻击的剩余时间；
- 撤退中单位的脱离进度和撤退目标；
- 生物群：成员与各自的生命值、位置、当前行动与目标、所属聚落，以及袭击线路的工作进度；
- 生物聚落：聚落类型和生成进度；新聚落全局事件的进度。

战报不保存。

### 资源与生产状态恢复

资源与生产系统的以下状态都是核心状态，不是渲染缓存，也不能读档后重置：Production Plans、ActiveBatch（含所引用的 Production 或 Recovery Process、FrozenExecutionSnapshot 与 StartedFromRevision）、Facility OutputBuffer、各节点资源的储量、各资源的初始总量与再生事件序号、ConstructionJob、RefitJob、RepairJob、DeconstructionJob、Deconstruction 的主动暂停状态、UnderRefit / UnderRepair / UnderDeconstruction 锁定、地块预留、Storage Reservations、聚居地电力池的 CurrentFuelEnergyRemaining、库存中各 Stack 的数量、各 Job 的 ProgressWork 与 priorities、施工任务冻结的总工作量与系数。Save → Load → Continue 必须与不中断运行在相同语义内容和命令输入下产生一致结果；Batch 的冻结执行契约随存档恢复，外部 Definition 仍按 DefinitionId 解析当前定义。资源系统实现切片接入存档时纳入这些状态。

### 交易与运行报告恢复

依据 [19](19-markets-and-trading.md)，以下属于核心状态：全局玩家资金、本局市场规则引用、现车实例及归属和损伤、显式排序的自动交易规则及其评估进度、当前运行累计与有上限的近期报告。租约、到期后的货物占位和冻结权限沿用聚居地状态；容量划分按 [12](12-inventory-and-storage.md#租用库存与共有容量)恢复，不因重新载入多出一份仓储。

余额与实际收付款按最小货币单位的 64 位整数保存，不转成浮点数。库存、人口、设施与租约派生的补货目标、可交易量、剩余现车收购名额和即时价格不是另一份权威市场库存；读档重新推导，不凭空补货、刷新现车或清空留货。

普通停车不结束运行累计，读档不重复记账或再次生成同一圈的报告。规则合法更新不重算历史成交和已付费委托；缺市场规则时保留相关状态，停用市场与自动交易/装卸，合法手动自有转移及仍有效的人口、生产系统不因此停用。精确价格参数的编码及跨层适配由[核心契约](https://github.com/odradekk/train/issues/287)、[内容契约](https://github.com/odradekk/train/issues/288)和[跨层事务](https://github.com/odradekk/train/issues/284)落实，不从 UI 通知或未保存的命令日志重建账目。

### 示例存档

- 示例是随游戏提供的普通存档。打开示例时建立新 UUID 的副本，原示例不会被覆盖。
- 开发阶段格式会变，所以每个示例由脚本按生成配置、种子和一组命令制作，格式变化时重新制作。打开示例只按普通存档恢复，不重跑脚本。
- 制作配方（生成配置、种子和命令列表）和制作出的存档文件都提交到仓库。CI 按配方重新制作，与已提交的存档比较检查点摘要；不一致说明配方、存档或确定性有误。
- 开发构建的主菜单提供“从示例开始”。示例用于自动测试、分支验收和标准测试地图，完整 Demo 的规模与活跃负载见 [00](00-product-and-core-loop.md#测试世界与标准混合负载)，具体内容由[Demo 内容与资产清单：覆盖场景与制作验收](https://github.com/odradekk/train/issues/283)补齐。Demo 的新游戏用生成器生成，不用示例，也不能以示例通过替代默认开局的验收。
- 坏档、边界值和内部故障夹具留在自动测试数据里，不进示例列表。

### 存档兼容

- 新的核心存档沿用 `SaveFormatVersion` 字段，从版本 6 开始。
- 格式 2–5 是基于全局体素世界的旧存档，不再支持。读取时明确报告“基于全局体素世界的旧存档已不支持”，保留原文件，不转换。
- 开发阶段只读取当前版本。每次不兼容的改动都提高版本号，不写迁移代码。
- 进入正式发行阶段后，存档向前迁移成为硬性约束。
