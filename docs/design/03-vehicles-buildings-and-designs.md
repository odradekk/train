## 不变量

- 核心模拟层的车辆和建筑实例不保存体素。每个实例有自己的设计，并保存部件耐久和结构耐久。
- 设计属性只由设计和当前内容定义派生，不手写第二份数据。能力必须来自真实的 Behavior，Tag 只表达兼容性。
- 部件与结构由定义决定：带功能性 Behavior 的体素和功能复合体是部件，其余体素是结构体素。
- 位置不是持久身份。
- 建造、改装、修理和损伤都按事务原子结算。
- 车辆和建筑只能由显式的建造、委托或世界生成产生；现车交易只转移既有车辆，不创建副本，Demo 中建筑不单独买卖，见 [19](19-markets-and-trading.md)。
- Behavior 的注册顺序没有游戏语义。

## 规则

### 车辆与建筑实例

- 车辆（车头或车厢）和建筑是核心模拟层中有独立身份的对象。实例保存以下内容：
  - 实例身份；
  - 设计：实例当前的构成，以设计哈希引用（ADR-0012）；改装期间另有目标设计；
  - 每个部件的当前耐久；
  - 结构耐久；
  - 所属关系（编组或聚居地）和锁定状态等运行状态。
- 核心状态中的实例不保存体素布局，只引用设计；布局在设计中，由内容层、场景和设计编辑器读取。
- 建造（包括委托）或世界生成时，从蓝图复制一份设计给实例，之后实例与蓝图无关；修改蓝图不影响已建成的实例。现车交易保留原实例、设计和损伤，不重新从蓝图复制，也不自动修复。改装就是把实例换成另一份设计。设计随存档保存，见 [09](09-persistence.md#存档中的内容)（[实例与蓝图：实例保存自己的设计，模板的存放与改装目标](https://github.com/odradekk/train/issues/260)）。
- 实例的设计就是修理的目标，不另外保存修复目标。
- 只改名称、说明、形状或涂装时，由面板明确提交“立即应用”：目标设计须通过完整合法性校验，再由内容层确认构成没有变化，核心通过一条命令更新实例的设计引用，不创建改装任务、不消耗货物，保留损伤、部件耐久和其他运行状态。包含构成变化时，整份目标设计走正式改装，不先单独应用其中的外观或文字修改；原实例因缺失定义或内容更新而不再合法时，也不能绕过校验（[编辑器接口决策](https://github.com/odradekk/train/issues/285)，2026-10-10）。
- 外部体素定义和功能复合体按 [02](02-definitions-and-content.md) 和 ADR-0005 解析为当前安装的定义。设计属性随之重算。存档中的耐久是绝对值，上限变小时不改写存档里的值，计算时取存档值和当前上限中较小的一个；伤害和修理按这个值结算并写回。例如上限 100、当前 80，上限降到 60 时按 60 计算，上限改回 100 又是 80。外部定义更新不要求改装，也不改变设计。内容缺失时的状态见[缺失的内容](#缺失的内容)（[功能复合体的来源、缺失内容的状态、结构耐久下限与嵌套排序](https://github.com/odradekk/train/issues/269)）。
- 复合体可以包含复合体：车辆和建筑上可以装大型设备，大型设备是有自己蓝图的复合体（[非立方体形状与构造语言](https://github.com/odradekk/train/issues/245)，2026-10-09）。规则见下文[复合体嵌套](#复合体嵌套)。编组和聚居地不是嵌套，用显式关系表示：编组是车头和车厢的有序组合；聚居地拥有建筑，但聚居地本身不是建筑。

### 部件与结构

- 一个体素是部件还是结构体素，只看它的体素定义：
  - 带有至少一个功能性 Behavior 的是部件。功能性 Behavior 指提供能力的 Behavior，例如动力、存储、武器、生产。
  - 没有功能性 Behavior 的是结构体素，例如车架、装甲板、墙体、装饰。
  - 哪种 Behavior 算功能性，由 Behavior 类型自己声明，内容校验时自动归类，不另设标记。
- 部件有两种（[行为模型：行为类型、参数、按层拆分与脚本](https://github.com/odradekk/train/issues/261)，ADR-0014）：
  - **功能体素**：单格，能力靠数量叠加。引擎舱里放 40 个引擎体素就是 40 个部件，动力是它们的总和。
  - **功能复合体**：蓝图本身带功能性行为的复合体，例如大型柴油机、多格火炮，整件是一个部件，耐久上限等于其中全部体素耐久上限之和。它只能由内容包提供，里面只装没有功能性行为的体素，不再嵌套复合体；玩家可以整件装上、拆下、替换和涂装，不能编辑它的体素或行为。宿主按身份引用它，不复制它的设计，见[复合体嵌套](#复合体嵌套)。
- 每个部件有自己的耐久，上限来自它的定义。部件被毁后，它提供的能力随之消失。部件在实例内按部件编号识别。编号覆盖每个体素，不论它是不是部件：先排宿主自己的体素，按坐标排序（先 x，再 y，再 z，从小到大）；再按放置位置 `at` 的同一顺序排各个被嵌套的复合体，组装体内部也按同样的规则递归排，功能复合体整件占一个号。编号不看定义，所以内容缺失不会让编号错位。设计不变，编号就不变。核心模拟层只把它当作标识，不解读几何；体素引擎层把它换算回坐标。设计哈希、部件编号、改装时的部件对应和存档里的部件记录用同一种遍历顺序，由内容层实现一次（[功能复合体的来源、缺失内容的状态、结构耐久下限与嵌套排序](https://github.com/odradekk/train/issues/269)）。
- 结构体素不逐个追踪，合并成整车或整座建筑的结构耐久。结构耐久的上限等于全部结构体素耐久上限之和，再加上每个部件自身耐久上限的一部分。这一部分是代码常量“部件结构比例”，初始为 1/2，在测试中调整；每个部件的贡献向上取整，至少为 1。功能复合体用整件的部件耐久上限计算。所以只要布局非空，结构耐久上限就大于 0，不需要为此另设合法性规则（[功能复合体的来源、缺失内容的状态、结构耐久下限与嵌套排序](https://github.com/odradekk/train/issues/269)）。
- 结构耐久降到 0 时，车辆或建筑被摧毁。只有伤害会摧毁实例；内容更新或缺失内容让上限变小，本身不会摧毁它。
- 被摧毁的车辆直接删除，车上的货物一起损失，不留残骸，见 [17](17-combat.md#结算)；被摧毁的建筑怎样处理，见 [16](16-settlements.md)。

### 设计属性

- 内容层为每份设计计算一份设计属性（[定义按层划分：核心、体素层和显示各读哪些数据](https://github.com/odradekk/train/issues/259)），包括：
  - 蓝图类别和尺寸档位；
  - 车辆长度（格，由内容层按布局算出）；
  - 建筑的地块尺寸、建筑类型和设施兼容标签；
  - 部件表：每个部件的部件编号、定义、耐久上限和能力。定义是体素定义，或功能复合体的标识；
  - 部件经 Behavior 提供的各项能力，例如动力、库存容量（列车的载量）、武器参数、生产能力；
  - 结构耐久上限，包含部件按比例贡献的部分；
  - 总质量，等于全部体素质量之和；
  - BOM 和施工计数：BOM 件数，以及改装时与目标设计的差额；工作量由核心按施工规则计算，见 [14](14-construction-refit-and-deconstruction.md#construction-capability-与-work)（[生产与供能：Demo 的内容参数和运行契约](https://github.com/odradekk/train/issues/282)）；
  - 建造合法性的结果。
- 核心模拟层不读取坐标、朝向、形状、碰撞、贴图、显示文本和涂装，见 ADR-0011。
- 设计属性在发布内容或加载存档时计算一次，外部体素定义变化时重算。
- 核心模拟层只读取设计属性，再结合实例的部件耐久得出当前能力：被毁部件不计入。
- 速度怎样由动力和质量得出，见 [06](06-railway.md)。

### 复合体嵌套

由[复合体嵌套：大型设备装到车辆和建筑上](https://github.com/odradekk/train/issues/249)于 2026-10-09 确认，见 ADR-0013。

- **包含方式**：嵌套有两种写法（[功能复合体的来源、缺失内容的状态、结构耐久下限与嵌套排序](https://github.com/odradekk/train/issues/269)）。
  - **组装体**（可编辑的大型设备，例如炮塔）：宿主的设计记录放置位置 `at`（宿主网格中的整数格）、朝向（24 种正交方向之一）和它自己的一份设计。这份设计从蓝图复制而来，修改设备蓝图不影响任何宿主，也不会出现循环。
  - **功能复合体**：宿主只记录引用：`at`、朝向、功能复合体的蓝图标识，以及可选的一个整件涂装颜色。它的作用像一个多格体素定义：加载和热重载时解析为当前定义（布局、行为、耐久），参数更新对已有实例生效；设计哈希只包含这条引用，不包含它的内容。
  - 同一个宿主里，被嵌套的复合体的 `at` 必须各不相同，由加载时检查。
- **层数与组合**：内容加载时最多 4 层，上限是内容常量。车辆、建筑、大型设备里可以装大型设备，例如负责水平转动的炮塔里再装负责俯仰的炮管；场景模型里可以装场景模型；生物暂时不能装任何东西。
- **安装**：被嵌套的复合体不能和宿主的体素或其他被嵌套的复合体重叠，计入宿主的尺寸包络。车辆、建筑和大型设备要求全部体素和被嵌套的复合体六面连成一体，所以设备不会悬空；场景模型和生物不要求相贴，宿主也可以只含复合体（[蓝图的格式说明、Schema 与样例](https://github.com/odradekk/train/issues/265)）。不另设安装接口系统（美术 Q199）。
- **转动**：设备蓝图可以声明一个转动：绕自身的哪根轴、转轴经过哪一格、角度范围（可以是 360°）。内容层算出转动扫过的格；安装时这些格必须是空的，并且在宿主的包络之内。转动只属于表现，核心里没有瞄准。
- **功能复合体的更新**：被引用的定义更新后，如果占的格变了，已有实例照常运行，合法性在下一次建造或改装时检查。定义缺失时，它变成占位，占的格未知，见[缺失的内容](#缺失的内容)。
- **核心中**：被嵌套的复合体不是单独的对象，没有自己的身份和耐久。被嵌套的组装体（例如炮塔），它的部件就是宿主的部件；功能复合体整件是宿主的一个部件，部件表里的定义是它的标识，见[部件与结构](#部件与结构)。组装体的结构体素并入宿主的结构耐久；两种复合体的质量、能力、BOM 和工作量都计入宿主的设计属性。设备身份只存在于设计和场景中，用于整体转动、整体替换和保存为蓝图。
- **作为货物**：大型设备能入库和交易。货物种类是：体素定义标识、功能复合体标识，或组装体的构成哈希。构成哈希是去掉名称、说明、形状和涂装（递归，包括功能复合体引用上的涂装）后的设计哈希，见 [02](02-definitions-and-content.md#语义哈希字段与规范化)。改名、改形状或重涂不改变货物种类，改变构成才改变。基本货币价值等于其中全部体素的 Value 之和。装上、拆下、更换设备都算宿主的改装，见 [14](14-construction-refit-and-deconstruction.md#bom)。

### 损伤与战斗事件

- 损伤落在某个部件或结构上，战斗中的落点怎样选择，以及部件的伤害怎样溢出到结构，见 [17](17-combat.md#结算)。先损坏部件，再损坏整体。战斗事件记录：哪辆车或哪座建筑，哪个部件或结构，伤害多少，是否被毁。场景据此表现破损，见 [01](01-voxel-engine-and-scenes.md)。
- 同一个伤害事件中的全部伤害先统一施加，再判定哪些部件被毁、哪些对象被摧毁，结果不依赖遍历顺序。
- 编组中被摧毁的车辆从编组中移除。编组不会因为受损分裂成两个编组；编组成员只在显式的编组、解编命令下变化，或因车辆被摧毁而减少。
- 核心模拟层不做逐体素的连通判定、断裂拆分、按 Value 选主后继或解体。

### 缺失的内容

读档时，设计引用的体素定义或功能复合体可能不存在，例如 Mod 被卸载（[功能复合体的来源、缺失内容的状态、结构耐久下限与嵌套排序](https://github.com/odradekk/train/issues/269)）。这些格变成占位，规则如下，存档侧见 [09](09-persistence.md#恢复流程)。

- 占位不提供能力、质量和价值，不计入结构耐久上限，也不受伤害：它们的格不参与落点选择。
- 存档中的部件耐久记录按部件编号保存。占位部件的记录不删除、不改写，存档时原样写回。
- 有占位时，占位的格不能改装或修理。整辆车或整座建筑可以拆解，占位的格什么也不返还。允许打开和保存含缺失定义的草稿：保留原引用，锁定缺失部分，可以编辑其他部分；缺失未解决时不能保存为有效蓝图、立即应用或提交改装。游戏界面和控制台明确列出缺失定义、所属包和被阻止的操作，装回内容后重新校验。功能复合体的占格未知时，不把局部检查当作完整合法性通过（[编辑器接口决策](https://github.com/odradekk/train/issues/285)）。
- 重新安装 Mod 后，一切按当前定义重算；部件编号对得上的记录原样恢复。

### 设计合法性

- 车辆和建筑的合法性分为两个概念，蓝图不再携带 Archetype 规则，见[首个切片的内容数据与预置蓝图](https://github.com/odradekk/train/issues/222)：
  - **建造合法性**：这份设计能否作为它的蓝图类别被保存为蓝图和建造。它需要布局，由内容层计算，结果放进设计属性；建造和改装时核心模拟层只检查这个结果和 BOM，不重新检查布局。
  - **运营状态**：实例当前能执行哪些功能，由完好的部件和结构耐久推导，分为正常、降级、停用和摧毁。
- 设计编辑器允许保存不合法的草稿，只有合法的设计可以保存为蓝图、建造或作为改装目标。Demo 中玩家可以用通用设计编辑器设计车辆和建筑，也可以使用预置蓝图，见 [00](00-product-and-core-loop.md#demo-范围)。

以下规则由[合法性规则：通用规则、类别声明与行为附带的规则](https://github.com/odradekk/train/issues/263)于 2026-10-09 确认。

- **蓝图类别由代码提供**，和行为类型一样。类别决定对象在世界中怎样运作，需要核心代码支持。每个类别在代码里声明自己适用哪些规则；规则的实现由内容层统一提供。
- **各类别的硬规则**：不满足时不能保存为蓝图，也不能建造。

  | 类别 | 用哪种体素 | 能装进去的 | 包络 | 连通 | 能入库 | 其他 |
  | --- | --- | --- | --- | --- | --- | --- |
  | 车辆 | 货物体素 | 大型设备 | 尺寸档位 | 要求 | 否 | — |
  | 建筑 | 货物体素 | 大型设备 | 地块尺寸，见 [16](16-settlements.md#地块与建筑) | 要求 | 否 | 声明建筑类型和设施兼容标签 |
  | 大型设备 | 货物体素 | 大型设备 | 无，装上后受宿主包络限制 | 要求 | 能 | 功能复合体只能来自内容包，里面只装没有功能的体素，不再嵌套 |
  | 场景模型 | 场景体素 | 场景模型 | 无 | 不要求 | 否 | — |
  | 生物 | 场景体素 | 无 | 无 | 不要求 | 否 | 必须带 `creature` 行为 |

  连通指全部体素和被嵌套的复合体六面连成一体。
- **所有类别都适用的硬规则**：
  - 布局非空，坐标不重复；
  - 引用的定义都存在，朝向是定义允许的；
  - 嵌套最多 4 层，被嵌套的复合体不重叠，同一宿主里的 `at` 不重复，见[复合体嵌套](#复合体嵌套)；
  - 玩家的蓝图不能带功能性行为。玩家的蓝图可以引用功能复合体（记在 `used_packages` 中），但复制进来的被嵌套设计里不能出现功能性行为，否则无效。“功能复合体只能来自内容包”由加载时的这条检查保证（[功能复合体的来源、缺失内容的状态、结构耐久下限与嵌套排序](https://github.com/odradekk/train/issues/269)）。
- **行为附带的规则**：行为类型可以带规则，用了这种行为就自动检查。Demo 中只有 `rotation`：转动扫过的格必须是空的，并且在宿主的包络之内。需要新的规则类型时只能由代码添加，内容不能写规则逻辑。
- **提示**：功能上缺东西只给提示，不阻止保存或建造。例如车辆没有控制或动力时提示“不能自己行驶”，它可以当车厢；建筑没有任何功能部件；库存容量为 0。列车能不能开动由编组决定，见 [06](06-railway.md)。
- **检查时机**：
  - 加载内容包时，包里的蓝图不满足硬规则，整个包无效；
  - 设计编辑器实时显示不合法的原因和提示，能定位到具体的格、被嵌套的复合体或字段；
  - 建造和改装时，核心检查“建造合法”的结果，再检查目标条件，例如地块尺寸、设施支持的档位；
  - 体素定义更新后某份设计可能变得不合法，已有实例照常运行，只在下一次建造或改装时重新检查，见 [09](09-persistence.md#恢复流程)。
- **规则参数**：五档尺寸的格数、地块尺寸、嵌套层数上限等，Demo 中是代码常量，在实测中调整。

历史首切片的内容加载只校验必填字段、五档尺寸声明、非空布局、坐标唯一、体素引用及允许朝向，未检查六面连通或尺寸包络。这个实现范围不再限制 Demo：设计计算与校验随[六阶段计划](00-product-and-core-loop.md#开发阶段)交付，基础贯通所需的车辆、建筑和模板须满足本章适用规则，不能等编辑器完成后才校验。仍不为建造合法性增加数据驱动的规则类型。设计属性汇总全部已放置体素，不使用接触点，也不读取表现或碰撞。

### 五档尺寸

一个体素格边长 0.5 米，见 [01](01-voxel-engine-and-scenes.md)。每个车头或车厢声明一个档位：

| 档位 | 长×宽×高（格） | 约合（米） | 场景中使用的轨距 |
| --- | --- | --- | --- |
| 小型 | 52×7×9 | 26×3.5×4.5 | 标准轨距 |
| 中型 | 64×10×13 | 32×5×6.5 | 宽轨 |
| 大型 | 80×14×18 | 40×7×9 | 宽轨 |
| 超大型 | 104×20×26 | 52×10×13 | 巨型轨距 |
| 泰坦 | 136×30×38 | 68×15×19 | 巨型轨距 |

- 尺寸是包络的上限：可以不填满，任何体素都不能越界，也不能自动升档。包络以车辆纵向中点、车体中心线和轨面为基准，高度从轨面算起，包括转向架。车辆蓝图的坐标原点就是这个基准点，贴图的平铺也从这里算起（[07](07-rendering.md#cube-voxel-rendering)）；这一条由[美术文档的整体一致性检查](https://github.com/odradekk/train/issues/253)于 2026-10-09 确认。坐标轴是 +X 向右、+Y 向上、+Z 指向车头，各类别的原点和写法见[蓝图的格式](../content/blueprint.md#坐标与朝向)（[蓝图的格式说明、Schema 与样例](https://github.com/odradekk/train/issues/265)）。
- 档位不直接影响核心属性，载量、速度等一律从部件派生。档位决定场景中车辆使用哪一种轨距（见 [01](01-voxel-engine-and-scenes.md)）。某个设施能不能建造或维修某一档的车辆，见 [16](16-settlements.md)。
- 建筑不套用车辆档位，按地块尺寸校验，见 [16](16-settlements.md#地块与建筑)。

### 建造、改装与修理

- **建造**：从选定的蓝图复制一份设计，按设计消耗全部 BOM，完成时生成新实例，部件和结构都是满耐久。
- **改装**：玩家从实例打开设计编辑器，以实例当前的设计为起点建立改装草稿；含构成变化的目标通过建造合法性检查后，下“改装到目标设计”的命令。目标设计也可以直接选一份蓝图。改装在自己聚居地的设施中进行，或委托非敌对聚居地进行；只有名称、说明、形状或涂装变化时走上文“立即应用”。
  - 当前设计和目标设计之间位置和定义都不变的部件保留耐久；新旧部件编号的对应由内容层按位置和定义算出。
  - 新增的体素消耗货物。
  - 拆下的完好部件变回普通货物；受损的部件先修好再拆下，修理计入本次任务；被毁的部件不返还。
  - 任务期间实例被锁定，完成时原子地换成目标设计。
- **修理**：把实例恢复到它自己的设计：补回被毁部件，把受损部件和结构耐久恢复到上限。
- 部件不在车辆或建筑之外保留个体身份。Demo 中列车不消耗燃料，武器不消耗弹药；燃料只由聚居地电力池消耗，见 [13](13-production-runtime-and-facilities.md#power-与-fuel)（[生产与供能：Demo 的内容参数和运行契约](https://github.com/odradekk/train/issues/282)）。
- 成本、工作量、锁定与失败规则见 [14](14-construction-refit-and-deconstruction.md)。Demo 的调试验证也使用正式改装及[运行到条件](15-design-editor-and-tools.md#运行控制)，瞬时调试改装不在本轮范围内。

### Tag、Behavior、Capability

三者严格分离：

- **Tag** 用于被动分类，例如 metal、structural、organic。
- **Behavior** 描述真正的逻辑机制，例如动力、武器、仓储。Behavior 类型由游戏代码提供，声明自己是否是功能性的。
- **Capability** 是功能性 Behavior 对外提供的能力，例如 Propulsion、Traction、Storage、Weapon、Power。Capability 不允许在 Mod JSON 中任意伪造，只能由实际注册的 Behavior 推导；车辆、建筑和组装的设备只从其中的部件得到能力，蓝图上不能直接写能力。设施的 Production、Construction、Storage、Power 等能力同样只来自建筑中部件的 Behavior，Facility Tag 只表达兼容性，见 [13](13-production-runtime-and-facilities.md)。

### Behavior 组合

- 采用 Behavior Registry + Composition。避免 Voxel → MechanicalVoxel → EngineVoxel → DieselEngineVoxel 这样的继承链；一个定义可以组合多个 Behavior，每种类型最多一个。
- 行为是数据，本身不运行：核心模拟层的系统读取汇总后的能力，场景按表现参数播放动作（[行为模型：行为类型、参数、按层拆分与脚本](https://github.com/odradekk/train/issues/261)，ADR-0014）。
- 行为类型由游戏代码提供，内容只选类型、填参数；内容定义不能自带脚本。类型按功能命名、带参数，例如所有武器和生物的攻击共用 `weapon`，不按具体物品命名；新增类型之前先看现有类型加参数能不能表达。代码 Mod 注册新类型放在 Demo 之后，只在启动时加载。
- 每种类型规定自己的核心参数（写在 `simulation` 一节）、表现参数（写在 `appearance` 一节），以及能力在一份设计里怎样汇总：数值相加、只看有无，或像武器那样逐个列出。一种行为可以只有一边。
- 行为可以挂在体素定义和蓝图上。蓝图上只能是：功能复合体的功能性行为；没有部件的类别（生物）给出自身数值的行为；只有表现的行为，例如大型设备的转动。
- Demo 的行为类型：

  | 类型 | 挂在 | 提供 |
  | --- | --- | --- |
  | `propulsion` | 体素、功能复合体 | 牵引力、额定速度 |
  | `control` | 体素、功能复合体 | 能驾驶 |
  | `storage` | 体素、功能复合体 | 库存容量：列车的载量，或聚居地的库存容量 |
  | `production` | 体素、功能复合体 | 工作能力 |
  | `extraction` | 体素、功能复合体 | 开采能力 |
  | `construction` | 体素、功能复合体 | 施工能力、最大车辆档位 |
  | `power` | 体素、功能复合体 | 电力 |
  | `weapon` | 体素、功能复合体、生物蓝图 | 每次伤害、射击间隔 |
  | `platform` | 体素、功能复合体 | 站台：每个完好的部件一个 |
  | `creature` | 生物蓝图 | 生命值、速度、撤退阈值、袭击时长 |
  | `rotation` | 大型设备蓝图 | 只有表现：转动 |
  | `wheelset` | 转向架体素 | 只有表现：渲染器在这里生成轮对 |
  | `light` | 体素 | 只有表现：灯光 |

  `cargo` 并入 `storage`，因为列车和聚居地的库存容量是同一种机制（[体素定义的格式说明、Schema 与样例](https://github.com/odradekk/train/issues/264)）。挂在体素上的类型的参数见[体素定义的格式](../content/voxel.md#功能性行为的核心参数)，只挂在蓝图上的类型的参数见[蓝图的格式](../content/blueprint.md#蓝图上的行为)。
- 核心模拟层不逐体素执行 Behavior。Behavior 在内容层汇总为设计属性；运行时只根据设计属性和实例状态计算。
- Behavior 按所属对象的语境生效（转录 Q69）。
