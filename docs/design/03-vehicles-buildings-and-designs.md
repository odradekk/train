# 03 车辆、建筑与设计属性

> **所属层**：核心模拟层（车辆与建筑的实例）；设计的体素布局与合法性属于内容和设计编辑器。
>
> **修订中**：文末的“本阶段改装操作”和“本阶段静态建筑契约”原样保留了以全局体素世界为前提的旧契约。“本阶段改装操作”和“建筑验收矩阵”交给[地图](https://github.com/odradekk/train/issues/193)迷雾“新阶段”，“本阶段静态建筑契约”由[聚居地的经营、建设与场景](https://github.com/odradekk/train/issues/206)改写。改写完成前，上述规则不能作为实现依据；其余规则继续有效。

> 决策出处：实例保存的内容、部件与结构、设计属性、损伤粒度、编组成员、五档尺寸，以及建造、改装、修理的含义，由[列车与建筑在核心模拟层的表示](https://github.com/odradekk/train/issues/201)于 2026-10-05 确认。它取代了逐体素实例、连通断裂、身份继承和体素所有权等规则。Tag、Behavior、Capability 三层与 Behavior 组合沿用转录 Q10–Q16、Q43–Q52、Q63–Q88；功能设备为单格体素沿用资源转录 Q284。

## 不变量

- 核心模拟层的车辆和建筑实例不保存体素。每个实例引用一个固定的蓝图版本，并保存部件耐久和结构耐久。
- 设计属性只由蓝图版本和当前内容定义派生，不手写第二份数据。能力必须来自真实的 Behavior，Tag 只表达兼容性。
- 部件与结构由体素定义决定：带功能性 Behavior 的体素是部件，其余是结构体素。
- 位置不是持久身份。
- 建造、改装、修理和损伤都按事务原子结算。
- 车辆和建筑只能由显式的建造、委托或世界生成产生。
- Behavior 的注册顺序没有游戏语义。

## 规则

### 车辆与建筑实例

- 车辆（车头或车厢）和建筑是核心模拟层中有独立身份的对象。实例保存以下内容：
  - 实例身份；
  - 蓝图版本：蓝图在某次保存时、按语义内容计算出的 Revision；
  - 每个部件的当前耐久；
  - 结构耐久；
  - 所属关系（编组或聚居地）和锁定状态等运行状态。
- 实例不保存体素布局。布局只存在于蓝图版本中，由场景和设计编辑器读取。
- 玩家修改蓝图会产生新版本，已建成的实例仍引用原来的版本。改装就是把实例换到另一个版本。实例引用的蓝图版本随存档保存，对应 ADR-0005 中存档内嵌玩家自定义内容的规则。
- 实例引用的蓝图版本就是修理的目标，不另外保存修复目标。
- 外部体素定义按 [02](02-definitions-and-content.md) 和 ADR-0005 解析为当前安装的定义。设计属性随之重算；部件耐久保留绝对值，超过新上限时截断。外部定义更新不要求改装，也不改变蓝图版本。
- 车辆和建筑都不能嵌套。更高层的组合用显式关系表示：编组是车头和车厢的有序组合；聚居地拥有建筑，但聚居地本身不是建筑。

### 部件与结构

- 一个体素是部件还是结构体素，只看它的体素定义：
  - 带有至少一个功能性 Behavior 的是部件。功能性 Behavior 指提供能力的 Behavior，例如动力、存储、武器、生产。
  - 没有功能性 Behavior 的是结构体素，例如车架、装甲板、墙体、装饰。
  - 哪种 Behavior 算功能性，由 Behavior 类型自己声明，内容校验时自动归类，不另设标记。
- 功能设备严格是单格体素，能力靠数量叠加。因此设计中的每个功能体素都是一个部件：引擎舱里放 40 个引擎体素就是 40 个部件，动力是它们的总和。
- 每个部件有自己的耐久，上限来自它的体素定义。部件被毁后，它提供的能力随之消失。部件在实例内按它在蓝图版本中的位置识别。
- 结构体素不逐个追踪，合并成整车或整座建筑的结构耐久。结构耐久的上限等于全部结构体素耐久上限之和。结构耐久降到 0 时，车辆或建筑被摧毁。
- 被摧毁的车辆变成什么、残骸怎样处理，属于战斗规则；被摧毁的建筑怎样处理，见 [16](16-settlements.md)。

### 设计属性

- 内容层为每个蓝图版本计算一份设计属性，包括：
  - 部件经 Behavior 提供的各项能力，例如动力、载量、武器参数、生产能力、库存容量；
  - 结构耐久上限；
  - 总质量，等于全部体素质量之和；
  - BOM 和各类任务的工作量，见 [14](14-construction-refit-and-deconstruction.md)。
- 设计属性在发布内容或加载存档时计算一次，外部体素定义变化时重算。
- 核心模拟层只读取设计属性，再结合实例的部件耐久得出当前能力：被毁部件不计入。
- 速度怎样由动力和质量得出，见 [06](06-railway.md)。

### 损伤与战斗事件

- 损伤落在某个部件或结构上。战斗事件记录：哪辆车或哪座建筑，哪个部件或结构，伤害多少，是否被毁。场景据此表现破损，见 [01](01-voxel-engine-and-scenes.md)。
- 同一个伤害事件中的全部伤害先统一施加，再判定哪些部件被毁、哪些对象被摧毁，结果不依赖遍历顺序。
- 编组中被摧毁的车辆从编组中移除。编组不会因为受损分裂成两个编组；编组成员只在显式的编组、解编命令下变化，或因车辆被摧毁而减少。
- 核心模拟层不做逐体素的连通判定、断裂拆分、按 Value 选主后继或解体。

### 设计合法性

- 每种车辆和建筑由数据驱动的 Archetype 描述合法性规则，分为两个概念：
  - **建造合法性**：这份设计能否作为这种车辆或建筑被建造。例如车头需要动力部件和控制部件，要求六面连通，并且不超出所声明档位的包络。设计编辑器在发布版本时校验；建造和改装时再校验一次。
  - **运营状态**：实例当前能执行哪些功能，由完好的部件和结构耐久推导，分为正常、降级、停用和摧毁。
- 设计编辑器允许保存不合法的草稿，只有合法的版本可以建造或作为改装目标。Demo 中玩家可以用通用设计编辑器设计车辆和建筑，也可以使用预置蓝图，见 [00](00-product-and-core-loop.md#demo-范围)。

### 五档尺寸

一个体素格边长 0.5 米，见 [01](01-voxel-engine-and-scenes.md)。每个车头或车厢声明一个档位：

| 档位 | 长×宽×高（格） | 约合（米） | 场景中使用的轨距 |
| --- | --- | --- | --- |
| 小型 | 52×7×9 | 26×3.5×4.5 | 标准轨距 |
| 中型 | 64×10×13 | 32×5×6.5 | 宽轨 |
| 大型 | 80×14×18 | 40×7×9 | 宽轨 |
| 超大型 | 104×20×26 | 52×10×13 | 巨型轨距 |
| 泰坦 | 136×30×38 | 68×15×19 | 巨型轨距 |

- 尺寸是包络的上限：可以不填满，任何体素都不能越界，也不能自动升档。包络以车辆纵向中点、车体中心线和轨面为基准，高度从轨面算起，包括转向架。
- 档位不直接影响核心属性，载量、速度等一律从部件派生。档位决定场景中车辆使用哪一种轨距（见 [01](01-voxel-engine-and-scenes.md)）。某个设施能不能建造或维修某一档的车辆，见 [16](16-settlements.md)。
- 建筑不套用车辆档位。

### 建造、改装与修理

- **建造**：按蓝图版本消耗全部 BOM，完成时生成新实例，部件和结构都是满耐久。
- **改装**：玩家在设计编辑器中以实例当前的蓝图版本为起点修改，保存为新版本，然后下“改装到某版本”的命令。改装在自己聚居地的设施中进行，或委托非敌对聚居地进行。
  - 版本之间位置和定义都不变的部件保留耐久。
  - 新增的体素消耗货物。
  - 拆下的完好部件变回普通货物；受损的部件先修好再拆下，修理计入本次任务；被毁的部件不返还。
  - 任务期间实例被锁定，完成时原子地切换到新版本。
- **修理**：把实例恢复到它自己的蓝图版本：补回被毁部件，把受损部件和结构耐久恢复到上限。
- 部件不在车辆或建筑之外保留个体身份。燃料、弹药等消耗品放在车辆的库存里，不记在单个部件上。
- 成本、工作量、锁定与失败规则见 [14](14-construction-refit-and-deconstruction.md)。世界编辑器和控制台的瞬时原子改装保留为调试命令。

### Tag、Behavior、Capability

三者严格分离：

- **Tag** 用于被动分类，例如 metal、structural、organic。
- **Behavior** 描述真正的逻辑机制，例如 EngineBehavior、WeaponBehavior、StorageBehavior。Behavior 类型声明自己是否是功能性的。
- **Capability** 是功能性 Behavior 对外提供的能力，例如 Propulsion、Traction、Storage、Weapon、Power。Capability 不允许在 Mod JSON 中任意伪造，只能由实际注册的 Behavior 推导。设施的 Production、Construction、Storage、Power 等能力同样只来自建筑中部件的 Behavior，Facility Tag 只表达兼容性，见 [13](13-production-runtime-and-facilities.md)。

### Behavior 组合

- 采用 Behavior Registry + Composition。避免 Voxel → MechanicalVoxel → EngineVoxel → DieselEngineVoxel 这样的继承链；一个体素定义组合 EngineBehavior、FuelConsumerBehavior 等多个 Behavior。
- 核心模拟层不逐体素执行 Behavior。Behavior 在内容层汇总为设计属性；运行时只根据设计属性和实例状态计算。
- Behavior 按所属对象的语境生效（转录 Q69）。

### 本阶段改装操作

- 世界编辑器和控制台的世界修改命令完整覆盖添加、移除、移动、旋转和替换车辆体素；旋转遵守体素正交方向约束。
- 支持一次提交多项修改，例如交换两个零件的位置。按最终方案校验并原子提交，施工中间状态不进入 Simulation。
- 移动、旋转已有零件时保留其身份、耐久和已有运行状态；替换表示旧件移除、新件加入，不将旧件身份和状态作为新件继承。
- 非法改装整体拒绝，原车辆及其零件状态不变；成功改装保留车辆身份。制造新车仍走 Blueprint 加载、Construction Validation 与 Instantiate 流程。

### 本阶段静态建筑契约

[静态建筑的结构、占用与新增内容更新契约](https://github.com/odradekk/train/issues/106)已确认 Q1–Q15，其中 Q5、Q10 采用用户修正：断裂不产生多个建筑，原建筑整体失效；修复必须完整还原该实例最后确认的完整设计。以下为目标契约，不表示建筑实现已经完成；建筑的单一身份规则取代车辆多后继规则在建筑上的适用。

- 建筑锚点使用整数世界坐标，整体仅允许 0°、90°、180°、270° 水平旋转，不缩放。内部零件仍按各自定义允许的正交朝向放置。建筑不套用车辆五档尺寸，按实际体素、世界边界和放置约束校验。
- 普通建筑的新建条件为非空、六面连通且至少含一个带指定建筑核心标签的部件。核心允许多个，不要求某个不可替换的特殊零件。受损后的核心判定须与下述单一建筑身份规则共同解释，不再按车辆规则自动产生多个建筑后继；身份、结构合法性与运营功能仍是不同概念。
- 主动新增或改装建筑必须同时验证地形、其他建筑、轨道占格和既有完整线路的通行净空；冲突时整次拒绝并保留原状态。没有列车经过也不允许把完整线路改成无法通过；新铺轨道同样不得侵入已有建筑。
- 世界编辑器中的建筑操作完整覆盖添加、移除、移动、旋转、替换零件及批量原子修改。移动/旋转保留零件身份和耐久；替换产生新零件。按最终布局校验，非法方案整体拒绝。伤害经过正式耐久和断裂结算，不因结果不再满足新建条件而拒绝伤害。
- 建筑无论如何断裂都仍视为一个建筑，不增加聚居地的建筑数量；一旦发生断裂即失效，必须修复后才可恢复正常工作。多个仍含核心的分离部分继续归同一建筑，保留原身份、类型及聚居地归属；只要建筑身份存在，聚居地列表仍记录这一个失效建筑。即使无核心部分转为世界体素后剩余建筑恰好连通，也不能据此自动解除本次断裂造成的失效。
- 修复必须完整还原该实例最后确认的完整设计：制造时记录所用蓝图，建筑完好时成功改装可更新目标。伤害不修改目标，外部 Blueprint/Layout 更新也不替换目标；失效建筑不能把残缺布局确认为新目标来绕过修复。实际受损布局与修复目标是两份不同事实。
- 修复成功后，布局、零件定义与朝向完全符合目标蓝图，所有目标零件耐久恢复到当前定义上限。仍存在且符合目标的零件保留身份，缺失零件新建并分配新身份；建筑保留原身份并解除结构失效。仅连接断口、满足新建最低条件或改成另一合法布局，都不能作为完成修复。
- 修复允许将可确认来自原建筑、仍在目标位置且符合目标蓝图的世界体素原子转回建筑所有权；来源、零件身份、位置和匹配关系须可验证，不能只凭相同材质猜测归属。不符合这些条件的残块不自动吸收。其他建筑、地形或轨道占据目标空间，或修复侵入铁路净空时，整次拒绝并保留原状态。
- 修复目标固定的是布局、零件定义标识与朝向，不把外部零件数值冻结为旧版本；数值继续采用当前有效定义。目标需要的内容同样进入引用校验。修复不重建铁路、不消除列车故障；建筑结构、站点停靠资格和列车运行条件分别校验。
- 所有核心均被摧毁时，原建筑彻底毁坏，结束其身份并从聚居地实际建筑列表移除；剩余体素原位转为世界体素。随后重新建造产生新的建筑身份，不复用已毁坏的身份。
- 无核心碎块在同一事务中原位转为 World ownership，保留位置、朝向、耐久及已有零件身份，占用和碰撞连续更新。本阶段不模拟建筑支撑力学或坍塌，移除地基后不自动下落；转为世界体素的悬空部分也保留原位。
- 建筑体素的放置占用与铁路净空均按实际存在体素的整格保守检查，不因碰撞形状为空或局部盒而允许侵入线路；普通碰撞查询按实际碰撞形状处理。建筑中没有体素的空格保持为空，可供满足净空约束的线路穿行。

#### 本阶段内容与功能边界

- 内容须能够数据驱动地声明普通建筑、站点和其核心规则、建筑 Blueprint、站点部件接轨接口与聚居地 Layout；生成器和世界编辑器都通过正式校验与实例化入口使用它们。建筑不需要虚假的车辆尺寸或轨道接触点才能加载。
- 车辆内容继续覆盖 [06](06-railway.md) 已定五档、混编与活动车头/接触能力。普通建筑不因存在或带有类型标签就获得生产能力；核心标签只参与分类与身份/结构校验，不伪装为 Behavior。
- 碰撞沿用 [01](01-voxel-engine-and-scenes.md) 的 None、Full Box、一个或少量格内局部 Box 及正交方向约束；建筑和车辆复用此语义。三路表现及资产契约由 [07](07-rendering.md) 和[表现验收](https://github.com/odradekk/train/issues/107)收敛。
- 只实现本阶段车辆运行、建筑结构和站点接轨确需的逻辑；Capability 必须有真实实现来源，不开放 JSON 任意伪造能力或任意行为执行。资源、库存、生产、耗时施工、材料成本、通用规则语言及插件框架不在本阶段。

#### 建筑验收矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| 整数锚点、四向建筑旋转、内部零件方向 | 合法位置落位一致；越界、同格冲突、非法整体旋转或缩放整体拒绝，不套用车辆尺寸档。 |
| 新建结构与核心 | 空布局、非六面连通布局或没有核心的布局拒绝；满足其他放置约束的单核心、多核心连通建筑均可新建。 |
| 建筑与铁路双向空间校验 | 新增/改装侵入地形、其他建筑、轨道占格或既有完整线路净空均整体拒绝，即使线路没有列车；反向铺轨侵入建筑也拒绝。 |
| 五类修改与批量交换 | 原子提交最终布局；移动/旋转保留零件身份和耐久，替换分配新身份；失败不改变实例、所有权及身份分配状态。 |
| 双核心建筑断开、单核心侧翼脱落 | 前者仍是同一个失效建筑并拥有多个分离部分；后者无核心碎块原位转世界，即使剩余部分连通也保持断裂失效。聚居地计数均不增加。 |
| 最后核心毁坏 | 原建筑身份结束、聚居地引用撤销、残块原位转世界；新建不复活旧身份。 |
| 修复目标的建立与更新 | 制造时记录完整设计；完好建筑成功改装后更新目标。伤害、外部 Blueprint/Layout 更新不改目标；失效建筑不能确认残缺布局来绕过修复。 |
| 修复缺口及受损零件 | 完整恢复实例目标布局、定义和朝向，并恢复当前定义上限耐久；可复用零件保身份，缺失件分配新身份。单纯接通断口不能冒充完整修复。 |
| 原位残块与外部障碍 | 原建筑且匹配的残块可原子收回；外来同材质体素不能冒充。目标被占或侵入铁路净空时整次拒绝，不部分修复、不偷偷挪动障碍。 |
| 占用、碰撞、净空与显示 | None/局部盒仍占整格且参与整格铁路净空检查；碰撞按实际形状，空洞不按建筑包围盒填充。修改和所有权转移后无重复占用、重复显示或残留碰撞。 |
| 站点断裂、接口部件消失、建筑修复 | 站点可用性和接口状态反映真实建筑；物理轨道不随站房受损自动删除，列车已有占用与安全保护不消失。 |
| Blueprint/Layout、零件语义及纯表现更新 | 新模板不重写已有布局或修复目标；合法零件更新按当前定义适配，纯表现不改变碰撞/连接；非法候选整批拒绝并保留旧内容与实例。 |
| 保存受损、多分离部分、原位残块及修复后状态 | 恢复实际布局、单一建筑身份、失效状态、修复目标、可验证残块来源与站点引用；读档不自动修复或多生建筑。完整目标入档、残块来源及唯一所有权校验见 [09](09-persistence.md#静态建筑与修复目标恢复)，跨进程对照见 [04](04-deterministic-simulation.md#确定性验收)。 |

以上需有领域契约检查、真实 Godot 显示/碰撞验证和世界编辑器操作证据。损伤与修复中的事务及确定性沿用 [04](04-deterministic-simulation.md)；建筑位置、统计、站点关系由 [16](16-settlements.md)消费，不再保存与实际实例脱节的手工计数。
