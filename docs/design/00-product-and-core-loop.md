# 00 产品形态与核心循环

> 决策出处：转录 Q2、Q8、Q109；`CONTEXT.md` 与历史 [MVP 规格](https://github.com/odradekk/train/blob/eb6a502329a1830a51c5da62e2c24545f34c9a46/docs/specs/mvp.md) 描述的 MVP 已验证循环；2026-09-05 围绕 [#29](https://github.com/odradekk/train/issues/29) 的产品方向确认。当前首版以专门测试场景验收体素基础，正式游戏场景与贸易玩法后续接入。

## 边界

本文回答三个问题：这是什么游戏，玩家在做什么，为什么是体素世界与桌面常驻窗口。经济规则、贸易方案编辑、列车调度、车辆设计 UI 的具体设计不在本文，留待后续扩充。窗口行为细节见 [08](08-desktop-window-and-camera.md)。

## 不变量

- 玩家不是一个直接控制的角色。
- 所有管理窗口只是同一个 World Model 的不同 View，不拥有独立世界状态；关闭辅助窗口不影响 Simulation。

## 规则

### 产品形态（已定）

游戏是一款以火车自动运行和贸易模拟为核心的桌面放置游戏。主要游戏视角是一个长期存在于桌面的 3D 条形窗口：

```text
┌──────────────────────────────────────┐
│                                      │
│          用户正在使用的其他软件        │
│                                      │
├──────────────────────────────────────┤
│         游戏 3D 火车观察窗口           │
└──────────────────────────────────────┘
```

首版默认：Windows-first；无边框；Bottom Dock；占满目标显示器宽度；高度可调整；默认主显示器，玩家可选择其他显示器；可以切换为 Floating 模式；Floating 模式允许任意移动和合理范围内调整尺寸，可选 Always-on-top；3D 窗口为游戏主窗口。

其他管理功能使用独立窗口，包括未来的：自动贸易策略、火车管理、车辆升级、车辆设计器、经济管理、其他 Gameplay UI。首版关闭主 3D 窗口视为退出游戏。

### 核心循环与当前阶段

- 长期产品方向沿用 MVP 已验证的循环：配置贸易方案 → 观察自动运行 → 阅读运行报告 → 策略迭代。相关术语见 `CONTEXT.md`。
- 玩家在桌面上长期观看底部 3D 条中的火车自动贸易，通过独立窗口配置贸易方案、升级改装与设计车辆（转录 Q8）。
- 当前首版先建立稳定、高效、支持修改的体素世界，并验证列车运行与桌面常驻观察。贸易玩法已在 MVP 验证，后续版本再接入，不作为当前首版验收条件。
- 开发按小切片推进，每次通过专门测试场景验证所选能力。达到下文验收条件后进入正式游戏场景开发，不以“整个系统完成”作为门槛，也不提前实现所有未来玩法需要的通用能力。

### 为什么是体素世界

- 转录 Q2：统一的体素模型让可交互物、设备、资源、地形共用一套建模与开发方式，简化内容生产；UI 与特效除外。
- 转录 Q109：铺轨、破坏地形、桥梁隧道等日后必加，它们依赖可破坏、可组合的体素世界，"这也是使用体素的重要原因之一"。
- 选择体素系统的重要原因是更简单、高效地支持修改、破坏与自定义。当前首版必须实际验证世界与车辆的这些能力，而不只展示静态体素场景。
- 可开采的自然资源、可铺设与破坏的铁路与地形、可组合和改装的车辆，是这些能力支持的玩法方向；不因此要求首版实现完整的开采、施工或车辆设计流程。
- 武器、生物属于"一切皆体素"的愿景（[01](01-voxel-world.md)），不在首版。

## 首版范围

当前首版是通过专门测试场景验收的体素基础版本。测试场景可直接加载地形、轨道与车辆，提供体素增删、破坏和车辆修改操作，用于开发、重复验证与性能测量；不要求正式面向玩家的建造或设计 UI。

本阶段长期人工调试统一进入 [Playground](playground.md)，支持生成、固定配置与恢复存档。旧四切片作为回归用例迁移，满足对应覆盖等价与验收条件后退役旧入口和专用驱动；独立自动验证继续保留。

测试场景直接使用正式的世界模型、模拟、渲染与存档代码。进入正式游戏场景开发前，需要证明：

- 按 [05 的生成契约](05-world-generation-and-settlements.md)生成实际地形、聚居地与至少四站网络，支持 10 节泰坦能力及三列联合运行；五档和跨档混编通过 [06 的几何与网络契约](06-railway.md)，包含弯坡、道岔、冲突防护及持续通行。
- 修改与破坏后，世界状态、显示和碰撞保持一致。
- 修改车辆后，其结构和运行行为符合规则。
- 静态建筑断裂后保持单一身份并整体失效，修复完整还原实例最后确认的设计；身份终止及残块按 [03](03-composite-and-behavior.md#本阶段静态建筑契约)验收。
- 全图全精度模拟、跨进程确定性、普通存档恢复及严格复现通过 [04](04-deterministic-simulation.md#确定性验收) 与 [09](09-persistence.md#本阶段保存与复现契约)的证据矩阵；默认有界录制和故障复现包可用。
- [Playground](playground.md)的生成、固定配置与恢复入口统一，三路表现、跨区观察及诊断可用，旧四切片按覆盖等价条件退役。
- 在冻结的世界规模、负载和修改频率下，普通 1080p 窗口中的运行与长期稳定满足 [性能验收契约](roadmap.md#本阶段性能验收)。目标实机暂无时保持待验证；桌面停靠和多显示器不作为本阶段完成门槛。

修改与破坏测试操作、Blueprint 形态、阵营延期及窗口策略已由 [#30](https://github.com/odradekk/train/issues/30) 确认，详见 [03](03-composite-and-behavior.md)、[08](08-desktop-window-and-camera.md) 与 [roadmap](roadmap.md)。[#37](https://github.com/odradekk/train/issues/37) 已确定前四个切片：单 Chunk 修改与破坏 → 跨 Chunk 修改与世界恢复 → 静置车辆改装与破坏 → 固定直轨运行与状态衔接。每个切片都服务于上述验收目标，但完成四个切片不等于完整首版已验收。

领域自动测试、Godot 集成检查与人工观感共同验收；场景尺寸、输入序列和明确通过条件由 [#38](https://github.com/odradekk/train/issues/38) 写入各切片 spec。前四个切片持续记录性能基线并及时排查卡顿或退化；大世界、高频修改与多列车的正式性能门槛由后续规模测试结合实际测量确定，不能把小场景通过视为规模保证。

## 明确延后

正式游戏场景、经济、AI、自动贸易、复杂运营调度、正式车辆设计与铁路施工 UI；Overlay、Top Dock、托盘与后台模式、离线进度（转录 Q18、Q154、Q85）。开发测试所需的修改操作入口属于首版。
