# 00 产品形态与核心循环

> 决策出处：[产品定位、玩法支柱与 Demo 范围](https://github.com/odradekk/train/issues/194)（2026-10-04）重新确定了产品定位、核心循环、体素的作用和 Demo 范围，取代此前依据转录 Q2、Q8、Q109 确定的定位，以及“桌面底部常驻 3D 条形窗口”的产品形态。架构调整见地图[体素引擎改作局部场景：设计文档与 open issue 全面修订](https://github.com/odradekk/train/issues/193)。`CONTEXT.md` 与历史 [MVP 规格](https://github.com/odradekk/train/blob/eb6a502329a1830a51c5da62e2c24545f34c9a46/docs/specs/mvp.md) 描述的 MVP 已验证贸易循环，是经济主循环的基础。

## 边界

本文回答四个问题：这是什么游戏，玩家在做什么，体素起什么作用，Demo 包含什么。战斗、征服、市场、人口等玩法的具体规则不在本文。窗口与界面见[窗口与界面的设计和规划](https://github.com/odradekk/train/issues/207)。

## 不变量

- 玩家扮演列车长，是管理者，不是一个直接控制的角色，也不操控单个单位。
- 世界自动运行。玩家通过计划、规则、建设和战前安排影响世界，不需要持续操作。
- 管理界面不拥有独立的世界状态。局部场景与核心模拟层的关系见[分层架构与局部场景的权威边界](https://github.com/odradekk/train/issues/198)。

## 规则

### 产品定位

游戏是一款自动经营（放置）游戏，经济、建设、战斗是三个并列的主循环。玩家扮演列车长，经营一家列车公司：设计并组建车队，取得、经营和建设聚居地，与世界生物和敌对的聚居地作战，通过控制市场和资源扩大经营。

“放置”指世界自动运行：玩家制定运行计划、交易规则、建设和战斗安排，观看自动运行的结果，按需调整；玩家可以开着游戏做别的事。游戏不采用离线收益、数值指数增长和周期性重置这些传统放置机制。

游戏使用普通游戏窗口，不做桌面停靠。默认视图、宏观地图的呈现、各类场景之间的切换、管理界面的形式、失焦时的行为和相机，由[窗口与界面的设计和规划](https://github.com/odradekk/train/issues/207)决定。[08](08-desktop-window-and-camera.md) 中 Bottom Dock、Floating、AppBar 等桌面停靠规则已不适用，由该票改写。

### 核心循环

三个主循环并列，每个循环都是“制定计划 → 观看自动运行 → 按结果调整”：

- **经济**：制定运行计划和交易规则，列车自动运输，聚居地自动生产和交易；玩家阅读运行报告和经营报告，再调整方案。MVP 已验证的“配置贸易方案 → 观察自动运行 → 阅读运行报告 → 策略迭代”是它的基础，相关术语见 `CONTEXT.md`。
- **建设**：在自己的聚居地建造和改装建筑（生产、仓储、防御、站点），扩建铁轨、修建新线路，设计并制造列车；结果是产能、运力和防御提高。
- **战斗**：给列车安装武器，安排护卫和路线，设定交战规则。遭遇敌人时自动结算，玩家可以打开战斗场景观看，并下少量高层指令。战后修复损伤；胜利带来聚居地、资源或更安全的线路。

三个循环互相支撑：经济为建设和战斗提供资金和货物；建设提高经济产出和战斗能力；战斗保护线路、取得新的聚居地，从而扩大经济。玩家的长期成长体现为车队规模、拥有的聚居地，以及对市场和资源的控制。

### 开局与聚居地

- 开局时玩家是一家列车公司，有资金和少量列车，没有聚居地。
- 玩家通过征服，或在无人节点上建立新聚居地，取得聚居地。只有自己拥有的聚居地可以建造建筑、管理生产。
- 聚居地对玩家的关系分为玩家拥有、非敌对和敌对。所有非敌对聚居地都向玩家提供有偿服务：委托制造、维修和改装列车，以及租用仓库。在取得第一个聚居地之前，建设循环靠设计列车、委托服务和修建铁路进行。敌对关系怎样产生和解除，属于具体玩法规则。
- Demo 中玩家的对手是不属于玩家的聚居地和世界生物。这些聚居地各自独立，不组成势力；Demo 中没有与玩家竞争的 AI 势力。世界生物在世界中游荡，或从巢穴出发，袭击线路和聚居地；清剿巢穴可以获得奖励，或者打通一片区域。

### 战斗

- 玩家以战前安排为主，包括列车设计、编组、护卫、路线和交战规则。战斗中可以下少量高层指令，例如撤退、集中攻击某个目标，但不操控单个单位。
- Demo 的战斗单位只有三类：装有武器的列车（武器是在设计编辑器中安装的零件）、聚居地的防御建筑、世界生物。没有步兵、下车作战的乘员或飞行单位。
- 战斗发生在世界图的边或节点上，即线路、聚居地和巢穴。
- 战斗怎样结算、战斗场景的结果是否写回，由[分层架构与局部场景的权威边界](https://github.com/odradekk/train/issues/198)决定。

### 体素的作用

核心模拟层负责整个世界，不涉及体素。体素引擎只用于玩家关注的局部场景：列车与建筑的设计和改装、聚居地管理与建设、战斗、列车运行。选择体素作为表现层的理由：

- 美术成本低：不需要高精度建模，配合合适的 shader 也能做出精美的画面。
- 玩家设计列车和建筑的门槛低：在编辑器里摆放体素零件即可。
- 战斗中的破坏效果容易表现。

原先“铺轨、地形破坏、桥梁隧道依赖可破坏、可组合的体素世界”（转录 Q109）这条理由依赖全局体素世界，已经删除。

## 本阶段范围

> **待改写**：本节和下一节以全局体素世界为前提（全图全精度模拟、四站物理铁路网络、10 节泰坦等），已不符合新架构。新阶段的范围、验收条件与性能目标由地图[体素引擎改作局部场景：设计文档与 open issue 全面修订](https://github.com/odradekk/train/issues/193)中的迷雾“新阶段”重新规划。在此之前，这两节只作历史参考，不作为验收依据。

本阶段是 Demo 之前的开发里程碑，交付通过世界编辑器和独立自动测试验收的体素基础；具体分期与排期见各实施 Issue。人工调试统一进入世界编辑器，按[存档工作流](09-persistence.md#世界编辑器存档工作流)新建、生成、打开和保存普通存档，直接创建和修改地形、轨道、建筑与车辆，用于开发、重复验证与性能测量；不要求正式面向玩家的建造或设计 UI。

编辑器可以免费、即时创建和修改对象，并可绕过后续玩法的进度和操作权限；身份唯一、引用完整、事务原子性、确定性，以及相应操作的结构、铁路几何和占用规则仍须满足。正式伤害形成的断轨、残骸和失效建筑是可保存、可运行的受损状态，不因不满足新建条件而被当作坏档。

编辑器、正式游戏、控制台和自动测试共用最终的领域校验与提交逻辑，上层流程可以不同。例如编辑器即时放置建筑，正式游戏以后先检查材料并执行建造任务，完成时仍经过同一建造校验与世界事务。相机、面板、预览和 Godot 图形节点不是世界事实的来源。

世界编辑器和自动测试直接使用正式的世界模型、模拟、渲染与存档代码。进入正式游戏场景开发前，需要证明：

- 按 [05 的生成契约](05-world-generation-and-settlements.md)生成实际地形、聚居地与至少四站网络，支持 10 节泰坦能力及三列联合运行；五档和跨档混编通过 [06 的几何与网络契约](06-railway.md)，包含弯坡、道岔、冲突防护及持续通行。
- 修改与破坏后，世界状态、显示和碰撞保持一致。
- 修改车辆后，其结构和运行行为符合规则。
- 静态建筑断裂后保持单一身份并整体失效，修复完整还原实例最后确认的设计；身份终止及残块按 [03](03-composite-and-behavior.md#本阶段静态建筑契约)验收。
- 全图全精度模拟、跨进程确定性、普通存档恢复及严格复现通过 [04](04-deterministic-simulation.md#确定性验收) 与 [09](09-persistence.md#本阶段保存与复现契约)的证据矩阵；默认有界录制和故障复现包可用。
- 世界编辑器的新建、生成与存档恢复入口统一，三路表现、跨区观察及诊断可用，旧四切片按覆盖等价条件退役。
- 世界编辑器可以创作、校验并发布车辆／建筑蓝图、体素定义与聚居地 Layout，发布结果能在世界中实际使用，流程见 [02](02-definitions-and-content.md#世界编辑器内容创作流程)；已提交的编辑支持有限撤销与重做，范围见 [04](04-deterministic-simulation.md#编辑撤销与重做)。
- 在冻结的世界规模、负载和修改频率下，普通 1080p 窗口中的运行与长期稳定满足下文的[本阶段性能目标](#本阶段性能目标)。目标实机暂无时保持待验证；桌面停靠和多显示器不作为本阶段完成条件。

修改与破坏测试操作、Blueprint 形态、阵营延期及窗口策略已由 [#30](https://github.com/odradekk/train/issues/30) 确认，详见 [03](03-composite-and-behavior.md) 与 [08](08-desktop-window-and-camera.md)；其中 Blueprint 形态已由[蓝图、布局与内容定义的创作和发布决策](https://github.com/odradekk/train/issues/141)更新为在世界编辑器中创作和发布，见 [02](02-definitions-and-content.md#世界编辑器内容创作流程)。

领域自动测试、Godot 集成检查与人工观感共同验收；具体配置、操作序列和通过条件由各实施 Issue 规定。大世界、高频修改与多列车的性能要求以下文的本阶段性能目标为准，不能把小场景通过视为规模保证。

### 本阶段性能目标

测量方案与数值冻结流程由[性能验收决策](https://github.com/odradekk/train/issues/98#issuecomment-5856117703)确认，[性能 Benchmark 决策](https://github.com/odradekk/train/issues/143)将其扩展到世界编辑器。具体帧耗时分位数、卡顿容忍、可支持负载和内存稳定容差在代表负载实测后提交用户确认；实施者不得自行放宽指标后宣布达标。

- **目标配置**：Ryzen 5 3600、桌面 GTX 1650 GDDR5 4 GB、16 GB 双通道内存、SSD、Windows 11 x64。开发机只用于开发和辅助测量，其结果不能替代目标配置验收，也不据此宣称产品最低配置。
- **体验目标**：1920×1080、Compatibility 渲染器、默认复现录制开启时，正常交互（包括世界编辑器中的观察与编辑）以 60 FPS 为目标，同时模拟持续跟上 1× 时间。
- **Benchmark**：分为操作基准、真实窗口体验和长期稳定三部分，可分别选择执行并各自给出结论。编辑器负载由少量代表流程覆盖，不穷举工具组合。性能回归只与负载、环境和计量方式一致的基线比较；这些条件改变时建立新基线，并说明结果不能直接比较。
- **正式测量**：使用目标配置实机、独立 Release 构建、真实 1080p 窗口和默认开启的录制。headless 吞吐、关闭录制或部分表现的对照只用于定位开销，不能代替完整运行通过。没有目标实机测试证据前，性能保持“待验证”。
- **未达标处理**：先定位瓶颈并修正实现。可以缩减超出功能基线的压力负载或多余地图内容，但保留四站网络、三列联合运行、10 节泰坦能力、完整模拟与默认录制；不自动降低帧率目标、铁路标准或模拟精度。满足几何和功能的最小标准地图仍无法达标时，明确失败并重新提出配置或范围取舍。

## Demo 范围

Demo 是最终游戏完整可玩的最小集合，包含：

- **经济**：贸易与运行计划；聚居地的生产、库存、市场与人口模拟；资源与生产的最小链条（开采 → 生产 → 库存 → 作为贸易供给），见 [10](10-resources-and-extraction.md)–[13](13-production-runtime-and-facilities.md)。资源模型由[资源与开采改为节点属性](https://github.com/odradekk/train/issues/205)改写。
- **建设**：在自己的聚居地建造和改装建筑；扩建铁轨、修复断轨、修建新线路。
- **设计**：面向玩家的通用设计编辑器，用来设计列车和建筑，同时提供预置蓝图。
- **战斗**：武装列车、聚居地防御、世界生物和巢穴。
- **聚居地取得**：征服，以及在无人节点上建立新聚居地。
- **世界与运行**：宏观世界的生成；多列车、多节编组在世界图上运行。
- **局部场景**：聚居地、战斗、列车运行和设计编辑器。
- **时间**：1× 以上的倍速运行，见 [04](04-deterministic-simulation.md)。

## Demo 之后

AI 势力与外交；离线进度；自动贸易策略；复杂运营调度；步兵、下车作战的乘员等非列车的战斗单位。

Overlay、Top Dock、托盘与后台模式（转录 Q18、Q154、Q85）已随桌面停靠一起从产品规划中删除，不再列为以后的功能。原先排在 Demo 之后的自由式车辆设计器、面向玩家的铁路施工和武器已经进入 Demo。
