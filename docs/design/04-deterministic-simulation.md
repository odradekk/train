## 不变量

- 模拟结果与帧率、相机、窗口状态、倍速和暂停时机无关，也与是否打开场景、打开哪个场景无关。
- 核心模拟层从不等待玩家。只有玩家暂停和内部故障能让时钟停下。
- 改变核心状态的只有命令和模拟步。每条命令在一个确定的模拟位置执行一次，作为一个事务原子结算。
- 注册顺序、容器枚举顺序、线程完成顺序不得决定结果。
- 所有随机最终源于 WorldSeed。目前只使用无状态带键随机；以后引入有状态随机流时，其完整状态必须持久化。

## 规则

### 时钟与倍速

- 核心模拟层拥有独立于渲染帧率的逻辑时钟，按固定步长推进：每秒 60 步，每步 1/60 秒。Godot 只作为主机驱动时钟：主机 → 时钟 → 核心模拟层。
- 步长是游戏构建的常量。改变步长会改变模拟结果，所以它写进复现包的模拟配置。市场刻等低频系统按“每 N 步”定自己的间隔。
- 核心模拟层以同一精度模拟整个世界，不按距离、视野或场景是否打开降低精度。
- 倍速档位为暂停、1×、2×、4×、8×；完整 Demo 以标准混合负载下跟上 8× 为验收目标，见 [00](00-product-and-core-loop.md#本阶段性能目标)，不能因实测未达标自行降低最高档或模拟精度。
  - 倍速只改变每秒真实时间推进的步数，不改变步长，也不跳步。主机跟不上时实际速度下降，界面显示实际速度。
  - 自动推进跨帧只保留不足一步的时间余量。每帧工作预算耗尽后，放弃尚未执行的整步额度；游戏时间可以落后于现实时间，后续帧不追赶这段差距。模拟步仍按连续步号完整计算，不跳过状态。
  - 暂停只停止主机推进时钟，不是让列车停车。暂停期间仍然可以提交命令。
  - 暂停期间不累计宿主时间；暂停与切换倍速保留不足一步的余量。
  - 暂停和倍速是主机设置，不是命令：不录制，也不进入检查点。
  - 核心模拟层不因战斗等事件自动改变倍速或暂停。“遇敌时自动降到 1× 或暂停”这类功能是界面选项，见 [08](08-window-and-ui.md#通知)。
- 单步、推进 N 步和主机自动推进共用同一个推进入口，结果与每帧推进几步无关。
- 游戏关闭时世界不运行，没有离线进度，见 [00](00-product-and-core-loop.md)。

### 核心不等待玩家

- 凡是需要做决定的情况，例如遇敌、运行计划走到尽头、任务缺料，核心模拟层一律按玩家预设的规则或默认规则处理，并发出领域事件供界面通知玩家。玩家之后的命令只影响此后的行为。
- 战斗进行时世界不暂停，见 [ADR-0008](../adr/0008-simulate-the-world-in-a-voxel-free-core-and-build-voxel-scenes-as-presentation.md)。

### 确定性目标

- 同一游戏构建 + 同一有效语义内容 + 同一初始状态或存档 + 同一命令序列（包括每条命令的模拟位置）+ 兼容运行环境 = 相同的模拟结果。Demo 的兼容边界为 Windows x64、同一 .NET 运行时版本；更换运行时、CPU 或操作系统后需要重新验证，不默认承诺逐位一致。#35 规定更新后的 Mod 数值作用于旧实例，因此变更语义内容不属于“相同输入”。
- 确定性只覆盖核心模拟层。场景可以使用 Godot 物理等不确定的表现手段，不影响任何结果。
- 所有能够改变核心状态的遍历顺序必须显式稳定。不能让以下因素决定结果：Dictionary 枚举顺序、HashSet 枚举顺序、Behavior 注册顺序、线程完成顺序、非确定性的异步完成顺序。
- `GetHashCode()`、`HashCode.Combine()` 等运行时哈希不能生成随机键或持久化身份。字符串身份的比较与排序使用 Ordinal 语义，与结果相关的集合遍历使用显式稳定顺序。
- #26 的源码与实验结论是选型依据，不是跨环境保证；库函数、运行时或数值优化变化均需在上述边界内通过确定性验证。

### 数值类型与计算边界

- 连续量统一使用 `double`，包括地图上的位置、线路上的距离和速度；计数和运行时 ID 使用整数。体素坐标只在体素引擎层出现。Demo 不引入定点数体系。
- 核心模拟层使用普通 C# 类型与标量计算，连续坐标由多个 `double` 表达。Godot 数学类型只用于适配层与表现层，转换后的渲染值不能写回核心状态。
- 核心模拟层不使用硬件宽度可变的 `System.Numerics.Vector<T>`。后续只在性能测试证明需要时考虑向量化，并单独验证它对计算结果的影响。
- 核心状态中的连续量必须有限，拒绝 `NaN` 与正负无穷。

### 浮点存档往返

- `double` 以可无损往返的 JSON 数值保存，不按显示精度截断或固定小数位舍入。写入采用与文化无关的 round-trip 表示，读取必须还原相同的 `double` 值；不写入非有限值。
- 格式化与展示不改变核心状态。存档往返测试覆盖实际出现的连续量及边界值，并验证恢复后的模拟与不中断运行一致；存档整体结构见 [09](09-persistence.md)。

### Tick 流水线

```text
边界：执行命令（暂停时可以在同一边界依次执行多条）
1. Evaluate：读取已提交的状态，产生请求；周期性系统按自己的间隔在这里运行
2. Resolve：仲裁对共享资源的竞争
3. Commit
4. 损伤结算：每个伤害事件的伤害先全部施加，再判定哪些部件被毁、哪些车辆或建筑被摧毁；被摧毁的车辆从编组中移除
5. 派生状态：当前能力、运营状态
6. 领域事件：供场景和界面使用
```

损伤结算的规则见 [03](03-vehicles-buildings-and-designs.md#损伤与战斗事件)。战斗的射击在 Evaluate 中产生，在损伤结算中施加，随后更新士气、判定投降和战斗结束，见 [17](17-combat.md#结算)。核心模拟层没有逐体素的连通判定、断裂或所有权转移。

### 命令

- 玩家在任何界面或场景中的操作，以及控制台、调试工具和自动测试的输入，都作为命令提交给核心模拟层。打开或关闭场景、移动相机、查询、暂停和倍速都不是命令。
- 所有命令经过同一个校验与事务入口。界面、控制台和自动测试只负责把输入解析成命令，不直接修改核心状态。
- 核心模拟层不提供撤销与重做。玩家想纠正操作时，下一条新命令，例如取消任务、改装回原来的设计。设计草稿中的撤销与重做属于设计编辑器，不经过核心模拟层。

#### 模拟位置与执行时机

- 接受命令时分配递增的命令编号，并在当前边界取下一个步内序号；命令立即在这个位置执行。运行中提交的命令在当前步结束后的边界执行。“已完成的步号 + 步内序号”给全部命令一个全序，序号不能由线程完成顺序或墙钟时间决定。
- 不设带目标步的待执行队列，存档中没有待执行命令。玩家的延后操作（例如按时刻发车）是运行计划等核心状态，不靠命令队列。复现和自动测试由驱动程序在记录的位置提交命令。
- 命令编号或步内序号到达上限时整次拒绝，不消耗编号或序号。

#### 执行结果

- 每条命令以单个事务执行，结果是执行、拒绝或故障三者之一。
- 执行时检查当前前提。目标已不存在或条件不满足时拒绝；拒绝同样占用该位置并记入日志。拒绝不自动重试、不换目标，也不撤销之前已成功的独立命令；复合命令内部整体回滚。
- 内部异常或不变量破坏属于模拟故障，不伪装成普通拒绝。命令执行中出现故障时，恢复到该命令执行前的状态；模拟步中出现故障时，恢复到该步之前的状态。之后核心模拟层冻结在最后一个完整边界，记录故障并导出诊断，直到读档或重新开始。
  - 权威状态只保存稳定故障信息。新故障的调用将原始异常诊断交给宿主，由宿主立即记录一次错误日志；异常消息、调用栈和真实时间不进入检查点或命令摘要。已经冻结的会话及恢复的故障不重复产生历史诊断。
- 直接写坏内部数据和故障注入只用于隔离测试，不能作为正常世界继续模拟。

#### 规范编码

- 命令使用输入格式版本 2。版本 1 的全部种类（`voxel.*`、`vehicle.*`、`rail.*`、`train.*`、`content.publish`）不再支持，解码时按未知格式拒绝；内容发布在版本 2 中重新定义。
- 编码是紧凑的 UTF-8 JSON，字段名与字符串按 Ordinal 比较，不依赖文化设置。顶层固定先写 `input_format_version`、`kind`，再按种类写固定的字段顺序。解码不依赖字段顺序，重新编码得到同一规范文本。
- 每种命令写明其中的列表是集合还是序列：集合按稳定身份排序，序列保持提交顺序。
- 整数写明位宽和符号；实体 ID 为非零 64 位无符号整数；`double` 使用与文化无关的 round-trip（`R`）文本，拒绝非有限值。
- 解码拒绝重复字段、未知字段，缺失或不支持的 `input_format_version`、缺失或未知的 `kind`（未知格式）；也拒绝越界整数、类型错误、零实体 ID 和非有限数（非法）。
- 摘要是规范 UTF-8 字节的 SHA-256 大写十六进制。执行记录在负载外加命令编号、模拟位置和结果；日志摘要为 `SHA-256(前一摘要 + "\n" + 记录规范文本)`，初值为 64 个 `0`。
- 每种命令实现时提供自己的固定向量，预期值独立于待测编码器给出。代码中输入格式版本 1 的固定向量（`Train.Tests/WorldEditEncodingTests.cs`）在代码重构时随旧命令一起删除。

#### 命令日志

- 核心模拟层保留一份有上限的执行日志，每条记录来源、命令编号、模拟位置、规范负载和结果（执行、拒绝或故障），只保留最近若干条（目前为 256 条）并维护链式摘要。日志是历史，不进入检查点或存档。
- 诊断界面、“运行到某个条件为止”等开发工具建立在命令日志和推进入口之上，见 [15](15-design-editor-and-tools.md#调试模式)。

### Resolver

多个行为竞争共享资源时：Request → Resolver → Commit。例如 Engine A 与 Engine B 同时 RequestFuel，Resolver 采用 Explicit Gameplay Priority → Deterministic Fallback，而不是“谁先执行谁得到”。Facility 对库存 Input、Power、Labor 与 Storage Capacity 的竞争同样经 Resolver，Input 按完整 Batch 授予，Power / Labor 允许部分分配，见 [13](13-production-runtime-and-facilities.md)。生产、开采与施工 Job 严格遵守 Tick Barrier：本 Tick 提交的状态变化下一 Tick 才参与评估。

多列车通行使用同一确定性仲裁边界：结果不能由列车的遍历先后决定，平局按稳定身份裁决。具体规则见 [06](06-railway.md)。

### Transaction

- 所有修改核心状态的顶层行为拥有单调递增的 TransactionId，用于调试、日志、随机键和事件索引。
- Transaction 不采用完整 Event Sourcing；当前核心状态才是权威事实。

### 随机性

- 所有随机来自 WorldSeed，但不存在一个全局唯一、不断消费的 Random 实例。
- **目前全部采用无状态带键随机**：结果由 WorldSeed、用途和稳定身份决定，与调用先后顺序无关。稳定身份包括节点、线路、车辆、战斗、事务、步号和生成候选等；不得用候选枚举顺序充当身份。
- **算法**：基于 [SplitMix64 参考实现](https://prng.di.unimi.it/splitmix64.c) 的 64 位整数混合函数组合显式输入。运算按 `unchecked ulong` 语义执行；每次调用只依赖传入的键，不保存或推进参考生成器中的可变状态。
- **随机键契约**：固定算法版本、各用途的字段顺序与编码。数字位宽、符号、字符串编码与字段边界必须明确，不能通过运行时哈希、文化格式或注册顺序隐式产生。每个新用途都必须写明完整键布局和组合步骤，并提供固定输入到预期输出的固定向量；后续实现调整不得悄悄改变结果。原来唯一的用途“断裂平局”已随断裂规则删除，代码在重构时一并删除；世界生成、战斗落点、生物行动和新生物聚落等用途在实现时各自补齐键布局和固定向量。
- 世界生成的阶段、候选与重试使用稳定用途及候选身份构造键，候选身份与正式 EntityId 分离，不使用候选遍历序号或线程完成顺序。键规范随相应生成规则的版本解释，不能静默改变旧输入的含义；失败候选不能通过消耗正式 ID 改变后续随机结果。
- 场景也用 WorldSeed 和地点身份派生的带键随机生成，保证同一地点每次生成相同；但场景不在确定性契约之内。
- **有状态随机流延后**：目前不实现有状态随机流，也不预置 AI、市场等流。后续玩法确实需要序列推进时再添加局部流，并保存完整状态。

### 内容哈希

- Semantic Revision 使用 SHA-256。它沿用现有 Catalog 的算法，不沿用将定义属性与图片像素混在一起的 Fingerprint 规则。
- 参与语义哈希的字段、规范化编码以及 Asset Revision 与 Catalog Generation 的分工见 [02](02-definitions-and-content.md)。随机取值与 Revision 内容身份是两个独立契约。

### 运行时 ID

- 运行时对象使用存档内唯一的确定性整数 ID：NextEntityId : ulong；不使用随机 UUID。
- ID 分配必须发生在确定性的 Commit 顺序中。跨存档的 Definition 身份继续使用 Namespaced ID。
- 生成候选使用独立的稳定身份，正式实体 ID 只按成功提交的稳定顺序分配；失败候选或失败事务回滚临时分配的实体 ID，命令编号与拒绝记录仍保留。已成功提交的 ID 即使对象销毁也不回收或重新分配给另一对象。
- 保存并核验 NextEntityId、下一个命令编号和当前步内序号；计数溢出明确拒绝，不绕回或重排现有 ID。

### 录制与复现

录制与复现用于排错和验证确定性。核心模拟层是确定的，一份起点状态加上之后按模拟位置排列的命令，就能在别处把这段运行原样重算一遍。经营游戏的问题往往在自动运行很久之后才出现，出问题后的存档只能看到已经坏掉的状态；有了录制，开发者可以重算到出错之前，逐步检查最早出错的地方。它不是玩家能看的回放，也不是撤销或存档。

核心负责命令记录、核心状态捕获、检查点和确定性重放；内容层提供所需内容，Godot 宿主组织完整存档与复现包、文件访问及会话切换。具体责任见[四模块契约规范](../contracts/README.md#跨层工作的责任)，跨层事务协议由其专票确定。核心重放计算仍须能在无 Godot 的测试中运行，不能因包的组装归宿主而依赖引擎。

- **默认开启**：所有构建都默认录制，包括 Demo 的玩家版本，玩家报告问题时可以导出复现包。
- **录制内容**：起点是本次会话加载或新建时的核心存档；之后记录每条命令的模拟位置、规范负载和结果。场景开关、相机等观察操作只作为观察记录，不是输入；暂停和倍速不记录。
- **窗口**：定期在完整边界另写一份核心存档作为新起点，确认新起点可用后才裁掉更早的起点和命令，只保留最近几份起点。写新起点失败时保留已有资料，并标记录制不完整。容量和起点间隔在性能实测后确认。
- **内容发布**：内容发布仍在窗口内时，保留发布前后的内容和发布结果，不能只留下发布后的状态。
- **故障片段**：发生内部故障时，自动保留当前这段录制，不随后续裁剪丢失。
- **复现包**：一个带格式版本清单的 ZIP，包含：
  - 起点存档；
  - JSON Lines 格式的命令；
  - 所需内容，包括被引用的设计和用户内容；
  - 构建与环境清单：游戏构建、模拟配置、操作系统与架构、.NET 版本；
  - 检查点摘要。

  导出先完整写入临时文件并校验，再发布目标文件；失败时保留已有文件。
- **重放**：在隔离环境中只运行核心模拟层，使用包内的内容，不覆盖已安装的 Mod 或用户内容库。重放到记录末尾、首次与检查点不一致或记录中的内部故障时停止，并报告位置；无法理解的输入或缺失的依赖明确拒绝，不跳过。重放时可以打开场景，场景按核心状态重新生成，不保证像素一致。
- **严格复现与普通读档分开**：严格复现核对原构建、原有效语义内容、模拟配置和兼容环境，不使用更新后的内容；普通读档使用当前安装的内容，并报告状态适配，见 [09](09-persistence.md)。
- 重放的界面、从重放建立可编辑副本等工作流见 [15](15-design-editor-and-tools.md#录制检查点与隔离重放)。

### 确定性验收

- 同一起点和命令序列重复运行，在相同模拟位置比较权威检查点。
- 连续运行与中途保存、退出、读档、继续运行，在相同有效语义内容下到达相同模拟位置时结果一致；内容更新后的读档另行验收状态适配。
- 改变渲染帧率、倍速、暂停时机，打开、关闭或切换场景，只要命令仍在相同的模拟位置执行，结果就必须一致。暂停期间的多条命令须保持相同的步内次序。
- 随机算法、键编码和命令编码以固定输入与预期输出验证，避免“同一错误实现跑两次”仍然通过。
- **权威检查点**：在完整边界写出一份与存档、日志分开的规范文档，再对这份 UTF-8 文本求 SHA-256（大写十六进制）。
  - 纳入：所有会影响后续模拟的核心状态，以及种子、生成器版本、模拟步、步内序号、下一个命令编号、下一个实体 ID、事务计数和内部故障。具体字段清单在代码重构时由核心状态的定义确定。
  - 无序集合按稳定身份排序，有序关系保持原顺序；`double` 使用 `R` 格式，拒绝非有限值。
  - 不纳入：场景及其状态（包括当前打开哪个场景）、相机、窗口、渲染、缓存、暂停状态、倍速、存档 UUID、显示名和日志。
  - 来源、构建身份和语义内容摘要记在检查点外层，对照前先核对。构建身份对不上、任一侧缺失或环境不在兼容边界内时，不能报告“已验证一致”；语义内容摘要不同是合法的内容适配，不报成确定性失败。
  - 差异报告定位最早的检查点、对象和字段。内部故障与合法的运营状态（停用、受损等）是不同字段。预期编码和摘要必须独立于待测编码器给出。

证据矩阵定义验收要求，不代表当前实现已通过：

| 对照或场景 | 必需证据 |
| --- | --- |
| 同输入重复运行；保存、退出、恢复后继续 | 跨进程比较相同模拟位置的检查点；失败报告能定位首次差异的对象与字段。 |
| 暂停时的命令与拒绝 | 保留步内次序，覆盖执行和拒绝；目标消失等预期拒绝不重试、不换目标、不撤销之前的独立命令，后续命令继续；保存恢复前后结果一致。 |
| 列车在图上运行 | 同向跟车与方向锁、对向等待不饿死、站台排队、断轨掉头、替换计划；跨保存恢复与不中断运行一致，规则见 [06](06-railway.md)。 |
| 建造、改装、修理、拆解与委托 | 任务启动、进行、完成与失败，跨保存恢复与不中断运行一致。 |
| 损伤与战斗结算 | 同一伤害事件的结果不依赖遍历顺序；开战与加入、撤退、投降与占领、聚落清剿，以及部件被毁、车辆摧毁与编组变化，跨保存恢复与不中断运行一致，规则见 [17](17-combat.md)。 |
| 地图生成 | 覆盖生成成功、失败与重试；改变集合枚举顺序不改变结果。 |
| 与观察无关 | 改变帧率、倍速、暂停时机，打开、关闭、切换场景，不改变同输入的结果。 |
| 损坏或不兼容的输入 | 明确拒绝并保持原状态；合法内容更新另行验收适配，不混入同输入一致性对照。 |
| 录制与复现包 | 新起点可用后才裁剪；覆盖起点写入失败与不完整标记；重放内容发布的接受与拒绝；导出失败保留已有文件；缺依赖、不适用的版本和损坏的包明确拒绝。 |

## Demo 范围

时钟与倍速（暂停、1×–8×）、单一命令入口与输入格式版本 2、命令日志、Tick 流水线、Resolver、Transaction、标量 `double` 数值边界、基于 SplitMix64 混合的无状态带键随机、SHA-256 Revision、默认录制与复现包，以及上述确定性验收。

## Demo 之后

定点数体系、未经独立验证的向量化；离线进度（见 [00](00-product-and-core-loop.md)）、跨平台逐位一致、完整 Event Sourcing。有状态随机流不预先排期，玩法确有需要时按上文随机性规则引入。
