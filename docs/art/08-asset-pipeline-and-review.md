# 08 资产制作流程与检查

> 决策出处：美术 Q220、Q230、Q239、Q240。交付物、源文件、目录与命名、制作顺序、检查清单、检查地点与检查光照、检查人与记录、样机的作用和各阶段范围，由[资产制作流程、交付物与检查](https://github.com/odradekk/train/issues/252)于 2026-10-09 确认；自定义模型的交付物、导入约定和源文件位置由[资产访问与导入：内容、体素和 Godot 的交接契约](https://github.com/odradekk/train/issues/286)于 2026-10-10 确认；制作顺序和检查条件从[美术方向初稿](../research/art-direction-draft-2026-10-08.md)第 11–12 节改写。

> 当前里程碑是完整 Demo，制作范围见[Demo 内容与资产清单](../content/demo-catalog.md)。当前按[完整 Demo 清单](../content/demo-catalog.md)和[六阶段工单重组](https://github.com/odradekk/train/issues/294)推进，各阶段分别联调验收。第一阶段验证基础场景与小型列车样稿，第三阶段验证三台样机、模型与涂装，第五阶段验证战斗视觉样稿，第六阶段分批补齐全部正式资产。功能试玩可使用其余占位资产；正式性能测量、完整窗口长测和最终人工验收须使用全部正式资产。

## 边界

本文规定美术资产的交付物、源文件、目录与命名、制作顺序、检查清单，以及检查由谁做、怎样记录。表现字段、文件格式和校验见设计文档 [02 的表现资产校验](../design/02-definitions-and-content.md#表现资产校验)，内容目录见 [02 的内容目录与格式](../design/02-definitions-and-content.md#内容目录与格式)，渲染路径见 [07](../design/07-rendering.md)，本文引用、不重述。各类资产的画法见 [01](01-construction-language.md)–[07](07-icons-and-ui.md)。美术工单和代码工单一样由一对 agent 完成，流程和证据规则见[实现 SOP](../implement-sop.md)、[审查 SOP](../review-sop.md) 和[派发 SOP](../dispatch-sop.md)。

## 不变量

1. **在游戏里检查。** 资产在真实的 Godot 游戏里检查通过才算完成。浏览器原型（包括样稿）只用来定方向和色值，自动检查只证明文件有效，都不能代替游戏里的检查（美术 Q240）。
2. **从具体对象出发。** 按样机或切片车辆的需要制作，已有的体素先复用，缺的才做，不先做闲置的体素定义（美术 Q239）。
3. **每份资产只有一个源。** 源是 PNG 本身或生成它的工具，二者选一；用工具生成的资产，改动都在工具里做，再重新导出。
4. **美术改动不改变玩法。** 只改图和表现字段，资产修订更新，语义修订不变（设计文档 02）。
5. **画面由用户验收。** reviewer 按检查清单审截图，通过后合并；画面是否最终通过，由用户在阶段试玩中决定。

## 规则

### 交付物

| 资产 | 交付物 |
| --- | --- |
| 立方体体素 | 各面 PNG，边长为 32 px × 平铺跨度；可选的正面图；面图 Alpha 按 [03 的玩家涂装](03-color-and-paint.md#玩家涂装)制作；`icon.png`，128×128（[07](07-icons-and-ui.md#物品图标)）；`.voxel.json` 中的表现字段：`faces`、`tile_span`、`material`，写法见[体素定义的格式](../content/voxel.md)；`.png.import`，导入方式改为 Keep File（`importer=keep`） |
| 形状 | 内置目录随代码提供，不按体素交付文件；美术只检查贴图投影到形状上的效果（[01](01-construction-language.md#形状)） |
| 自定义模型 | 通过 Blender MCP 操作 Blender 制作；源文件 `.blend`；导出的 `model.glb`，贴图嵌在文件里；每个表面的材质类别（[02](02-materials-and-textures.md#形状与自定义模型)）；`.glb.import`，导入方式改为 Keep File（`importer=keep`）。单位、原点、轴和文件内容的限制见[模型文件的约定](../content/voxel.md#模型文件的约定) |
| 场景模型、样机 | 内容文件：场景模型和样机都是蓝图 `.blueprint.json`，写法见[蓝图的格式](../content/blueprint.md)。车辆蓝图和重型车辆工厂样机由创作模式维护，按精确路径登记在 `AUTHORED_FILES`；其余场景模型和建筑蓝图仍由生成器生成 |
| 检查记录 | 写在实施工单的完成评论里，见[检查人与记录](#检查人与记录) |

### 源文件

- 手绘的贴图和图标，源文件就是 PNG 本身。贴图每格 32 px，最大的平铺图 256×256，直接改 PNG，不另存分层文件。
- 贴图、共用贴图、磨损叠加、色卡和图标，由实现者逐项选择用图像模型生成或用脚本生成，并在检查记录中写明。
- 用图像模型生成的图，源文件就是最终的 PNG；检查记录写明所用模型和提示词。
- 用工具或样稿生成的图，生成它的工具就是源文件，留在仓库里，并在检查记录中写明。改色值时，样稿和对应的美术文档一起改。
- 自定义模型的 `.blend` 等源文件要保留。内置内容的源文件放在仓库根目录的 `art-source/`，按包和定义分目录，例如 `art-source/core/voxels/<local id>/model.blend`；目录里放 `.gdignore`，Godot 编辑器不会自动导入 `.blend`，导出包也不含它。源文件不放进内容包，Mod 作者自己保管源文件。
- 暂不使用 Git LFS。

### 目录与命名

- 每个体素一个定义文件和一个同名文件夹（设计文档 [02 的内容目录与格式](../design/02-definitions-and-content.md#内容目录与格式)），文件夹 `resources/voxels/<local id>/` 里的图按面命名：`top.png`、`side.png`、`bottom.png`、`front.png`、`icon.png`；自定义模型叫 `model.glb`。
- 几个面用同一张图时，直接绑定同一个文件，不复制。例如底面同顶面，就都绑定 `top.png`。
- 几个体素共用的图放在 `resources/voxels/shared/`，文件名写内容，例如 `vehicle-underside.png`。
- local id 用英文小写，单词之间用连字符，例如 `dry-grass`、`ballast`（设计文档 [02 的 ID 与命名空间](../design/02-definitions-and-content.md#id-与命名空间)）。目录只用来组织文件，不决定身份。

```text
builtin/core/resources/voxels/
├── grain.voxel.json
├── grain/
│   ├── top.png
│   ├── side.png
│   └── icon.png
└── shared/
    └── vehicle-underside.png
```

### 制作顺序

1. 选一个具体对象：样机或切片车辆，列出它要用的体素。
2. 已有的体素直接用；缺的才做，优先做能通用的（美术 Q239）。
3. 画贴图，写表现绑定。
4. 装到对象上，在游戏里按检查清单查看。
5. 通过后接入正式内容。

制作时在运行中的 Debug 构建里改图，用 `reload` 命令或 Ctrl+Shift+R 热重载后直接看效果（[控制台 reload](../console/reload.md)）。

### 检查清单

**单个体素**（做完就查）：

- 自动检查通过：内容校验（正方形、2 的幂、三面同尺寸、大小上限）和内容冒烟检查。自定义模型另查包围盒在格内、表面数和材质类别数一致、没有骨骼和动画等不支持的内容（[模型文件的约定](../content/voxel.md#模型文件的约定)）。
- `.png.import` 和 `.glb.import` 是 `importer=keep`，人工核对。
- 方向正确：侧面图的上方朝上；正面图在体素前方（局部 +Z）的那一面。
- 平铺：同种体素铺成至少 3 倍跨度宽的一片，看不出接缝；在任意位置切开，图案仍然均匀（[02 的贴图画法](02-materials-and-textures.md#贴图画法)）。
- 像素大小和相邻体素一致（32 px/格）。
- 材质类别填对。
- 按 [03 的玩家涂装](03-color-and-paint.md#玩家涂装)检查面图 Alpha、保留区 RGB 和模型表面分区；导出、过滤和 Mipmap 后仍符合该规则。
- 图标放进外框缩到 32 px 后仍认得出（[07](07-icons-and-ui.md#物品图标)）。

**装到对象上之后**（在游戏里查）：

- 三种距离：近看（约 3 米）、跟随列车的默认距离、远处（对象只占屏幕的一小部分）。
- 运动：列车过弯、相机绕车转动时，贴图不闪烁、不游移。
- 光照：三种检查光照（[05](05-lighting-and-readability.md#检查光照)）。
- 可读性：先认出整体和用途，再看细部（[05](05-lighting-and-readability.md#可读性)）。
- 轮对排布、旋转与车体匹配，转向架模型只制作侧架和轴箱，开口给专用轮对留出轮面（[06 的动画](06-wear-damage-and-motion.md#动画)）。
- 第三阶段起按 [03 的玩家涂装](03-color-and-paint.md#玩家涂装)检查涂装与保色区域，并检查内置设计的默认外观；磨损叠加和损伤符合 [06](06-wear-damage-and-motion.md)。

性能不属于美术检查，按设计文档 [00 的本阶段性能目标](../design/00-product-and-core-loop.md#本阶段性能目标)。

### 检查地点与检查光照

- 不另做资产浏览器，检查都在真实游戏里做：在线路场景和节点场景里，用一列装了新素材的编组；第三阶段起，单个体素和组装的检查也可以在设计编辑器里做。
- 三种检查光照用 Debug 构建的控制台命令切换：中性日光、阴天、夜间人工照明。只供检查，不是游戏里的时段。命令由[检查光照：Debug 构建切换三种检查光照](https://github.com/odradekk/train/issues/255)实现。

### 检查人与记录

- 自动检查由实现者运行，结果写进完成评论（实现 SOP）。
- 画面检查：实现者先按清单自查，用下述美术检查截图入口截图，截图放在被忽略的 `.godot/validation/<名称>/`，不进仓库；reviewer 对照 docs/art 审截图，通过后合并。工单标为 `awaiting-user`，由用户在阶段试玩中查看，用户确认后才关闭。
- 完成评论用一张表记录：检查项、条件（距离、光照、运动）、结果、问题。
- 不通过的问题在同一张工单里返工，超出工单范围的另开工单。用户在试玩中提出的画面问题，也在原工单里重新分派返工。
- 规格要改时，例如换色值，先改 docs/art 和该批资产的唯一源，再重新交付资产。

截图入口使用编辑器可执行文件运行独立场景；先按[本地验证约定](../local-environment.md)构建和导入。从普通存档恢复真实内容与编组，只拍指定列车的第一节车辆。场景参数为 `edge:<线路ID>` 或 `node:<节点ID>`。名称只接受英文字母、数字、连字符和下划线，输出目录已存在且非空时拒绝。

```powershell
dotnet build Train.csproj -c Debug
```

资源导入及截图都按[隔离子进程片段](../local-environment.md#agent-手动启动-godot)启动。导入使用片段中的默认参数；截图时把 Godot 参数替换为 `--path . --scene res://App/ArtCapture/ArtCapture.tscn --log-file <本次原生日志> -- --capture-save TestResults/art-input.save.json --capture-location edge:1 --capture-train 1 --capture-name issue-374`。每次启动使用新的运行目录，用户目录重定向只在子进程内生效。

用 [Train.Cli](../../examples/README.md) 的 `make` 制作配方目标位置的存档，或用 `save` 指定更早的步数。输入列车必须在所选场景中，并在接下来的 120 个模拟步内实际转向；已提交的 `basic-through/save.json` 包含停车命令，不能用它代替运动输入。下面从已启动、尚未停车的位置保存；正式美术检查应使用装有待检查素材的配方和存档。

```powershell
New-Item -ItemType Directory -Force TestResults | Out-Null
dotnet build Tools/Cli/Train.Cli.csproj
dotnet Tools/Cli/bin/Debug/net10.0/Train.Cli.dll save . examples/basic-through/recipe.json TestResults/art-input.save.json 100
# 按配方目标制作：将上一行 save 改为 make，并去掉末尾的步数。
```

成功退出码为 0，输出 129 张 PNG 和 `manifest.json`：三种距离 × 中性日光、阴天、夜间人工照明共 9 张静态图；日光下以默认跟随距离拍 60 帧过弯和 60 帧绕车。近景距车辆包围盒表面约 3 米，方位在默认方向上偏向包围盒前侧角，偏角为 `atan2(宽, 长)`、俯仰 0.2 弧度，焦点为车辆中心；其余距离使用玩家相机的默认角度和默认距离，far 使用所在场景的自由相机缩放上限：节点暂定 96 格（48 米），线路为 240 格（120 米），见[设计 08](../design/08-window-and-ui.md#相机)。文件名标明场景、距离或运动类型、光照及帧号。使用项目窗口分辨率，清单记录实际视口尺寸、构建提交、输入存档哈希、列车、每张图的模拟位置、表现时间、光照和相机变换，重复运行可比较清单与文件列表。

采集会话保持暂停，过弯每帧只用普通 `Step` 推进两步；绕车不推进。等待资源时不推进采样时钟，每次等待最多 120 秒真实时间，仍未完整显示则失败。不提交核心命令、不写存档、自动存档或录制；采集结束丢弃会话。缺输入、场景、编组，列车不在该场景、资源失败、未过弯及写盘失败均非零退出；失败后的残留图不算完整检查，换一个空输出目录重跑。

调试和发布导出都不能运行截图入口，用编辑器可执行文件运行；不能用 `--headless`。

### 样机

- 样机是检查共用体素定义的对象。新的体素定义至少装在一台样机上检查过，才算做完。
- 通用的体素定义要在不同用途的样机上都看得过去（美术 Q220、Q239）。
- 存档中的 Testbed 002 原型只是历史记录（[美术参考与原型证据](../../archive/prototypes/art-reference-v1/README.md)），不能当作检查环境。

## 本阶段

按[六阶段工单重组](https://github.com/odradekk/train/issues/294)逐阶段联调验收：

| 阶段 | 美术交付与检查 |
| --- | --- |
| 第一阶段 | 基础场景与小型列车风格样稿，在真实场景里检查 |
| 第三阶段 | 大型民用机车、泰坦武装重型车辆、重型车辆工厂三台样机，以及模型、六张推荐色卡与四种磨损叠加样稿；涂装按 [03 的目标规则与实施分工](03-color-and-paint.md#本阶段)接入与迁移 |
| 第五阶段 | 生物、损伤与战斗视觉样稿 |
| 第六阶段 | 分批完成全部正式贴图、图标、模型、车辆、建筑、自然环境、工地、生物与特效，并核对完整目录 |

每批交付遵循上文目录、源文件和三光照检查规则。历史首个切片的两张浏览器样稿曾作为该批 PNG 的生成器，不自动成为所有 Demo 资产的唯一源；新批次须明确选择 PNG 本身或生成工具。正式性能测量、完整窗口长测和最终人工验收必须在全量正式资产交付后执行。

第三阶段样稿沿用以下制作方式，后续按具体对象复用：车辆蓝图及重型车辆工厂样机蓝图由创作模式维护，按精确路径登记在 `scripts/content/generate_small_world.py` 的 `AUTHORED_FILES`，生成器保留文件并检查存在和 Schema。嵌套设备继续由生成器维护。机枪、火炮和转向架的唯一源是 `art-source/core/voxels/<id>/model.blend`，纹理打包在源文件中，与部位有关的磨损画在模型贴图上；导出的 GLB 登记为手工文件，体素绑定和 Keep File 声明仍由生成器输出。转向架使用 `bare_metal` 表面，保留 `icon.png`，不再输出转向架面贴图；轮对仍由宿主专用表现生成。共用面贴图继续使用原生成器，四种运行时磨损复用 `Rendering/scene_material.gdshader`；色卡由选色器直接绘制，轮面辨识标记由宿主的轮对表现生成。
