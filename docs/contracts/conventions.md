# 公开契约的公共约定

本页与[契约索引](README.md)一起定义四模块的共同规则，依据[四模块的依赖、公开类型归属与契约变更规则](https://github.com/odradekk/train/issues/279)。目前是目标规范；已有声明与接入样例的范围和证据见[核心契约](core.md)、[内容契约](content.md)、[体素契约](scenes.md)及[Godot 契约](godot.md)，不表示整组检查工具或模块隔离测试已经实现。

## 各种资料的权威范围

| 资料 | 唯一负责的信息 |
| --- | --- |
| 可编译契约声明 | 类型、方法签名、可见性、可空性等结构；文档引用声明，调用样例必须编译 |
| 模块接口文档 | 调用方需要知道的所有权、生命周期、时序、失败原子性、线程、释放和性能约束 |
| 设计文档 | 玩法与系统规则；接口文档引用，不复制维护 |
| 契约测试 | 验证上述承诺，不暗中增加或改变约定 |

声明、文字和测试冲突时视为契约缺陷，阻止建立新基线；任何模块不能自行选择一种解释。接口文档的解释不能代替声明的编译检查，测试通过也不能覆盖未写明的语义。成员文档遵循[代码注释规则](../implement-sop.md#code-comments)，局部说明与模块文档保持一致。

## 公开面的范围

公开契约只放调用所需的声明、值类型及其局部不变量，不放模拟算法、内容加载、设计计算、场景生成等实现。调用方应能创建或恢复会话、提交命令、推进模拟和读取结果，不需要提供核心内部如何计算的对象。实现内部的状态布局、计算阶段和缓存由实现自行决定。

普通公开数据须有受支持的构造方式，使消费方可以只依赖契约准备合法输入和测试数据。对有生命周期的会话或资源，通过公开创建操作获得；测试替身实现公开接口，不依赖生产实现构造器、反射或友元访问。无需给每个内部类建立对应接口。

## 身份、数值和单位

- 不同领域身份保持强类型，不统一成无类型字符串。跨模块声明的唯一归属见[类型归属](README.md#跨模块类型归属)；同一身份不因经过多个模块而重定义。
- 连续量沿用标量 `double`，计数和运行时身份沿用整数；耐久、伤害、流程与施工总工作量采用整数，结构累计耐久使用 `long`。工作量系数采用整数，进度、速率、电量和劳动力仍用 `double`；货币定价采用下条的局部例外。字段必须说明单位、范围、空值和特殊值，业务有效数值拒绝 `NaN` 与无穷值。不另建通用单位换算框架。确定性边界仍见 [ADR-0003](../adr/0003-use-scalar-doubles-and-stateless-random-for-determinism.md)。
- 货币余额与实际金额使用最小货币单位的有符号 64 位整数；定价中间结果保留精确分数，到结算单位才取整，不先经 `double` 近似或以 epsilon 修补。此例外由[市场决策](https://github.com/odradekk/train/issues/281) Q27 确认，规则见 [19](../design/19-markets-and-trading.md#货物的边际价格)。经[核心模拟层公开契约](https://github.com/odradekk/train/issues/287)确认，基本价值也用 `long`；价格倍率、敏感度和价差公开为万分比整数（10000 表示 1），不公开 `Fraction` 或通用数值框架。核心内部使用标准整数类型进行精确中间计算，并做必要溢出检查；意外溢出沿用核心内部故障，不新增“金额超出范围”业务拒绝或自动跳过分支。这是规划约定，尚非实现证据。
- 内容世代、设计和构成哈希、语义指纹、资产修订各有独立语义；不可因它们都能用整数或哈希表示而相互替代。规则见[内容设计](../design/02-definitions-and-content.md)。

## 不可变值与缓冲所有权

普通命令输入、查询结果、内容投影和事件数据默认具有不可变值语义：调用方保留旧结果后，后续模拟或重载不能改变它；接收方保留输入后，也不能被调用方后续修改影响。这一承诺包括集合内的元素，而不只是最外层集合。

`IReadOnlyList` 等只读访问类型本身不足以保证这项承诺。实现可以复制、冻结或共享真正不可变的数据，不要求每次深拷贝。

不可变性与相等判定是两项承诺。C# record 按成员各自的 Equals 比较；ImmutableArray 的默认相等比较底层数组身份，不递归比较元素。需要判断草稿或设计内容相同时，须比较完整字段及递归集合，不能直接把 record 的 == 当作深相等。请求配对可以使用会话与修订身份，但身份比较不能冒充内容比较。

大型网格、像素等缓冲可以在具体接口中声明借用或所有权转移的例外，但须明确有效期、线程、释放责任及失效后的行为。未经明确约定，生产方不能复用已返回的可变数组。具体缓冲策略由相关模块接口票确定，不在公共约定中预建资源管理框架。

当前体素契约已选择普通不可变网格和显示值，无借用例外，接收方释放引用即可；像素和 GPU 资源不进入体素契约。若实测要求改变这一承诺，须走下述受控变更流程。

## 失败与诊断

各模块拥有自己的错误类型和稳定错误码，共用以下分类原则，不建立覆盖所有模块的全局错误枚举，也不强制所有操作采用同一个 `Result`。

- 资金不足、设计不合法、文件缺失、格式不支持等预期失败返回明确结果，调用方不解析异常文本。
- 违反接口前提的编程错误可以抛异常；具体接口写明条件。
- 核心运行中的内部故障沿用[冻结语义](../design/04-deterministic-simulation.md#执行结果)，不伪装成业务拒绝。稳定故障信息与异常堆栈等诊断分开，后者不进入确定性状态。
- 错误提供定位所需的对象身份、字段路径和阶段；面向玩家的展示由界面负责。各接口写明失败后哪些状态保持不变，不能从一个统一错误包装推断原子性。

## 每份模块文档必须说明什么

接口文档按实际调用场景组织，包含职责和不负责的工作、公开声明引用、输入输出、单位与不变量、所有权与保留期限、生命周期、调用时序、失败及原子性、线程约束、资源释放、相关性能约束、可编译样例及相应验证入口。没有某项责任时明确说明，不让调用方猜测。

各模块分别确定具体方法和例外；本页不预设全系统同步或异步模型、线程调度、缓冲策略或事务协议。阻塞接口的语义须在对应票解决；需要 Profiling 的预算写清测量责任和确认条件，不写成已经验证的承诺。

## 契约基线与受控变更

四模块共用一组契约基线，包括可编译声明、装配工厂的公开面、接口文档和契约测试，指向明确的 Git 提交。契约只约束调用方必须知道的行为；[Godot 内部方案](../godot-host-design.md)不属于跨模块基线，内部实现调整不因写在设计文档中就成为契约变更。既定产品行为仍受设计文档约束。Demo 阶段不建立独立发布的契约包版本体系，不承诺新旧契约任意混用，也不默认维护兼容垫片。

经[阶段性交付流程](https://github.com/odradekk/train/issues/293) Q7 确认，初始基线是基础贯通阶段的准备任务，在四模块并行开工前交付共享骨架和检查入口。骨架只统一项目组织、编译范围、允许依赖、测试支持及检查入口，不提前实现后续玩法，也不制造空生产模块或抛 `NotImplementedException` 的假工厂。真实工厂随迁移接入；已存在的公开工厂面纳入检查，尚未接入的明确记录，后续加入时按受控变更更新基线。

初始基线统一完整声明、文档、可编译调用样例、共享测试情景与断言，并按[验证矩阵](testing.md#最小调用原型的验证矩阵)证明适用检查机制能够发现违规。基线固定约定与检查方式，不表示全部生产行为通过；缺少真实实现的行为逐项列为待验证并落实到阶段任务。每阶段必需的真实路径须实际通过，未实现功能不能靠替身、空结果或默认成功计入验收。本次规划本身不建立初始基线，也不将归档原型自动升级为生产检查工具。

经[完整 Demo 接口与实施计划的一致性验收](https://github.com/odradekk/train/issues/295) Q1 确认，两张准备票依次交付：[建立共享工程骨架与初始契约基线](https://github.com/odradekk/train/issues/302)先给出基线候选；[实现结构检查、实际隔离与契约检查入口](https://github.com/odradekk/train/issues/304)完成适用检查及证据后，由用户确认整组初始基线。基线候选通过前一票不等于正式基线已确认；四模块的生产实施仍须等待后一票通过。

基线变更流程：

1. 提出原因与替代方案，列出生产方、调用方、测试及实施工单的影响；签名不变的行为变化同样属于契约变更。
2. 经用户确认后，协调受影响模块的修改范围；模块不能单方面修改契约，也不能为保留旧接口而暴露内部实现。
3. 同步声明、接口文档、契约测试、调用样例和工单，运行受影响的兼容性检查。
4. 记录新的整组基线提交和实际验证结果。未完成影响处理或存在语义冲突时，不建立新基线。

提交与推送仍等待用户指令；本流程不额外授权发布。存档、内容格式、命令格式保留各自的版本规则，契约基线不能代替它们。并行分支接收变更及阶段性联调的执行流程由[交付流程票](https://github.com/odradekk/train/issues/293)确定。

经该票 Q8 确认，由接口所属模块牵头一张范围明确的变更任务，按上述流程说明原因、替代方案和影响并取得用户确认。在同一协调 PR 中同步受影响的声明、公开工厂面、接口文档、共享用例、替身、调用样例、工单及已实现的生产方和调用方；验证完成并获准合入主线后记录新的整组基线。未实现部分更新约定与任务，仍按已确认阶段实现，不因变更契约而提前开发后续阶段。

活动分支合并包含新基线的主线提交，按影响运行结构、契约、隔离和消费方检查；影响 Godot 行为或其消费契约时取得真实引擎证据。受影响分支未接收新基线前不能交付，无关工作可以继续。沿用调度 SOP 的 merge 更新方式，不改写已发布历史，不为过渡在主线长期维护两套接口；兼容检查通过也不能代替阶段联调。

## 自动检查要求

下表规定检查必须发现的违规；经[独立构建与契约检查票](https://github.com/odradekk/train/issues/291)确认的组织方式、替身责任和验证矩阵见[独立构建与契约验证](testing.md)。这些仍是目标要求，尚不是现成工具或通过记录：

| 检查 | 必须能发现的违规 |
| --- | --- |
| 依赖检查 | 项目或实际程序集越过[引用允许范围](README.md#依赖与装配)，包括间接引入其他实现或 Godot；公开签名泄露实现类型；Godot 在 `App/Composition/` 之外调用真实创建工厂 |
| 公开面检查 | 契约与工厂公开声明的变化；语义变化另由文档、测试和用户确认纳入基线，不能只靠签名差异判断兼容 |
| 隔离验证 | 不提供其他三个模块实现时，目标模块无法编译或运行自己的测试；替身通过链接对方源码、反射或友元访问绕过隔离 |

隔离测试保留公共契约和必要测试替身。Godot 测试使用真实引擎验证自身相关行为，不能用纯 .NET 替身冒充 Godot；聚合测试项目通过不等于隔离成立。开发期间持续检查契约兼容性，并执行真实模块的阶段性联调；本阶段联调通过后才能开始下一阶段开发。完整 Demo 仍须执行完整游戏联调、回归与人工测试，替身通过不能替代它们。
