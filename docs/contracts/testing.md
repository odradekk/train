# 四模块独立构建与契约验证

本页记录[四模块独立构建、测试替身与契约一致性检查](https://github.com/odradekk/train/issues/291)经用户确认的 Q1–Q7，落实[公共约定](conventions.md#自动检查要求)的验证责任。项目引用和类型归属仍以[契约索引](README.md)为准，测试政策仍以 [Testing standard](../implement-sop.md#testing-standard)为准。
本页的命令提交、业务输入身份与创作写入边界按[契约审计修订 #296](https://github.com/odradekk/train/issues/296)调整；保留上述历史决策出处，以下协议为当前约定。


本页规定目标方案。现有测试已拆分为 Core、Content、Godot 宿主三个项目，统一入口已接入模块选择；Scenes 尚无生产行为或测试项目。Core 和 Content 的正确性入口已在缺少其他模块实现的临时目录重建并运行，18 个现有项目的依赖与初始公开面基线可检查。Godot 隔离装配和整组契约基线提交尚未建立。[契约原型](https://github.com/odradekk/train/issues/292)验证过声明、调用方式、替身和检查机制，其证据范围见下文。

已归档的[运行原型](../../archive/prototypes/contract-probe/README.md)提供上述机制的最小实证入口，分别报告有限情景、真实文件与 Godot 检查，并用故意违规证明检查有效。它没有接入生产测试入口；真实模块尚未实现的项目仍记为待验证，具体运行结果与输入身份保存在忽略目录的单次摘要中。

## 四种证据分别说明什么

| 证据 | 必须执行的检查 | 不能据此宣称 |
| --- | --- | --- |
| 编译与结构 | 契约、调用样例和目标模块编译；检查项目及实际程序集依赖、公开面、工厂调用位置 | 时序、所有权、失败原子性等语义正确 |
| 契约语义 | 同一组契约情景和断言分别检查真实实现及其有限情景替身；消费者在这些情景下执行自己的生产代码 | 替身未覆盖的行为或真实 I/O 已验证 |
| 真实 I/O 与引擎行为 | 使用真实文件系统、编解码或 Godot，验证本模块实际承担的责任 | 四个真实模块已联合工作、画面质量或目标硬件体验已验收 |
| 真实模块联调 | 本阶段所需真实模块连接后的新增游戏流程与既有路径回归，以及阶段要求的验收；完整 Demo 再覆盖全部范围 | 阶段通过等于尚未开发的功能通过，或可以省略独立开发所需的契约与隔离检查 |

检查按实际执行的行为分类，不能把所有普通 C# 测试都归为单元测试，也不能把启动标记、mock 调用次数或进程未崩溃当作行为契约。

## 模块测试的组织与入口

保留 `scripts/run-tests.ps1` 作为统一入口，扩展模块选择及多个测试项目的发现与调度，不新增一套独立的测试入口。模块表示被验证的责任，现有 `family` 表示测试类别，`scope` 表示功能范围，三者不混用。

目标模块取值为 `core`、`content`、`scenes`、`godot`。增加 `-Module` 后，同维度多个取值取并集，不同维度取交集；不指定模块时保留原有选择含义。模块选择须在构建与发现前限定所需项目，不能先构建全部实现才能选择一个模块。无效名称、明确选择零匹配、必需项目或环境缺失都不得变成成功。

以下为目标入口语义；已接入的选择与尚缺的隔离证据以实际运行报告为准：

| 目标选择 | 行为 |
| --- | --- |
| `-Module core -Family unit`，其他模块同理 | 仅运行该模块选中的单元测试，提供日常反馈；不宣称完成隔离验证 |
| `-Module core -Correctness`，`content`、`scenes` 同理 | 检查目标模块的结构和调用样例，在隔离目录构建并运行该模块的正确性检查及共享契约用例；不启动 Godot |
| `-Module godot -Correctness` | 隔离其他实现，以真实 Godot 构建、导入和运行本模块的非导出检查 |
| `-Correctness` | 汇总四模块的结构、契约与隔离检查，以及届时已登记的真实模块集成检查；仍不自动包括导出、Benchmark、长测和人工验收 |

沿用现有 MSTest 元数据发现和 `scripts/runner-catalog.json` 的外部 runner 登记。隔离构建、依赖检查等机制通过这些入口汇总，断言保留在相应检查中。一次选择不重复执行同一用例；在隔离目录已运行的用例无需再在完整仓库运行一遍。共享契约变化的验证范围按受影响生产方、消费方和替身确定，不能仅按修改文件所属模块缩小。

模块测试拆开，任何独立模块测试项目最多引用本模块的一个真实实现；允许的契约范围沿用[生产依赖矩阵](README.md#依赖与装配)，不能经测试支持库绕过它。

| 模块 | 最小构建与测试入口 | 保留的契约 | 依赖替身与真实责任 |
| --- | --- | --- | --- |
| 核心模拟层 | `Core/Train.Core.csproj` 与独立的 `Train.Core.Tests` | 核心契约 | 用核心公开输入构造内容投影样例；真实核心执行命令、查询、状态编解码和确定性相关检查，不加载内容或体素实现 |
| 内容层 | `Content/Train.Content.csproj` 与独立的 `Train.Content.Tests` | 内容、核心契约 | 替换其声明的宿主能力；真实内容实现负责解析、投影及设计计算；声称覆盖物理 I/O 的用例使用真实 I/O |
| 体素引擎层 | `Scenes/Train.Scenes.csproj` 与独立的 `Train.Scenes.Tests` | 体素、内容、核心契约 | 用核心查询和内容访问替身供给情景；真实体素实现生成场景数据、拾取及编辑结果，不依赖 Godot |
| Godot 层 | 根 `Train.csproj` 的隔离装配与本模块真实引擎 runner | 三个契约 | 替换核心、内容和体素实现；真实宿主执行启动、交互、资源及文件适配。普通 .NET 测试可补充纯逻辑检查，不能替代引擎 runner |

Core 和 Content 测试已各自引用一个实现；原聚合项目的 492 个用例拆为 Core 249、Content 196、宿主 47，单独运行均通过。宿主的普通 .NET 项目 `Tests/Godot/Train.Godot.Tests.csproj` 测试日志、控制台和物理存档，不提供真实引擎或隔离装配证据。Scenes 尚无可运行实现与用例。Godot 不为对称额外建立契约程序集；真实跨模块集成测试单独归类。

## 共享用例、样例与替身

每个公开接口的所属模块维护它的契约情景、输入与预期结果、共享断言、可复用替身及可编译调用样例。宿主能力接口即使由 Godot 实现，也由声明该接口的模块维护契约断言；Godot 负责真实适配器及其引擎或 I/O 验证。

测试支持代码按接口所有者组织，只依赖所属契约及其允许引用的契约，不依赖真实实现。只写所需的普通 C# 夹具和情景，不建立通用测试框架、脚本语言或复制全部契约的测试模型。普通数据通过公开支持的构造方式创建；会话与资源通过公开创建操作取得，不反射构造、友元访问或链接对方生产源码。

同一个情景包括输入、操作顺序、预期结果和外部可观察状态。真实实现与替身可以有各自的公开入口准备过程，但共享语义断言，不能各自维护一份稍有不同的预期答案。预期结果来自契约规定和可独立核对的最小样例，不能调用被测算法重新计算一次充当答案。

| 责任方 | 必须证明什么 |
| --- | --- |
| 真实生产者 | 满足全部适用的契约用例，并有本模块完整行为测试；不能只挑替身支持的子集 |
| 可复用替身 | 对明确支持的情景运行同一组契约断言，提供符合契约的成功、拒绝、故障及生命周期行为 |
| 消费者 | 使用上述情景驱动自己的生产代码，验证处理结果与自身状态；期望的错误、所有权和时序含义与共享断言一致，不重写生产者规则 |

替身只保存情景所需的状态、返回固定结果或提供可控的完成顺序，不实现经济、模拟、内容计算等第二套业务规则。明确列出支持的情景与契约用例；缺少真实实现时，相应验证记为待验证，不能由替身结果补成通过。消费者若需要新情景，由接口所有者补充或澄清契约，并同步共享用例；不能在本地偷偷扩大替身语义。

替身遇到未配置的输入、操作或调用顺序时，让测试明确失败并指出未覆盖的情景，不能默认成功、返回空值或自行推算。只有契约规定的顺序才成为约束，不为了锁定实现细节而断言无关调用次数。

故意违反契约的测试替身只用于验证明确需要的消费方防御或检查机制。它须与合规替身区分，不参与“替身满足契约”的通过结论，也不把防御所有可能的违规提供者变成新的产品要求。

## 实际隔离与结构检查

隔离运行在本次验证拥有的临时目录中进行。按目标模块的显式输入清单，只放该模块生产源码、允许的契约、必要测试支持、测试资源，以及构建所需的配置和工具；不提供其他三个模块的实现源码或程序集。

临时目录重新构建，不从工作区复制 `bin/`、`obj/`、`.godot/` 等产物。依赖解析与输出检查须确认不存在从原仓库路径、共享构建产物或包引用偷偷取回其他模块实现的情况。复制和构建输入清单、实际解析的程序集及路径属于隔离证据，只有“换了工作目录”不足以证明隔离。清理只处理本次拥有的目录和进程，失败证据按现行运行器规则保留。

Godot 隔离构建只替换真实创建工厂所在的装配入口及其实现项目引用，宿主流程、渲染、界面和相关资源仍使用同一份生产代码。测试装配不能伪造缺失的生产程序集来蒙混依赖检查，也不能用另写的迷你宿主演示代替生产代码。真实装配入口仍须在正常游戏构建中编译并接受结构检查；隔离装配通过不能证明真实模块联调。

结构检查应组合以下证据，不能只搜索 `using` 或项目文件中的文本：

| 检查 | 输入与判定 |
| --- | --- |
| 依赖允许范围 | 检查构建求值后的项目引用、实际解析及输出程序集依赖，覆盖间接依赖和条件引用；按目标构建配置应用契约索引的允许范围 |
| 公开面 | 提取契约和公开工厂声明，与已确认基线比较，包括签名、可见性、可空性等结构；新增、删除或变化都报告，未经确认不能自动接受新基线 |
| 类型泄漏与装配限制 | 检查公开声明所用类型的归属；按解析到的真实工厂符号检查调用位置，拒绝 Godot 在 `App/Composition/` 外调用真实工厂，不能只凭路径或方法名称猜测 |
| 隔离构建与测试 | 验证目标模块在缺少其他实现时仍能编译、运行自身用例；检查测试支持未引入对方实现、友元访问或源码链接 |

公开面不变不能证明语义兼容。行为变化仍按[受控变更流程](conventions.md#契约基线与受控变更)更新文档、用例及受影响调用方，经用户确认后才记录整组新基线。提取器和构建脚本是检查工具，不在生产契约中引入检查框架。

当前 `contracts.structure` 检查 18 个已存在项目的求值引用、解析路径、输出程序集、源码归属和友元声明，并编译四组调用样例。公开声明比较使用 [public-api.txt](public-api.txt)：Roslyn 从契约源码提取开发者声明的类型、成员、record 参数、可空性和常量，并从构建后的程序集检查跨契约类型归属与枚举实际值。用户于 2026-10-11 确认这 1,163 条声明为 #304 的初始公开面基线；文件 SHA256 为 `8B23EAB5586CDB42BA530E998663C4953AFF162C204534F8E8DBBBA37415F33C`。整组基线仍需记录提交，真实工厂建立后再把其公开面纳入检查。Core/Content 的 `-Correctness` 另在只复制本模块源码与测试的目录构建并运行；Scenes 真实行为和 Godot 隔离装配保持待验证。

## 最小调用原型的验证矩阵

下表是[契约原型](https://github.com/odradekk/train/issues/292)必须覆盖的路径及责任。四份模块接口补齐具体操作、单位、生命周期和错误语义后，将每行映射到可编译调用样例及用例；签名或协议尚未确定时明确记为待验证，不由本页猜测。原型可用替身连接路径，各模块的独立运行仍只保留本模块的真实代码。

| 路径 | 契约断言与消费方责任 | 真实验证的承担方 |
| --- | --- | --- |
| 内容投影 → 核心输入 | 消费方只凭契约构造和使用数据；核心不读取布局或重算设计属性；内容生产者输出与约定样例相符 | 内容验证投影与设计计算，核心验证接收与使用；原型的固定投影不证明真实计算 |
| 核心命令、查询、事件 → 体素场景 | 按约定处理成功、拒绝和故障；保留旧快照后推进模拟或更新场景，旧值及其嵌套数据保持不变 | 核心验证结果及快照，体素验证场景消费；同时按公共约定验证保留输入不受调用方后续修改影响 |
| 场景数据 → Godot | 真实引擎完成资源提交、更新与释放，遵守线程及缓冲生命周期；换成其他模块替身后仍执行相同 Godot 生产代码 | 体素验证输出，Godot 验证真实引擎适配；有借用或所有权转移的缓冲按明确例外检查，不强制永久不可变 |
| 编辑草稿 → 设计校验与提交 | 合法、拒绝路径均可调用；拒绝不能误发布，也不能要求调用方复制合法性规则 | 内容验证校验与发布结果，体素验证编辑会话，Godot 验证提交协调；具体分工跟随对应接口 |
| 读档、内容发布、会话切换 | 新局／读档验证独立候选，同步内容命令验证接受／拒绝／冻结及完整配对；玩家单文件失败保留旧目标，开发多文件允许部分写入；真实文件适配使用真实 I/O | 各生产者验证局部承诺，Godot 用受控失败情景验证协调与自身 I/O；完整容器往返还需真实模块联调 |
| 异步结果返回 | 控制结果完成顺序，验证过期结果不发布及相关资源处理；不靠等待时间或随机竞争证明正确 | 生产者验证完成与释放契约，负责发布的消费方验证过期判断及可观察状态 |

失败断言必须对应具体错误类别和事务边界，不能把“旧状态保持”推广成所有故障一律回滚，或与核心内部故障的冻结语义冲突。读档、发布、保存和异步接入使用[跨层协议的失败矩阵](transactions.md#失败分类与验证矩阵)，资产使用[已确认的交接规则](README.md#表现资产的交接)，编辑与创作包发布使用[编辑协议的验证矩阵](editing.md#后续契约与验证)；四份接口文档补齐各自的操作声明。本页仅规定验证责任，不复制第二套协议。

设计与命令的矩阵还须覆盖 `DesignInput` 随命令提交、`CoreInputId` 不因动态库变化而改变、所有 Completed（含拒绝和故障）的依赖保留，以及接受建城后模板副本关联异常停止活动组。崩溃后的开发包只验正常加载诊断，不验自动整包恢复或无日志的完成清单。

## 证明检查能发现错误

契约原型在可抛弃副本中分别制造代表性错误，保存正确版本、故意破坏版本与恢复版本的结果。破坏版本须由预期的检查明确失败；依赖缺失、工具未启动等无关错误不算检出。之后恢复同一检查并确认通过。

| 故意破坏 | 应检出的检查 |
| --- | --- |
| 给目标模块加入禁止的实现引用，或在 Godot 装配目录外调用真实工厂 | 依赖或装配检查；隔离验证还须拒绝借用完整工作区的产物 |
| 修改公开接口使调用样例或替身不兼容 | 公开面检查及相应编译检查 |
| 在规定应保持旧状态的失败情景中提前改变旧状态 | 共享契约用例或协调方的行为断言 |
| 让旧请求晚返回，并故意允许其覆盖当前发布状态 | 受控完成顺序下的过期结果用例 |
| 复用可变数据，让后续更新改变已返回快照 | 快照保留用例，包含集合内部元素 |

这些检查机制有实质变化时重做相关故意破坏验证；不要求每个业务测试都进行变异测试。未配置情景让替身测试失败的行为也须通过替身自身的检查验证，不能仅靠使用约定。

## 阶段性联调的验收

经[阶段性交付流程](https://github.com/odradekk/train/issues/293)的 Q4–Q6 确认，各阶段的功能边界见[开发阶段](../design/00-product-and-core-loop.md#开发阶段)。每阶段使用一个明确的主分支提交验证；模块任务已合并、隔离检查或替身通过，都不能代替阶段联调。所需真实路径未实现、必需检查未执行或失败时，阶段保持未通过。

每阶段须取得以下适用证据，不要求提前实现后续阶段的功能：

| 检查 | 阶段要求 |
| --- | --- |
| 完整正确性回归与真实模块联调 | 运行当时已实现范围的完整正确性检查，包括适用的结构、契约与隔离检查；连接真实模块验证本阶段新增路径，并回归此前已贯通的路径。不能通过遗漏已实现用例缩小回归。 |
| 确定性与保存恢复 | 按[确定性证据矩阵](../design/04-deterministic-simulation.md#确定性验收)覆盖当前已实现行为，执行适用的跨进程重复运行、保存退出恢复对照，以及与帧率、倍速和场景观察无关的检查。后续行为加入时扩充矩阵。 |
| Godot 与 Windows | 在真实 Godot 中验证阶段路径，并实际导出和运行 Windows 构建；分别记录引擎运行、导出和导出后运行的结果，不能以构建成功或启动标记替代行为验证。 |
| 人工检查 | 用户检查本阶段新增流程、交互及受影响的既有路径。早期功能试玩允许占位美术，只能证明功能和交互；美术检查与完整 Demo 人工验收仍使用正式资产，见[占位资产的使用范围](../content/demo-catalog.md#占位资产的使用范围)。 |
| 规模与性能 | 对本阶段的复杂度、内存和规模风险做专项测量，记录实际负载与环境。前期结果只支持已测范围，不能冒充完整 Demo 性能通过；预算和阈值仍按产品规范实测并经用户确认。 |

完整 Demo 阶段执行[产品验收](../design/00-product-and-core-loop.md#本阶段验收)与[性能目标](../design/00-product-and-core-loop.md#本阶段性能目标)规定的全部检查，包括标准混合负载、两项完整长测、大尺寸与拥挤专项、目标实机和正式资产要求。前期不要求用尚未实现的功能凑齐混合负载，也不要求每阶段重复两项完整长测；阶段需要的专项检查仍须执行。此前证据能否复用，遵循 Testing standard 的适用性规则。

模块实施者提供本模块交付证据；协调者在阶段验收票核对已合入主线的成果、所用内容与环境，执行联调并汇总技术结论；用户完成所需人工检查并确认是否通过。先取得自动正确性与真实边界结果，再在同一被测版本上补齐阶段所需人工与性能证据。共用验证机和 MCP 的安排沿用[调度 SOP](../dispatch-sop.md#selecting-tasks)，不把多人同时运行的结果当作可比较性能数据。

阶段票将范围和证据逐项对应，区分通过、失败、未执行，以及只适用于后续阶段的条目。发现问题时保持阶段票开放，由所属模块的当前阶段修复任务处理，修复合入后按影响补验。被测提交变化后须重新判断已有证据是否适用，不能将旧通过记录直接套用到新提交；验收范围和门槛的改变仍须用户确认。用户确认放行及后续任务阻塞遵循[阶段调度](../dispatch-sop.md#stage-integration)。

## CI 与交付时机

沿用当前统一入口和显式较重 CI 的安排，目标增量如下。此表不会改变当前 [Windows CI](../ci.md) 已执行的选择；实施接入后才更新其可执行命令与覆盖说明。

| 时机 | 目标检查 |
| --- | --- |
| 日常开发 | 所改模块的相关用例；范围不确定或失败超出所选范围时扩大验证 |
| 常规 CI | 保留现有全量 unit 和游戏构建，增加依赖、公开面、调用样例编译，以及核心、内容、体素三个无引擎模块的隔离构建和契约测试；不启动 Godot |
| 显式较重检查 | 在前述检查基础上包含真实 Godot 的隔离与契约行为检查，并执行当时已登记的非导出正确性检查 |
| 相关变更交付前 | 取得受影响模块及消费者的适用证据；影响 Godot 行为或其所消费契约时须有真实引擎证据，常规 CI 通过不能代替 |
| 契约原型及整组基线确认 | 完成规定调用矩阵和相关故意破坏验证；初始基线先交候选，再由检查工具任务完成适用证据并取得用户确认，候选交付不提前确认基线；缺少真实实现的验证单列待办，不冒充生产模块通过 |
| 阶段性联调与验收 | 连接本阶段所需的真实实现，执行阶段要求的回归及人工、平台和性能验证；本阶段联调通过后才能开始下一阶段开发。完整 Demo 的全量验收要求保留，具体流程由[交付流程票](https://github.com/odradekk/train/issues/293)确定 |

先测量检查耗时，再按 Testing standard 处理成本，不提前冻结速度门槛或以耗时为由静默减少必需检查。Benchmark、长测、导出和人工检查继续按风险与阶段要求单独选择。CI 触发方式和权限保持现有约定，不自动调整分支保护或开展付费的较重运行。

## 结果与证据

继续使用 `TestResults/run-tests/<id>/summary.json`、`report.md`、原生 TRX 和引擎日志，不新建平行报告系统。扩展现有摘要时只补足本方案需要的信息：

- 被测提交与脏状态、所依据的契约基线；原型没有正式基线时记录实际声明版本，不虚构基线通过。
- 模块、构建配置、选择及实际执行命令，构建与测试耗时、环境和相关输入身份。
- 隔离输入清单、构建及加载的第一方程序集身份和来源；各接口由真实实现还是哪种替身提供，替身支持哪些情景。
- 验证矩阵到用例及原始日志的对应关系，实际证明的是编译、契约语义、真实 I/O/引擎还是联调。
- 故意破坏内容、预期失败检查、实际失败与恢复结果；未执行、受阻及仍需真实实现补齐的项目。

所选必需检查失败、受阻、取消或未完成时整体非成功，沿用现有退出码及逐项结果语义。报告中的阶段待办不能混入通过数量；替身通过、缺失真实实现和真实实现通过须能明确区分。证据放在忽略目录和 Issue 评论，不提交运行报告或截图到仓库。

接口尚未确定的条目由相应决策票补齐，原型发现的契约缺口回到接口票修订；不把这些缺口默认为后续联调工作。本页不另造一组重复的决策票，也不授权生产实现、提交、推送或版本更新。
