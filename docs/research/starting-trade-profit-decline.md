# 起步贸易四小时现金流下降调查（#586）

旧版起步贸易后两小时净现金流下降，主要是城市工业原料在约两小时后耗尽，结构金属需求随生产停止而消失，并非金属价差下降。当前版还同时受到城市初始金属库存挤压可收需求、农业镇燃料分配不足推高主食采购价的影响。现有证据支持这些原因，但没有验证任何路线或内容调整后的效果。

这里的“收益”均指钱包净现金流，不是包含期末货值的会计利润。当前列车 2 期末仍持有 100 件结构金属，不能把这部分现金占用全部视为已实现亏损。

| --- | --- | --- | ---: | ---: |
| `before-340` | `34e8de8` | 三列单机车 | 356.21 秒 | 16,061,460 字节 |
| `current` | `c0dad87` | 两列编组列车 | 380.63 秒 | 16,102,001 字节 |

两个基础版本的 Core、Contracts、Content、Tools/Cli 无差异，均使用同一份带公开诊断输出的 Release 构建；构建身份和哈希保存在 `TestResults/issue-586-trade-profit/build-identity.json`。但车队、配方、起始资金和内容库存同时变化，两个版本之间的差额不能解释为库存单变量效应。

诊断源码为 `2e8a51c7`；环境为 Windows 10.0.26300 x64、SDK 10.0.112、PowerShell 7.6.6、Python 3.10.11。Release 构建先于该源码提交，编译的两个诊断源码文件与提交 blob 一致，身份记录保留了比对结果及五个程序集哈希；后续文档修改不影响这些采集结果。

原始公开查询、事件、运行元数据及汇总均在 `TestResults/issue-586-trade-profit/`：`{current,before-340}.json`、对应 `.run.json`、`*-summary/summary.json` 和 CSV；运行二进制另存于 `diagnostic-build/`。分析不读取检查点的 `canonical_text`。原始数据不入 Git；提交内容是报告、最小 CLI 诊断扩展、汇总脚本及相应测试和说明。

矿镇冶炼也在 step 432480（2:00:08）因投入不足停产，铁矿石起点、第 1、2 小时库存为 960、480、0。但终点仍有 1100 件结构金属，足够可售；本次不能归因为金属货源已经断供。

## 上游缺口与可选后续

[市场规则](../../builtin/core/resources/rules/basic-market.market-rule.json)将生产备货时长设为两小时，[生成配置](../../builtin/core/resources/generation-profiles/basic-through-world.generation-profile.json)启用开局填货；[初始化实现](../../Core/World/WorldGenerator.cs)只在生成时填充库存，市场目标本身不会自动送货。六地现有设施计划没有导电金属、玻璃、聚合物、特种材料生产，路线也不运输它们；工业生产约两小时后缺料符合这一配置。城市电子部件最终库存为 1440，没有接入后续生产。相关规则与配置入口见[生产运行设计](../design/13-production-runtime-and-facilities.md)、[生产网络设计](../design/11-goods-and-production-network.md)及[聚居地模板目录](../../builtin/core/resources/settlement-templates/)。

| 可选调整方向 | 对应当前问题 | 后续范围 |
| --- | --- | --- |
| 路线优先补农业燃料，调整装货量或出售顺序 | 农业断能；改变运输分配和现金流 | 核心工具新票；参考 #386 范围 |
| 增加可达工业原料货源／生产计划，再接入运输 | 当前六地除城市留用库存外没有这四类原料现货，单改路线无法恢复工业供给 | 内容新票，沿 #379 的内容方向；联动核心工具路线 |
| 调整初始储备或生产备货时长、工序工作量 | 延后耗尽时刻、改变留货和生产速度；本身不会形成持续供给 | 内容新票，沿 #379 的内容方向 |
| 权衡委托备料库存与市场需求 | 车辆材料占据库存，减少城市收购需求 | 内容新票，联动 #387 |
| 隔离库存用途或增加自动补货 | 改变当前共用库存和一次性初始化规则 | 核心规则新票 |

以上是候选方向，不直接承诺修改已关闭的 #379 或 #340。本次配方没有现车交易；[#340 记录](https://github.com/odradekk/train/issues/340#issuecomment-6241900373)的补色前后 22 个样本中玩家列车、库存和现金一致，因此 [#597](https://github.com/odradekk/train/issues/597) 的 NPC 在售车型变化对本次货物贸易没有已知影响，它也不解决上述货物流问题。

## 统计口径与复现

- 每小时按完整 Position（step、sequence）比较，使用 `(小时起点, 小时终点]`；实际均价为成交金额除以成交数量，无成交记“无成交”。
- 实际消耗 = 库存起值 + 产出缓冲起值 + 本小时完成产量 + 净转入 − 库存末值 − 产出缓冲末值。它包含批次投入、居民和燃料合计，不把 `PotentialConsumption` 当实际消耗。
- 两次汇总均通过逐小时钱包对账，以及全部列车跨采样连续报告去重累计与成交事件对账；有限的近期报告没有被直接当作全程累计。

当前输出含 22 个样本、292 笔成交、4833 次生产完成及 3 次设施状态变化。三类事件 JSON 合计 2,993,125 字节。`lease-expiry` 配方会产生 13 个样本/检查点；将非事件部分按 `13/22` 缩放、事件部分按 `24/4` 倍外推，粗估输出 25,704,904 字节（约 24.51 MiB）。这是体积估算，不是上界或租约长配方的实测结果；完整分项保存在 `output-sizes.json`。
