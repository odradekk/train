# 跟随视角长帧与倍速损失分析（#478）

日期：2026-10-15。范围：[Issue #478](https://github.com/odradekk/train/issues/478)、[批准决定 D1–D8](https://github.com/odradekk/train/issues/478#issuecomment-6183067791)。本报告只分析，没有实施优化、调整 5 ms 预算或修改测量入口。

## 结论与证据强度

当前基线复现了阶段 1 的主要现象：跟随 8× 的未插桩帧 p99 为 87.55–105.62 ms、实际倍速 7.319–7.566×；地图和固定节点 8× 接近 8×。跟随 1× 也有 171.74–340.50 ms 长帧，故问题并非只有 8× 才触发。

已观察到两个相互重叠的主要长帧来源：线路后台构建的大量托管分配及 GC 暂停；线路段接入时主线程的网格资源准备和原生显示提交。不能把 GC、含 GC 的调用跨度、后台并行工作和渲染时间相加成一张互斥百分比图。`Observe` 同步调用和浮动原点变化均不足以统一解释本批长帧；单个 Core 墙钟尖峰也不能直接解释为 Core 计算量大。

倍速损失有两项主要机制：宿主执行完一步后达到预算、丢弃当帧剩余额度；引擎传给 `_Process` 的累计 delta 少于单调墙钟。后者与宿主丢步分开核算，并结合 Godot 4.7.2 的限步与时钟平滑源码解释。采样端点项保留符号并给出上界，三项逐运行闭合，见下文。

SDFGI 另有明确的持续 GPU 负担；SDFGI/TAA 的若干额外尖峰仍落在相同线路段的主线程提交上，不能用 GPU 绘制或原点变化单独解释。TAA-on 三份发生失去前台，保留、标记并计入原条件运行记录，但从“持续前台”的因果比较中排除；不能声称焦点变化对它们毫无影响。其余 TAA-on 只有 2 份对照、1 份插桩持续前台，因而本报告对 TAA 只给受限判断，不声称完成了三次无焦点干扰的因果验证。

## 插桩方法、对齐和自身开销

插桩只在本地临时提交：App主循环／driver／单步Core推进、读视图、dispatch及各边界消费者；Scenes的Observe/Present、段任务owner/edge/segment及构建快照step、地形/隧道/地表列采样/铁路网格、原点和FrameDiff；Rendering的prepare/commit、网格转换与原生提交。记录QPC起止、线程、App frame、完成step和该线程分配差额，用共同单调时间轴关联；不改变生产预算或入口。最终6个format-patch和SHA留在`probe-patches/`。

优先使用内置观测：viewport measure CPU/GPU、Performance monitors、逐draw的 `GC.GetTotalPauseDuration()` 与各代 `GC.CollectionCount` 差值；另在关键跨度记录GC累计暂停差，不能将嵌套差值相加。[GC API的含义](https://learn.microsoft.com/en-us/dotnet/api/system.gc.gettotalpauseduration?view=net-10.0)是进程生命周期的累计GC暂停，不是调用本身的CPU时间，不能从“Core跨度内发生GC”推出“Core算法消耗同等CPU”。

viewport getter异步返回，不能默认属于当前draw。最终构建在render thread写唯一`issue478.frame.N` timestamp，收集原始viewport begin/end，以唯一marker回绑；GPU原始单位ns、CPU为µs，不能按本地XML对GPU单位的错误描述缩放。24份共82235采样帧均唯一匹配，无缺失、冲突或负跨度。采样后只自然排空render delay+2帧，不在采样中强制同步。getter值仅作旁证，不以固定滞后或read_frame猜帧。viewport CPU不包含完整App，GPU跨度不等于端到端呈现延迟；未使用ETW/PresentMon，原生等待、驱动排队和未插桩区间保留未知。

跨度是inclusive墙钟，含GC、抢占和等待；父子不相加，后台与主线程不相加。分配差是线程局部累计差，含子调用和探针；跨样本边界的跨度只裁切墙钟、保留完整分配差，故只能作为分配热点线索，不能当严格30秒精确分配总额。探针在内存排队，采样后输出旁置JSON；其队列和时钟读取仍可改变分配／调度。

## 逐帧对账和倍速损失

### D1：额度、完成、丢弃及最后一步

核算依据是[当前帧驱动](../../App/SimulationFrameDriver.cs)，不是以“帧>5ms”直接推出丢步。对每帧，`A=floor((delta×v+R_before)×60+1e-9)`，R以模拟秒计；`C`是完成步数，`D=A−C`，更新余量只保留不足一步，未执行额度不追赶。预算在每个完整step及其同步消费者之后检查，所以某一步可以穿过5ms；不能把整帧超额都说成预算设置失效。

实际逐帧额度、完成步数、余量及报告计数全部相符；24轮地图/节点六份均无丢步。D1分类采用归档v2规则，保留原v1便于审计；宿主实际总丢步与D7不受分类选择影响。

effective按实际时钟定义：非末迭代取相邻`host.advance_one`入口间隔，末迭代取原循环`simulation_end_seconds`减最后步入口，包含探针入队及循环尾。b优先：任一effective迭代≥5ms归b1；否则delta≤1/60秒仍丢步归b2（少量亚5ms慢步累计耗尽预算）。其余丢步归a：delta>1/60且所有迭代<5ms。1/60是保守采用模拟步长的长delta门槛，不表示屏幕以60Hz刷新。follow8此时产生超过名义一帧8×额度；门槛并非性能验收阈值。

### D7：引擎delta与采样端点

令W为FramePostDraw采样墙钟，P为相同连续process记录的首尾QPC差，S为这批process交给driver的delta之和，v为请求倍速，ΔR为末减初余量。三项采用有符号值：

```text
请求倍速 − C/(60W)
  = D/(60W)                    宿主预算丢弃
  + v(P−S)/W                   引擎delta交付差
  + [v(W−P)+ΔR+roundoff]/W     draw/process端点、余量和舍入
```

逐帧既保留draw interval−delta，也保留process interval−delta；两者因process到draw的相位变化不应逐帧混同。引擎当前delta描述此前的引擎时钟间隔，根因事件按前一process入口→当前process入口检索，而非只找当前draw内事件。QPC间隔同时和Godot uptime差核对，并计入读取前后夹界误差；无跳帧／timescale变化。正、负交付差一起求和，不把平滑之后的补偿丢掉。

端点绝对上界使用首末process→draw相位绝对值之和×v，加不足一步、舍入残差和QPC读取裕量，再除W。App入口晚于native `Main::iteration` 取时，另以首末完整process间隔夹住native端点相位，给更保守上界。这个上界不是Godot内部平滑状态的界，也不能把所有不明时间都塞进端点；数值见对账表。

机制按本机版本的官方源码核实，而不是推测：

- [Main::iteration，4.7.2精确提交](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/main/main.cpp#L4921-L4960)：在timer advance后，若本轮physics_steps超过8，从process_step减去超额步数×1/60，再限至8；调整后的process_step传到[process回调](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/main/main.cpp#L5062)。扣减发生在timer内部deficit更新之后，后者不记录这项扣减。
- [MainTimerSync](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/main/main_timer_sync.cpp#L252-L314)：delta smoother有启用条件和leftover，不是每帧必开；[advance_checked](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/main/main_timer_sync.cpp#L432-L498)另有jitter约束和下帧deficit补偿。delta_smoothing配置为true不能单独证明它是累计丢时来源。

实测physics增量8是“达到上限”，无法恢复限前physics_steps。报告把超长间隔／8步／交付差及同期事件列为限步机制的证据，保留平滑、jitter与端点残差；不伪造每帧内部扣减数，也没有未经批准关闭平滑或提高限步来声称因果收益。

### native提交跨度测量的是什么

由本地代码可确认的托管调用链为：

`SceneDisplay.Prepare → SceneResources.Prepare → AcquireGeometry → CreateMesh → ArrayMesh.AddSurfaceFromArrays`。

`CreateMesh`先把契约中的顶点、法线、两组UV、custom通道和indices转换为Godot数组，再反转三角形绕序。`resource.mesh`覆盖这些准备以及native子调用；`resource.mesh.native`覆盖`AddSurfaceFromArrays`、随后的`GetSurfaceCount`及返回路径。后者是主线程调用墙钟，可能包含GC、原生处理和同步等待，不是GPU执行时长；也不能把`resource.mesh.native`简单解释成纯托管CPU时间。

资源准备完成后的提交链另在 `SceneDisplay.Commit` 内：退役/换父对象`RemoveChild`，更新root transform，逐visual调用`PreparedVisual.Update`，将新visual/root `AddChild`，替换fog/debug节点，最后退役visual的`Dispose`以及root的`Free`。`PreparedVisual.Update`可能设置材质参数或wheel transform；`Dispose`会释放节点及持有的资源。当前`display.commit`只有总跨度，没有这些子阶段的独立计时。因此证据尚不能区分节点进入场景树、材质/管线准备、资源退休、渲染线程同步或GC分别贡献了多少；不能把整个commit峰值直接命名成“shader编译”或“GPU上传”。本次没有扩展到Godot原生内部调用链的独立验证。

GPU/viewport CPU使用 `render_groups.entries` 内唯一`issue478.frame.N`回绑N，不使用读取时的`read_frame`，也不假定固定两帧延迟。viewport begin/end原始CPU单位为微秒、GPU单位为纳秒，分别除1,000和1,000,000得到毫秒。24份82,235个采样帧均有可回绑的完整viewport pair，无冲突和负时长。GPU原始绝对时间不与QPC比较。viewport CPU、GPU和App主线程跨度并非天然互斥，不作为可直接加总的帧分解。

### origin标记核查：必须区分候选帧与实际显示变化

插桩提交的 `RailwayScene.Present` 和 `SceneFrame` 构造均使用条件：`Enabled && (displayed is null || displayed.Origin != origin)`。因此动态name里的revision用于标识帧，不表示“每个revision都发marker”。但该条件也不等于“上一实际显示帧已完成一次平移”：没有displayed基线时会发；新的origin未被显示接纳时，之后生成帧仍可相对同一旧displayed重复发。

实际数据印证这一限制：follow8三份 `railway.origin.xyz` marker为590/543/765条，相邻marker坐标相同544/497/719次。原来的离线`per_frame.origin`、`origin_groups`、`notes.txt`条件分组和`edge2-segment5-selected.json.origin`均仅表示“origin候选marker出现在该绘制区间”，不能当作实际显示平移计数。本节以 `verify-origin.py` / `origin-verified.json` 的核对结果替代这些旧字段的解释。

实际变化采用 `report.json.identity.scene_observations[*]` 的 `sampled && origin_changed`。先用侧车首次 `view.show_frame` 的frame查到对应draw，再用首次scene observation的`elapsed_seconds`还原MeasurementRun的QPC `_created`。随后将每条scene observation的`_created+elapsed_seconds`映射至draw；本次核对的follow1/follow8/SDFGI/TAA全部18份运行均逐条通过：时间误差小于10⁻⁷秒，`completed_steps`完全相同。由此得到实际显示变化帧身份，不再使用重复candidate marker冒充变化。

| follow8运行 | 实际显示origin变化帧 | p99集合中实际变化帧 | 选中集合中实际变化帧 |
| --- | ---: | ---: | ---: |
| probe1 | 43 | 6 | 7 |
| probe2 | 45 | 4 | 6 |
| probe3 | 41 | 8 | 8 |
| 合计 | 129 | 18 | 21 |

即102个p99帧中84个、401个选中帧中380个没有同帧实际显示origin变化；follow8 probe1/2的最长帧也没有变化，probe3最长帧有。follow1三份实际变化都为8帧，前两份选中帧均无实际变化，第三份只有1个选中帧有变化。SDFGI-on实际变化为44/44/46帧，off为46/46/46帧，远少于candidate marker计数。

这些结果排除“所有线路尖峰都必须由同帧origin变化直接触发”。它们不排除origin引发的后续GPU更新、前一帧变化的延迟影响、场景切换或其他跨帧重建。特别是follow8 probe1最长帧2552的前一帧2551确有实际origin变化，因此不能用“2552无变化”进一步宣称它完全不受origin影响。
