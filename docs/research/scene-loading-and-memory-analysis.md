# 场景打开时间与内存分析（#479）

## 结论与证据范围

当前节点首开慢的主因是先构建整个节点的地形格和逐面网格，完成后再上传全部网格。现有“小型存档”生成的节点实际上铺满约 960×960 格的地形，不是只有几个建筑的体积。首个节点的实测帧包含 5,533,086 个格、11,500,184 个顶点和 3,988 个网格；未实现的城市建筑还没有进入这笔成本。节点首开约二十多秒，与 #298 的 20.8–24.1 秒处于同一量级。

内存有两个可分开验证的来源：数百万个 C# 格和顶点对象及其引用数组；转换并上传网格后形成的 Godot 渲染 buffer。独立 Ready 堆快照有约 1.92 GiB 托管对象，其中格、格引用数组、顶点及顶点引用数组约 1.67 GiB。渲染计数约 1,011 MiB，其中 buffer 约 633 MiB。整个进程的私有字节约 4.1 GiB，工作集约 2.85 GiB；这些口径不能相加。私有字节扣除 GC committed 后仍有约 2 GiB 未归因，不能把它全部分给 Godot、驱动或临时数组。

同目标重开可复用构建结果，节点约三秒；上传仍要重新进行。只把更多结果留在缓存，不能同时达到打开快和内存小。优先比较的两条路线是减少每格、每面和每个网格的表示成本，以及只构建并保留当前视野所需区块。前者处理单位成本，后者限制首次工作量和驻留范围；本票没有实施优化，也没有确认新的预算。

本报告对应 [#479](https://github.com/odradekk/train/issues/479) 和[批准决定](https://github.com/odradekk/train/issues/479#issuecomment-6172136706)。下文的开发机、暂停世界和受控几何测量用于定位，不能替代 [Demo 目标配置](../design/00-product-and-core-loop.md#本阶段性能目标)上的真实混合负载验收。节点建筑与模板场景尚待 #326，不能把本报告称为真实核心城市测量。

视觉复核了 B 第一轮全部 11 条路径的 first-visible PNG，并对比跟随重开的 Ready PNG。跟随重开的首帧能看到周边地形，但中心列车仍被未加载雾遮住；后续 Ready 截图中列车已显示。因此本表“可见”是首个场景几何出现，“可操作”是相机响应，不能解释为关注目标已显示或可拾取。后续体验验收应追加焦点目标/近处操作区域已加载的条件。

截图读回在首帧时间戳之后执行，B 的 33 次读回为 0.0059–0.0749 秒，节点首开三次为 0.0581–0.0588 秒；它可能延后可操作或随后 Ready 的观测，不能从该差值假定被测游戏本来需要这些时间。原入口插桩对照不包含 UI 五点拾取及截图读回，其自身影响另列。

每次新进程隔离 APPDATA/LOCALAPPDATA，Godot 用户着色器缓存新建；进程内重开有已构建几何可复用，用户 shader 缓存已经历前次绘制，但仍重新创建 Godot mesh 并上传。OS 文件缓存与 NVIDIA 驱动缓存均未清除，源文件和导出已被读取，分别记为未清除/偏热、共享且暖度未知。不得称这些运行“完全冷启动”。pipeline 编译次数按 Surface/Draw/Mesh/Specialization 分别记录，次数不是编译耗时；Mesh=0 也不等于没有编译。第一节点后台构建约占绝大部分等待，尚无证据表明驱动编译主导。未清同机共享驱动缓存，编译与原生上传内部的耗时仍未拆开；若后续尾部由编译主导，应安排专门机器分别清缓存与热缓存运行。

## 阶段与内存证据

临时插桩保留单调起止、线程、累计分配和 GC pause：node.layout、node.build、node.terrain_part、grid.index、mesh.cull_build、railway.terrain_render、scene.present、render.prepare、mesh.convert_upload、render.commit。嵌套阶段不相加；后台 build 与主线程轮询并行，累计 span 也不等同于点击墙钟。GC pause 已包含在墙钟阶段内，另列后不能再相加。

A 的探索性首开节点单次（临时提交 `744adc5a4ff2647bad6d3a5cd6fd5d27931184cc`）：layout 0.035 秒；整个 build 24.101 秒，其中 900 个 terrain part 累计 22.887 秒、grid.index 1.958 秒、cull/build mesh 17.964 秒；随后 render.prepare 2.744 秒、convert/upload 2.471 秒、commit 0.046 秒。build 累计分配约 3.40 GiB，网格构建子阶段约 2.09 GiB，转换上传约 0.67 GiB。这说明后台任务本身就很重，后台化没有消除玩家等待；上传尾部也不是零成本。此处为定位样本，不与最终三轮统计混用。

同步 UI handler 约几十毫秒；layout 生成与场景切换入口远小于整个 build。核心读取、内容解析和模板复制只记录合并的读档操作，没有独立归因到每个子步骤。遮罩期间主线程等待 build 的时间是关键路径依赖，不能算成另一份 CPU 开销。AddSurfaceFromArrays 区间包含 .NET 数组转换和 Godot 调用，不是精确 GPU 执行时长；着色器编译/native 细分未归因。

外部负载会影响任务等待、分配/GC、资源提交与实际绘制时刻。因此时间表只描述本次开发机条件，少量重复不能给出产品等待尾部上限；总 CPU 含本测游戏，不能全部归为外部负载。独立计数、类型尺寸及几何增长比时间更适合跨负载核对。约 2 GiB 的私有口径残差没有定位，原因排序只覆盖已归因部分，不能宣称已经解释了全部进程内存。

完整巨型包络确已实测，但空心仅占 684,040 / 37,748,736 = 1.812%。它的格数为 384²×6 层的 77.3%，面数却为 4.498 倍、托管存活为 2.929 倍。必须同时看 N、C、F，不能用每包络格平均内存推算任意建筑。完整满占用约 3,775 万格，初步仅托管主要项约 4.2 GiB，还未包含输入临时列表、上传/native、内容及其他 pair；安全预算更高，因此没有冒险测实心点。

同形状四点拟合：实心薄层对象增量约 `800,011 + 264.10N` B，空心约 `−4,047,156 + 1,008.52N` B；R² 分别 0.999998/0.999932。对宽度的幂指数约 1.910/2.079。负截距是范围内拟合产物，不是负的固定成本；每组 N 与 F 高度共线，不能据此独立推导单位面或单位格价格，更不能把空心系数用于满实心。

由快照对象尺寸与源码结构得到的主要项估算为 `M ≈ 104N + 262,168C + 344F` B：96 B 格对象及 8 B 平面引用；每个 32³ chunk 引用数组及头；每面四个 72 B 顶点和各 8 B 引用，加六个 4 B 索引。另加对象 subject、lookup、容器余量、内容、临时峰值与 Godot 资源。chunk 数必须按每个独立格组分配，不可把全城拼接后理论填满的 chunk 数当实测。

薄地形占格随面积线性增长，表面近似随面积；实心体格成本随体积增长、外表面随体积的 2/3 次方；空壳与碎片建筑的 F/N 高得多，极端离散格 F/N 可到 6。沿长度、面积、体积放大 100 倍不是同一种“百倍”。保持与当前节点相同几何组成而同时复制 N/C/F，主要托管项 10/30/100 倍就约 19/58/192 GiB、mesh buffer 约 6/19/62 GiB，仅为线性外推，不是成功承载。GC 压力、内存带宽与分页可让时间劣化，但四点不足以证明算法必然超线性。

## 原因排序与方案比较

| 排序 | 已验证事实 | 推断与未解部分 |
| --- | --- | --- |
| 1 | 节点整片 build 完成前没有节点几何提交；逐面构建占后台大部分耗时，格/顶点对象占托管对象大部分 | 这同时解释打开和内存；正式城市增加建筑后只会新增成本，具体量依占用和表面而变。 |
| 2 | 每面四个对象顶点、格对象与 32³ 引用 chunk；节点 chunk 槽平均占用约 14.7% | 稀疏 chunk 大量空引用槽和对象分配有明显表示成本；压缩效果须真实样例测，不预先承诺倍数。 |
| 3 | 几千个网格转换上传约 2–3 秒，buffer 约 633 MiB；关闭明显下降 | 托管几何和渲染 buffer 同时存在，临时转换也有成本；native 私有部分与编译耗时尚无法拆开。 |
| 4 | 独立正常首开有秒级 GC pause；build 累计分配数 GiB | pause 包含在 build 内；缺少同负载分配优化对照，不能把每个慢帧都归 GC。 |

## 待用户确认的标准

建议把“秒开”定义为 1080p 默认画质、录制/自动存档默认开启，在目标配置和标准混合负载下，地图首开、重开、node↔edge、跟随、读档后首显各至少 30 次，点击到可操作画面 p95≤0.5 秒、最大≤1 秒。焦点目标和近处操作区域须已显示、可按实际业务拾取，不能仅以周边地形出现或相机移动计为体验达标。普通场景打开不出现阻挡操作的全屏遮罩；允许远处细节在 ≤5 秒内补齐，已显示区域保持真实拾取和相机响应，尚未加载区域必须明确显示。读档总等待另设上限，不把其前置时间藏到点击前。

候选内存预算：单个节点打开后的稳态增量（相对同存档地图）私有字节≤1 GiB、GPU buffer/texture 增量≤512 MiB；整个游戏私有字节≤4 GiB、工作集≤3 GiB、渲染分配≤2 GiB。预算为 16 GiB/4 GiB 目标机器给 OS、录制及临时峰值留余量的起始提议，不是当前实现已达标、也不由开发机换算。候选/切换峰值另限为稳态增量的 1.5 倍，退役完成后的相同地图状态增量≤100 MiB；反复打开两小时不得持续增长。

放大要求采用已确认真实样例及巨型地块，至少三个 N/C/F 规模点。固定视野扩大远处场景 10/30/100 倍时，稳态驻留与首个可操作时间应保持工作集预算；若选择全量 Ready，则单独允许随总内容增长，不能偷换成整世界都 Ready。满占用巨型与碎片高暴露面属于单独边界，是否保证、内容组合和可接受细节补齐方式由用户确认。以上数值不写入脚本或 CI，本票交付后由用户决定目标、方案和后续实施。

完整切换序列中私有字节约可到 5.76 GiB，不能把单次首开的约 2.9 GiB 工作集作为全程上限。

## 官方指标依据

Windows [WorkingSet64](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.workingset64?view=net-10.0) 是驻留页，[PrivateMemorySize64](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.privatememorysize64?view=net-10.0) 是不可共享进程字节；[dotnet-gcdump](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-gcdump) 会诱发 full GC。Godot [RenderingServer](https://docs.godotengine.org/en/4.7/classes/class_renderingserver.html) 的视频/纹理/buffer 计数与 [pipeline 说明](https://docs.godotengine.org/en/4.7/tutorials/performance/pipeline_compilations.html)核对 4.7.2 源码；Release [memory.cpp](https://github.com/godotengine/godot/blob/4.7.2-stable/core/os/memory.cpp) 的 static 指标为 0，不能用于 native 归因。上述口径决定本报告的残差和未验证边界。

另外，[4.7.2 performance.cpp](https://github.com/godotengine/godot/blob/4.7.2-stable/main/performance.cpp) 的 ObjectResourceCount 读取 ResourceCache 的缓存资源数量，不是全部动态 ArrayMesh/材质实例；本输入 Ready 常为 26，不能据此断言只有 26 个原生资源。ObjectCount 与 NodeCount 的下降只作为释放的数量证据，不换算字节。
