# Demo 后性能与内存剩余差距的处理

Status: proposed

## Problem

设计 00「本阶段性能目标」里的各项目标，Demo 完成后大多仍未达标，或修复后没有重测：
- 场景打开：Linux runner 上 p95 为 0.81–4.90 秒，目标是 p95 ≤ 0.5 秒、最大 ≤ 1 秒。
- 节点内存：稳态私有字节增量超出 1 GiB 预算 0.9–2.2 GiB。
- 整个游戏的私有字节：仍高于 4 GiB。
- 离开节点后的存活堆：没有按 100 MiB 复查。
- 跟随路线：1× 实际倍速只有 0.945× 和 0.908×。
- 8×：Core 每步已在预算内，但完整游戏的 8× 从未测过。
- 远景补齐：线路首开时远景约 21 秒才补齐，目标是 5 秒内。

现有数字多数测于场景大对象分配、地形碰撞和 Core 每步成本这几轮修复之前，又分别来自开发机和 Linux runner，不能直接比较。帧耗时尾部阈值、内存按稳态还是峰值判断、加载等待上限和场景构建预算一直没定，“达标”没有完整定义。

## Proposal

1. 先把判断标准补进设计 00：
   - 帧耗时尾部：p95 ≤ 16.7 ms、p99 ≤ 25 ms、最大 ≤ 100 ms。
   - 内存预算按稳态判断。峰值由现有规则约束：候选场景构建与切换的峰值增量 ≤ 稳态增量的 1.5 倍。
   - 加载等待上限：读档到首个可操作画面 ≤ 10 秒。
   - 场景构建预算：主线程每帧场景准备 ≤ 4 ms，与设计 01、设计 07 的每帧准备预算一致。
   - 录制容量与起点间隔、区块边长、分段长度、预取距离等场景参数，按重测数据另行提交确认。
2. 先减少测量代码自身的分配：遍历场景 UI 节点、世界计数查询和探针监听，合计约占 Linux 小对象分配的 19%，会让测量结果偏高。
3. 在 Linux runner 上按设计 00 的完整测量清单重测当前 master，逐项报告每个目标的当前值和差距。清单包括：
   - 五类场景的正常操作和 8×；
   - 八种打开和切换方式，各至少 30 次；
   - 三个规模点；
   - 两小时长测。
4. 按重测结果修实现。
   - 第一优先：
     - 场景打开和远处补齐，包括线路首开时远景变晚；
     - 内存：节点增量、整个游戏私有字节、离开节点后的存活堆、两小时增长。
   - 第二优先：
     - 8× 完整游戏和跟随路线 1× 的实际倍速；
     - 节点 13 前方建好的轨道不足 32 米的时间，比基线多约 0.2 秒。
   - Scenes 和 Rendering 的小对象分配（世界场景会话接入、设计几何网格生成等）是降低 GC 暂停的手段，按重测得到的 GC 暂停占比决定修不修。
5. 正式的改前改后对照在 Linux runner 上做，一次一个。开发机只用于定位问题，以及同一窗口内交替运行的快速对照。
6. 不在本笔记范围内：设计编辑器 60 FPS；读档时 Content 剩余的大对象分配；轨道会话测试偶发挂起，单开一张缺陷工单。

## Alternatives considered

**直接修已知热点，不先重测。** 现有数字多测于主要修复之前，8× 完整游戏没有数据。按过期数据排优先级，可能修到已经不是瓶颈的地方。

**正式对照在本机安静窗口做。** 同一构建在两个窗口之间差 1.25–1.30 倍，原因未明；后台任务还会打断窗口，结论不稳定。

**阈值等重测后再定。** “达标”会继续没有完整定义。建议值已有依据，重测本身也要用它来判断。

**内存按峰值判断。** 切场景时的短暂高点也会被判超标，而尖峰已经有 1.5 倍规则约束。

**缩减测量清单。** 只测超标项能省半天，但其余目标继续没有当前数据，设计 00 也不允许自行缩短验收。

**以全部目标达标为完成。** 没有明确终点。缺少目标配置实机时，设计 00 规定性能一直是“待验收”。

**本轮同时做设计编辑器 60 FPS。** 剩余差距 2.3–21 倍，需要大改，此前讨论过的虚拟列表没有被采用。

## Acceptance criteria

- 设计 00 写明帧耗时尾部阈值、内存按稳态判断、加载等待上限和场景构建预算。
- Linux runner 上有一份按完整清单测量当前 master 的报告，覆盖设计 00 的每个目标，逐项给出当前值和差距。
- 第一优先的每一项都有已合并的修复工单，或有经用户同意的不修理由。
- 修复完成后在 Linux runner 上再做一次完整复测，逐项报告通过或仍差多少。剩余差距交用户决定下一步。

## Risks

- Linux runner 一次只能跑一个任务。完整清单约要一整天，多张修复工单的正式对照要排队，进度受它限制。
- Linux runner 是 Arc 核显，窗口由平铺窗口管理器摆放，结果不代表目标配置。目标配置实机仍然没有，按设计 00，性能结论仍是“待验收”。
- 帧耗时尾部和加载等待的建议值依据有限，重测后可能证明过严或过松，到时另提新笔记修改。
- 设计编辑器 60 FPS 和读档时的大对象分配本轮不处理，这些差距继续存在。
- 节点的缓冲区加纹理增量距 512 MiB 预算只剩约 6 MiB，修其他项时容易超出。
