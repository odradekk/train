# 节点内存剩余差距：先共享材质，大节点按体素格数定预算

Status: accepted

## Problem

设计 00 的「本阶段性能目标」要求：相对同一存档的地图，打开节点后的稳态私有字节增量不超过 1 GiB，渲染缓冲区与纹理合计增量不超过 512 MiB；各规模点都要满足同一份预算。#860 合并后，Linux runner 上三轮中位数是：

- 标准世界：私有增量 1090 MiB，超出 66 MiB。#861 之后 Linux 上测到 1137 MiB，但开发机同一时段的交替对照只差 3.7 MiB，用户认定没有变差。缓冲区加纹理 329.6 MiB，达标。
- 规模 1×：私有增量 2206–2276 MiB，超出约 1.2 GiB。缓冲区加纹理 483 MiB，离 512 MiB 只剩约 29 MiB。
- 规模 10×：约 7.7–7.9 GiB，最后一段没有稳定，只记录。

`2026-10-26-post-demo-performance-and-memory-gaps` 把节点内存列为第一优先。用户 2026-10-30 在 #860 决定先收下已测到的收益，剩下的差距另写笔记，并在笔记里决定三件事：要不要改 Scenes 契约、让帧上传后不再保留顶点数组；要不要改整站预取；要不要调整规模 1× 的预算。

#860 的定位数据（Windows，只用于定位）：

- 标准世界的私有增量里，托管存活对象约 729 MiB。其中最大的一项是上传 GPU 后仍由帧保留的托管顶点数组，标准世界约 285 MB，规模 1× 约 470 MB。
- 节点有 6654 个材质，6652 个只给一个视觉对象用，按参数归并后只剩 182 个。在 Windows 上单独测，多出的 6420 个材质约占 84 MiB 私有字节。这次测量不是完整场景，也没有在 Linux 上测。
- 规模 1× 的增量约是标准世界的两倍，原因是从地图打开聚居地时，会预取整个模板和停车线。这条规则写在设计 01，是用户在 #708 定的，为的是在聚居地里移动时不用等内容补齐。

整个游戏的私有字节在 #882（master `824b6dcc`）的两小时长测里最高 3.940 GiB，没有超过 4 GiB。

## Proposal

1. 标准世界分两步补上差距。
   - 第一步：节点场景按材质参数共享材质，参数相同的视觉对象用同一个材质实例。不改契约和设计。合并后在 Linux runner 上测标准世界和规模 1× 的节点增量。
   - 第二步：只在第一步之后标准世界仍超过 1 GiB 时做。修改 Scenes 契约，帧上传到 GPU 后不再保留托管顶点数组。契约变更合并前由用户确认。
2. 节点的私有字节预算按节点规模计算：预算 = 1 GiB × max(1, 节点场景的体素格数 ÷ 标准世界节点场景的体素格数)。
   - 标准世界节点的格数是基准，它的预算仍是 1 GiB；更大的节点按格数比例放宽。
   - 缓冲区加纹理不超过 512 MiB 不变，不按规模放宽。
   - 整个游戏私有字节不超过 4 GiB 照常判定，它是大节点的总约束。
   - 设计 00 的「本阶段性能目标」改写成这条规则。测量报告记录节点的体素格数和算出的预算，并按这个预算给出结论。
3. 整站预取不改，设计 01 和 #708 的决定保持不变。
4. 本笔记接续 `2026-10-26-post-demo-performance-and-memory-gaps` 里节点内存这一项，不替换那份笔记的其他决定。测量报告的改动沿用 `2026-10-26-performance-measurement-system` 定下的报告和读法。

## Alternatives considered

**直接改契约，帧上传后不再保留顶点数组。** 这一步省得最多：标准世界约 285 MB，规模 1× 约 470 MB。但它要改 Scenes 契约和渲染的上传流程，是大改动。材质共享已测出约 84 MiB 的收益，可能已经够标准世界用，所以契约改动放到第二步，只在不够时做。

**材质共享和契约改动一起做。** 理由同上：如果材质共享已经够用，契约改动的成本就白花了。

**接受标准世界的差距。** 差距只有 66–113 MiB，而且有一个不改契约、已测出收益的做法，不值得放弃。

**改整站预取，只预取视野附近的部分。** 规模 1× 能省下大部分差距，但玩家在聚居地里移动时会看到内容补齐，等于推翻用户在 #708 为流畅移动做的决定。

**保持 1 GiB，把规模 1× 记为已知差距。** 规模 1× 超出 1.2 GiB 以上，靠内存优化补不上。而且不管节点多大都用固定的 1 GiB，这条预算本身意义不大。

**固定两档：标准世界 1 GiB，规模 1× 2.5 GiB。** 最简单，但数字是按现状定的，换一个存档就不适用。

**按节点内的建筑数量算规模。** 大建筑和小建筑算一样多，和内存的对应比体素格数粗。

## Acceptance criteria

- 材质共享合并后，Linux runner 上标准世界和规模 1× 的节点增量各测三轮，报告私有增量、缓冲区加纹理和材质数，并和 #860、#861 的数字对照；节点画面和拾取结果不变，有测试覆盖。
- 标准世界节点私有增量不超过 1 GiB。如果第一步后仍超出，就在第二步合并后达到；第二步的契约变更合并前经用户确认。
- 设计 00 写明按体素格数计算的节点预算；测量报告记录节点的体素格数和算出的预算，并按预算给出通过或差多少，有测试覆盖。
- 规模 1× 的节点私有增量不超过按规则算出的预算，缓冲区加纹理不超过 512 MiB；各视图长测里整个游戏私有字节的最大值不超过 4 GiB。
- 规模 10× 仍只记录，不要求达标。

## Risks

- 大节点的预算放宽后，节点内存主要靠整个游戏 4 GiB 来约束。存档再变大时，整个游戏可能超出，到时还要回头处理整站预取。
- 体素格数和内存不完全成正比，材质数量、网格合并方式和建筑结构都会影响内存，算出的预算可能偏松或偏紧。
- 共享材质后，依赖单个材质实例的效果，例如选中高亮、损伤显示和涂装，可能互相影响。实现时要确认这些效果不变；做不到的对象保留独立材质。
- 规模 1× 的缓冲区加纹理只剩约 29 MiB 余量，后续改动容易超出。
- 标准世界在 Linux 上 1090 MiB 和 1137 MiB 的差别还没有定论，第一步的前后对照要在同一批次里测。
