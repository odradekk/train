# 性能测量系统：守护的操作、负载、运行位置和代码布局

Status: accepted

## Problem

设计 00「本阶段性能目标」已经写明场景打开、远处补齐、帧耗时、实际倍速和内存的目标，但测量这些目标的代码分散在约九个目录，游戏内有几组测量场景互相重复，私有内存有四种读法，帧耗时百分位算了两遍。每次正式对照用的辅助脚本（交替运行、负载采样、CPU 预检、常驻显示、汇总分析）都在验证归档里按工单各抄一份，仓库里没有维护的版本。报告一律写「阈值待定、不判通过」，唯一有阈值的 Core 吞吐基准用很小的世界、留 3 倍余量，#350 之后吞吐降了 28% 也没有拦下。结果是同一目标在不同工单里测法不同，改前改后不能可信地比较，后续优化也不能从固定的测量出发。

## Proposal

本笔记定测量系统本身；接下来做哪些性能工作、按什么顺序，由决策笔记 `2026-10-26-post-demo-performance-and-memory-gaps` 定，两者一致：正式对照在 Linux runner 上做。

1. **守护三个操作**，目标都按设计 00：
   - **场景打开和远处补齐**：完成点是点击到可操作，以及远景全部补齐。先建这一个。
   - **完整游戏的帧耗时和实际倍速**：跟随路线、节点、聚居地和战斗，1× 和 8×，完成点是采样窗结束。Core 每步耗时在这里一起体现，不单独守护。
   - **内存**：节点稳态增量、整个游戏稳态内存、离开节点后的存活堆、两小时增长。
2. **负载**：典型负载是 standard-world；重负载是 crowded-station、busy-combat、long-consist，加上设计 00 的三个规模点（远处内容放大 10、30、100 倍）。数据用已提交的示例存档原样测，内容版本就是提交号；规模点存档由已提交的 CLI 配方生成。
3. **优化允许的行为变化**：Core 模拟结果逐字节不变（存档、回放、命令输出）；场景就绪后显示的内容不变；流式加载的顺序和时机、就绪前的空白可以变化，但不得超出目标。
4. **产品代码里的测量钩子**：只保留现有的只读观测钩子（场景显示、世界场景视图、设计编辑器面板和编辑器场景控制器、开发检查面板上的那几处）。新增钩子必须不改变行为，并经 reviewer 批准。
5. **代码布局**：游戏内的测量场景留在 Godot 宿主的测量目录，因为它们必须编进游戏程序集；runner 一侧的脚本集中到 `scripts/measure/`（运行命令、导出、常驻显示、负载采样和 CPU 预检、交替对照运行器、汇总分析），取代验证归档里的一次性副本。测量目录的 `AGENTS.md` 管这两处的规则。
6. **基线**：提交小的汇总文件，记录中位数、范围、机器、提交号和内容版本；原始数据放验证归档，不提交。
7. **运行位置和预算**：正式测量在 Linux runner `lan-linux-nightly` 上跑，由 workflow 新增的、可指定场景列表的 `measure` 选项手动触发，一次一个 job；只报告，不强制预算。开发机只用来定位问题，以及同一窗口内交替运行的快速对照。Core 吞吐基准的阶段阈值撤掉，基准本身留作诊断工具。
8. **整理现有代码**：保留 `scene-*` 一套测量场景，删掉与它重复的旧场景和渲染选项对照场景；私有内存统一成一种读法，帧耗时百分位只留一份实现；报告逐项对照设计 00 的阈值判断通过与否，没有目标配置实机时整体结论仍是「待验收」；长示例列表删掉没有存档的 `standard-world-long`。
9. **分工**：本笔记、测量规则和 `train-performance` 技能由协调者和用户在会话里写；代码改动拆成工单交给 pair，在 #812 合并后进行；全量重测 #813 等 runner 的 `measure` 选项完成后开始。

## Alternatives considered

**另建顶层测量目录。** 游戏内的测量代码本来就要编进 Godot 程序集，搬到顶层要移动大量文件，没有实际好处。

**维持现有布局。** 重复的测量场景和归档里的一次性脚本会继续增加，同一目标在不同工单里继续测法不同。

**单独守护 Core 每步耗时。** 设计 00 要求 8× 和 60 FPS 在完整游戏里同时验证；Core 每步耗时已在预算内，放进完整游戏的实际倍速里一起看即可。

**守护地图视图帧耗时、存档时间、内容加载或设计编辑器。** 前三项只有规模增长一类的结构性证据，没有变慢的报告；设计编辑器 60 FPS 已被性能笔记排除在本轮之外。

**在 CI 里强制预算。** runner 一次只能跑一个 job，完整测量要数小时，每个 PR 都跑不现实；预算还没在 runner 上校准。

**保留 Core 吞吐基准的阈值。** 它测的世界太小，3 倍余量抓不到回归，留着只会给出假的安全感。

**不提交基线。** 不能看出随时间的漂移，每次都要回归档里找。

## Acceptance criteria

- 测量目录有 `AGENTS.md`，写明布局、运行方式、钩子、基线和预算规则；`train-performance` 技能列出三个守护操作的场景、运行命令、指标、基线位置和运行位置。
- Linux runner 的 workflow 能按场景列表运行测量；`scripts/measure/` 里有交替对照、负载采样、CPU 预检、常驻显示和汇总分析各一份维护的版本。
- 重复的测量场景和渲染选项对照场景已删除；私有内存和帧耗时百分位各只有一种实现；报告逐项给出设计 00 阈值的通过与否。
- Core 吞吐基准不再有阶段阈值；长示例列表没有无存档的条目。
- 三个守护操作各有一份提交的基线汇总，来自 Linux runner。

## Risks

- Linux runner 一次只能跑一个 job，整理工单的验证、#812 和 #813 都要排队，进度受它限制。
- 删掉旧测量场景后，历史工单里用它们测的数字不能再直接复现；需要时从验证归档的副本复现。
- 只报告、不强制预算，回归要靠有人看报告才发现。
- Linux runner 是 Arc 核显、平铺窗口管理器，结果不代表目标配置；没有目标配置实机时，性能结论仍是「待验收」。
- 整理测量代码的工单和 #812 改的是同一批文件，必须等 #812 合并后进行。
