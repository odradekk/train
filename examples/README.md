## 基础贯通

`basic-through/recipe.json` 固定生成配置身份、种子、生成器版本、存档元数据、命令位置和目标位置。它使用仓库已提交的 `builtin/core`，执行 `train.replace_run_plan`、`train.start` 和 `train.stop`。命令名和计划结构沿用核心输入格式 2：`plan` 包含 `loop` 与 `stops`，基础例子使用 `{kind:"waypoint",node}`。命令裁决和模拟推进均由真实 Core 工厂执行。

在仓库根目录构建并运行：

```powershell
dotnet build Tools/Cli/Train.Cli.csproj
dotnet Tools/Cli/bin/Debug/net10.0/Train.Cli.dll run . examples/basic-through/recipe.json TestResults/run.json
dotnet Tools/Cli/bin/Debug/net10.0/Train.Cli.dll run . examples/basic-through/recipe.json TestResults/repeated.json
dotnet Tools/Cli/bin/Debug/net10.0/Train.Cli.dll compare TestResults/run.json TestResults/repeated.json
dotnet Tools/Cli/bin/Debug/net10.0/Train.Cli.dll replay . examples/basic-through/recipe.json TestResults/replayed.json
dotnet Tools/Cli/bin/Debug/net10.0/Train.Cli.dll make . examples/basic-through/recipe.json TestResults/remade.save.json
dotnet Tools/Cli/bin/Debug/net10.0/Train.Cli.dll check . examples/basic-through/recipe.json examples/basic-through/save.json
dotnet Tools/Cli/bin/Debug/net10.0/Train.Cli.dll save . examples/basic-through/recipe.json TestResults/prefix.save.json 150
dotnet Tools/Cli/bin/Debug/net10.0/Train.Cli.dll resume . examples/basic-through/recipe.json TestResults/prefix.save.json TestResults/resumed.json
dotnet Tools/Cli/bin/Debug/net10.0/Train.Cli.dll compare TestResults/run.json TestResults/resumed.json
```

输出目录须已存在，制作存档要求目标文件不存在。`run` 输出模拟位置、权威检查点、`CoreInputId` 及运行身份；`compare` 先核对 `CoreInputId` 和当前构建／运行环境，再由核心比较检查点，失败返回非零退出码并报告首个差异位置与字段。它也支持从连续运行中已有的检查点位置开始比较恢复运行的完整后缀，上例以 150:0 为保存边界。`replay` 使用本次运行的录制及内容视图逐检查点核对，不读写复现包。

工具只加载内置内容。PNG 端口支持 8 位 RGBA、非交错编码，校验签名、块 CRC、头部、解压长度。GLB 复用宿主的容器检查，从 BIN 块中的实际 POSITION 顶点及节点层级变换计算米制包围盒，并报告表面透明方式和不支持特性的事实；内容层判断是否符合单格模型规则。CLI 支持单 BIN、未归一化且非 sparse 的 FLOAT VEC3 POSITION 和节点 TRS／matrix；`extensionsRequired` 非空时返回 `UnsupportedContent`。无法解码返回 `CannotDecode`，不支持的编码返回 `UnsupportedContent`，不读取外部资产。这不替代真实 Godot 资产解码或视觉验证。

`basic-through/save.json` 是推进到 200:0 的普通格式 6 存档，当前核心载荷为格式 23。`make` 推进到配方目标后保存，`save` 在指定步的序号 0 边界保存；该位置的命令由 `resume` 执行。保存同时捕获核心状态与内容依赖，UUID、名称和保存时间取配方固定值。容器编解码、临时文件读回校验及发布直接链接宿主同份源码；恢复依次读取容器、解码核心和内容、准备恢复内容、准备核心、激活后继续配方。

Godot 开发构建（编辑器运行和调试导出）的主菜单提供“从示例开始”，发布构建隐藏此入口。游戏从 `res://examples/basic-through/save.json` 读取同一份普通存档，经过正常恢复流程打开暂停的宏观地图，不执行配方。恢复后的对局使用新 UUID，沿用名称“基础贯通小世界”，标记为未保存；第一次手动或自动保存才写入新 UUID 的用户存档目录，原示例保持不变。

发布导出的 `--smoke` 从 PCK 验证示例恢复、新身份、200:0、暂停和未保存状态，并检查菜单入口隐藏；不保存副本或读回。副本保存由宿主测试在临时目录使用真实文件 I/O 验证；调试导出的菜单入口另做人工验证。这些证据不替代 #298 的四模块阶段验收。

`check` 按配方重新运行，并与普通存档恢复后的检查点比较。比较前只显式核对检查点之外的 `CoreInputId`：运行取当前内容视图的身份，恢复取存档捕获的 `InputIdentity`，不同则报“配方或内容已变，需要重新制作”。种子、生成器版本、生成内容修订和配置已包含在存档 `world.source` 中，交给核心检查点比较报告首个差异字段，例如 `/world/source/world_seed`。示例一致性以检查点摘要为准，容器头部或内容载荷的无关变化不要求字节一致；正常恢复只需要 `save.json`。工具保持两个模块载荷不透明。

已提交示例的重新制作比较仅在 Windows 测试，同机跨进程比较在所有平台测试。示例一致性检查使用当前已提交的内置内容，不重跑内容制备脚本，也不宣称跨构建或跨平台确定性。篡改测试只改临时副本，已提交文件保持原样。

## 经济配方与查询

配方 `format_version` 仍为 1，新字段可省略。`checkpoint_steps` 是严格递增、不超过目标步的整数数组，各项表示 `step:0`；它补充保存恢复比较所需的边界。查询与权威检查点在同一位置采样，包括起点、推进到命令的边界、命令执行后、补充边界和终点。`starting-trade` 每 54000 步（15 游戏分钟）列一个检查点，直到 864000 步，包含 216000、432000、648000、864000 四个小时点。这些边界也用于在近期报告保留上限内核对两列车的报告连续性；其他配方不隐式按时间采样。

Station 的形状为 `{kind:"station",node,dwell_steps,goods_rules}`，省略后两项分别表示 0 和空规则。每条规则为 `{action,good,local_inventory,target_quantity}`；Buy 动作为 `{kind:"buy",maximum_unit_price:null}`，Sell 为 `{kind:"sell",minimum_unit_price:null}`，限价也可填非负整数。货物使用 `{kind:"voxel",definition:"core:fuel"}`；装卸命令也接受大型设备 `{kind:"composite",definition:"core:heavy-turret"}`。数组保留业务顺序，核心按实际需求、库存、钱包和容量裁决。

命令可以带可选的 `expected_decision`，取值为 `accepted` 或 `rejected`，加载时校验。CLI 记录回执后比较实际裁决，不一致时以非零退出码失败，并在错误中指出命令序号、命令种类、实际裁决和问题项；`run`、`replay`、`make`、`check` 和 `resume` 都经过同一检查。它只断言裁决，不断言问题码、数值或状态。

配方可以带可选的 `expectations` 数组，每项为 `{at,key,node,minimum,maximum}`：在 `at:0` 边界读取一个计数，`minimum` 与 `maximum` 至少给一个，均含边界；`node` 可省略，给出时只统计该节点上的对象。`at` 必须是 `checkpoint_steps` 之一或序号为 0 的 `target`。未知的 `key` 在读取配方时拒绝；不符时 `run`、`replay`、`make`、`check` 和 `resume` 都以非零退出码失败，报告位置、键、预期范围和实际值，`make` 不写存档。`samples[].counts` 在每个样本记录同一组全世界计数。计数只读公开查询，当前的键：

| key | 含义 |
| --- | --- |
| `nodes`、`settlements`、`player_settlements` | 节点数、聚居地数、玩家所有的聚居地数 |
| `trains_in_plan`、`vehicles_in_plan` | 正在执行计划的列车（活动不是 `Stopped` 或 `NoRoute`）及其车辆数 |
| `trains_running`、`trains_servicing`、`trains_queued` | 活动为 `Running`、`Servicing` 的列车数，以及有 `platform_wait` 阻塞、在节点排队的列车数 |
| `largest_train_vehicles`、`largest_train_meters` | 最长列车的车辆数和长度（米） |
| `titan_trains_in_plan` | 正在执行计划、含泰坦级车辆的列车数 |
| `buildings`、`facilities_running` | 建筑数，以及状态为 `Running` 的生产或供能设施数 |
| `jobs_working`、`dismantles_working`、`titan_builds_working` | 状态为 `Working` 的施工任务（建造、改装、修理、拆解）数，其中的拆解数，以及制造泰坦级车辆的任务数 |
| `creatures`、`creatures_guarding`、`creatures_wandering`、`creatures_raiding` | 生物总数，以及驻守、游荡、袭击聚居地或线路的生物数 |
| `armed_combats`、`armed_node_combats`、`armed_line_combats` | 至少有一个带完好武器的玩家单位（列车车辆或建筑）参战的战斗数，以及其中在节点、线路上的场数 |
| `armed_trains_in_combat`、`armed_buildings` | 活动为 `Combat` 且有带完好武器车辆的列车数；带完好武器的建筑数 |
| `large_creatures` | 内置大型生物（`core:large-creature`）的数量；生物定义没有尺寸档位，只能按身份统计 |

配方可以用 `base` 引用另一份配方的相对路径，继承它的生成输入、存档元数据、命令、检查点和预期。本配方不能覆盖生成输入和元数据；它的命令必须位于 base 目标及之后，检查点接在 base 的检查点之后，所以 base 目标之前的运行与 base 示例完全相同。

可选的 `load` 为 `{from,targets}`，`targets` 每项为 `{key,minimum,maximum}`：从 `from` 步起，在每个 `checkpoint_steps` 和终点逐项判定实际负载。除上表的键外，还可以用三个区间键：`goods_transfers`、`production_completions` 是本进程上一个测量点以来的转运和生产完成次数，`jobs_progressed` 是这段时间里进度增加的施工任务数。不满足只记录在进度文件中，不中止运行，也不影响 CLI 的退出码；长示例脚本结束时汇总各进度文件，有任一项不满足就写 `outcome=load_unmet`、逐项列出键和首末位置，并以非零退出码结束。

`run`、`replay` 和 `resume` 在输出文件旁写 `<输出>.progress.jsonl`，每个检查点和终点一行，包括墙钟秒数、本段步/秒、强制回收后的托管堆、私有字节、工作集、已保留检查点文本的字节数、全部计数和未满足的负载目标。这些数据不进检查点比较。

每次采样还检查生产、运输与仓储、施工和战斗的不变量：设施实际工作速率不超过能力速率，批次和施工进度在范围内且施工进度不倒退；库存与预留非负、货堆数量为正、列车库存不超容量；列车速度有限且非负（动力部件被毁后列车会从高于最大速度逐步制动）；每辆车最多属于一列车，编组中的车不在停放或待售列表；车辆结构和部件耐久、生物生命在零到上限之间；参战单位和其他被引用的对象都查得到；每个样本的状态都能通过读档时的核心状态校验，例如 #714 那样站台部件被毁后节点站台数没有重算，会在下一个样本记为 `state /world/nodes/platforms`。违反项按对象和字段只记首次，写进结果的 `findings`；`run`、`replay`、`resume` 先写出结果再以非零退出码失败，`make`、`save` 不写存档，`check` 直接失败。

CLI 委托支持制造车辆，以及 `request.kind` 为 `repair_vehicle` 的修理。`construction.start_owned` 另支持 `request:{kind:"dismantle_building",facility,building,priority}`，由玩家所有聚居地的施工建筑拆解建筑。制造车辆时 `facility` 是执行施工的建筑编号，能力固定为 `Construction`；`blueprint` 是内置包中的车辆蓝图身份，由内容模块交出完整设计输入。`sources` 是按消费顺序排列的库存编号数组，必须显式给出，空数组表示整份材料都从当地 NPC 补购。`maximum_payment` 为非负整数。制造任务优先级为 0。修理的 `request` 含 `facility`、`vehicle`、`sources` 和 `priority`，设施形状与制造相同。改装的 CLI 配方入口尚未增加。

租期必须是正式规则一天（5,184,000 步）的整数倍；配方不能借缩短租期加速验证。不支持本票未使用的续租、手动货物买卖或自动装卸。这些是 CLI 配方能力，没有新增游戏控制台命令，单命令手册不适用。

`run`／`replay`／`resume` 的 JSON 另外包含：

- `samples[]`：位置（节点位置包含可空 `entered_from`、`entered_track`、`next_edge`、`next_track`，与 Core 公开位置一致）、钱包、全局未归属委托工钱，全部列车的位置／活动／库存身份／当前运行累计／近期报告／车辆结构耐久和受损／被毁部件数，全部节点的占据种类及聚居地或巢穴编号，全部聚居地的关系、是否投降、库存身份、待售车辆与委托任务编号，以及按任务编号查询的任务种类、状态、工作进度、冻结工作量、投入货物和阻塞，全部租约的到期状态，以及这些对象引用的库存容量、已用、可用、权限和全部货物。数据直接来自公开查询；报告与当前累计保留 Core 给出的收付款、净现金流、运量、载运率和未完成规则，不重算。近期报告有核心规则规定的保留上限。
- `command_receipts[]`：配方中的零基 `command_index`、`kind`、`decision`（accepted／rejected）、`problems[{code,field,related_identities}]`、`quoted_total`。现车购买使用执行前的公开 `QuoteVehicle.Total`，车辆委托使用 `GetJobQuote.TotalPayment`；启动条件不足时为空，单纯资金不足时仍有已计算总额。其他命令为 null；报价不预留交易条件。
- `samples[].settlements[]` 另含公开查询中的 `market_goods`（库存、补货目标、留用、可售／可收量及阻塞）、`facilities`（流程、状态、实际工作速率、限制、输出缓冲、潜在消耗及阻塞）、`residents` 和 `population_needs`。潜在消耗不是实际消耗。
- `goods_transfers[]`、`production_completions[]`、`production_state_changes[]` 保留命令提交和推进返回的三类公开事件，含实际模拟位置和事件序号。成交记录含列车、聚居地、货物、数量及实际金额；生产完成量包含仍在输出缓冲中的货物。
- `samples[].unassigned_service_payments` 是全局未归属委托工钱，`samples[].commission_jobs[]` 是委托任务详情（`kind` 为施工种类），`samples[].settlements[].commission_jobs[]` 是当地任务编号。所有问题项（含 `blockers`、`reasons` 和 `incomplete_reasons`）均保留 `code`、`field`、`related_identities`。

现金流按同一运行中钱包余额的差计算，不统计成交笔数。起步例子只使用两列初始列车和货物买卖，不卖车、不租仓、不委托。两列车分别在 0、1800 步启动，每站停靠 300 步，按下表循环。买入目标表示车上该货物的目标存量，已有货物只补到目标；卖出目标均为 0，实际成交受目的地可收量限制。

### 运输与建筑材料

建城只从一列列车扣料：小站点需要 1696 件建筑材料和 2 个站台设备，基础工棚需要 412 件建筑材料和 1 个基础吊机，合计 2111 件。开局两列车分别只有 1260、1080 容量，不能单独承运。可在同一非敌对聚居地、停车且货舱为空时先解编两列车，再用 `FormTrain` 将原有 8 辆车编成一列（两台机车、五辆货车、一辆武装车）。无需买车或委托造车，合编容量为 2340，装齐建城材料后尚余 229。

当前规则下该编组具有控制部件，总牵引力 1440 kN；空车质量约 316.152 吨，建城货物约 97.096 吨，装齐后的加速度约 3.485 m/s²，高于 0.15 的出发下限。编组总长 208 米，小站点的站台段长 96 米；当前核心按中心位置运行、按站台数量预约，没有列车长度不得超过站台段的准入限制。已用 `33d06b17` 的核心规则和本票正式内容，在种子 40 新局中核对解编、合编、矿镇停靠，以及完整 BOM 的实际购买和满载运行；这不表示建城命令已通过。

默认模板中只有矿业镇的建材厂启用建筑材料生产，种子 40 的矿镇在节点 13。建材厂每批消耗 4 件石料、产出 4 件建筑材料，30 work、1 work/s，名义产率为 480 件/游戏小时；开局按两小时潜在产量预存 960 件。买够建城所需的 2108 件，还需累积 `2108－960＝1148` 件，即 287 批，至少 `287×30＝8610` 秒（2:23:30）的满速工作，另有批次启动和离散步开销；这不是无条件等待时限。六条默认生产线最初合计耗电 8，发电机输出 16，燃料 `fuel_energy` 为 960。矿镇燃料不会自动补货，必须从油田运输燃料，保持采石、建材生产和可用仓储。导电金属、聚合物等 #586 上游缺口不直接参与石料到建筑材料这条链。

`conquest/recipe.json` 使用种子 40。第 0 步把列车 2 的交战设为优先武装、只打武装单位、接敌、撤退结构比 0；对聚居地 3（林业镇，节点 8）宣战。该镇的待售车辆 13 有一挺机枪，镇内有完好武器，因此占领必须先投降。运行计划只有节点 8 一个停站，停留 400,000 步，不循环。

## 标准世界长测

`standard-world-long/recipe.json` 以 `base` 继承标准世界配方。标准世界在三场战斗同时进行的 125,050 步保存，长测从这里起判定负载，终点 1,421,800 步，负载下至少推进 1,296,000 步（6 游戏小时）。检查点在 110,000 步，以及 125,050 步起每 36,000 步（10 游戏分钟）一个；`load` 从 125,050 步起按[设计 00 的标准混合负载](../docs/design/00-product-and-core-loop.md#测试世界与标准混合负载)逐项判定：执行计划的列车 20 列、80 辆，运行、交易、排队各至少 1 列；聚居地 25 个、玩家 5 个；建筑 100 座、运行中的设施 50 个；进行中的施工 10 项；生物 100 只，驻守、游荡和袭击各至少 1 只；有玩家武装参战的战斗 3 场，节点和线路各至少 1 场；每 10 分钟至少 1 次转运、1 次生产完成、1 个施工任务有进展。游荡和袭击是短暂状态，10 分钟一次的采样会漏掉，结果如实记录。

配方只追加一条命令：无武器的列车 11 在 182,950 步到达节点 31 时遇到袭击，按交战规则撤退，188,157 步在节点 36 完成撤退后停车并保留计划；197,800 步像玩家一样重新发车，`expected_decision` 为 `accepted`。其余负载不追加命令：当地库存不够材料，NPC 车间的中型、大型和超大车辆委托都会被拒（`insufficient_goods`），只有约 48 分钟的小型货车能用本地材料制造；15 个生物聚落的聚落边都没有铁轨，节点战斗只能来自对武装聚居地的宣战，线路战斗只持续约 1,400 步。所以施工和战斗在负载达到后不久就低于目标，长测结果如实记录持续时间。

长示例脚本对这一例运行三组：A `replay` 连续运行并严格重放全程，作为连续基准；B `run` 在另一个进程重复运行；C 在 773,050 步（负载后第 3 小时）保存后由新进程 `resume`。最后 `compare` 比较 A 与 C 的后缀，`compare-repeat` 比较 A 与 B。没有已提交存档，不运行 `make` 和 `check`。

## 重制与长验证

当前核心状态格式为 23：#332 的车辆改装、拆解使用格式 16，#342 的冻结建城任务使用格式 17，#541 的节点进出铁轨使用格式 18，#343 将施工目标改为实例并增加地块后使用格式 19，#350 增加战斗、交战规则和撤退目的地后使用格式 20，#344 增加铁路扩建与修复任务及按边自动修复来源后使用格式 21，#351 增加生物群后使用格式 22，#352 增加聚居地士气与投降后使用格式 23，命令输入和重放外壳仍为格式 2；格式 1–22 的示例存档和重放起点须重新制作，不能手工修改生成载荷。断轨修复的公开配方是 `rail-repair`。#622 已接入设置生产计划。

同一份存档使用同一种构建配置制作和检查。日常测试只运行短经济命令、现车、容量和委托例子。本次车辆内容迭代中，`starting-trade` 只做 `make` 和一次正常读取；`lease-expiry` 通过 Linux runner 制作并执行长验证。长例不能放进日常集成层。改内容的工单只重制受影响的示例存档并做一次正常读取；长示例的完整检查和重放在阶段验收时做（用户 2026-10-17 决定）。

[长示例脚本](../scripts/checks/run-long-example.ps1)构建一次 Release，然后并行执行三组：A 连续运行并严格重放；B 保存退出后由独立进程恢复；C 制作普通存档再从零按配方检查。保存边界为起步贸易 **432000**、租约到期 **5183999**、断轨修复 **959400**（扩建任务进行中）、征服 **40000**（战斗进行中，宣战之后、占领之前）、清剿 **1043200**（巢穴战斗进行中，清空之前）、合法经营失败 **1060000**（无武装机车进入巢穴之后）、长编组 **17000**（编组发车之后）、标准世界 **110000**（游荡检查点）、繁忙战斗 **330000**（武装列车出发之后、放入生物之前）、拥挤站点 **880000**（大站点施工中，编组之前）、标准世界长测 **773050**（负载后第 3 小时，组合见[标准世界长测](#标准世界长测)）。`replay` 的输出作为连续基准，最后比较恢复后的完整检查点后缀，不额外运行一次 `run`；标准世界长测例外，它用 B 组 `run` 代替制作与检查，见上节。脚本创建独立运行目录，每条命令完成即保留退出码、耗时和日志，任何失败或未执行均非零退出。runner 触发与下载方法见[远端检查](../docs/run-tests.md#远端检查)。

`basic-through`、`storage-tight`、`commission-branches`、`retreat`、`damaged-vehicle-trade`、`long-consist`、`starting-trade`、`rail-repair`、`conquest`、`clearance`、`operating-failure`、`standard-world`、`busy-combat` 和 `crowded-station` 的存档在 Windows 制作；`lease-expiry` 在 Linux runner 制作。`check` 在制作平台使用同种构建配置比较；Linux 重制不能验证 Windows 存档的一致性，反之亦然。基础例子的命令形式见[基础贯通](#基础贯通)，长示例使用表中 Release 配置。同机跨进程比较、保存恢复和本次录制的严格重放在两种平台都有效，不宣称跨平台确定性。
